## Problem restated (verified)

The authorization endpoint defects are verified in current code. `MapAAuthAuthorizationEndpoint` only checks that `context.GetAAuthVerification()` is non-null (`AAuthApplicationBuilderExtensions.cs:154-158`), so a verified agent or auth token reaches the application handler even though the authorization endpoint requires a person token. It returns `401 invalid_request` when no verification result is available (`AAuthApplicationBuilderExtensions.cs:154-158`) instead of a `person-token` requirement, rejects non-JSON bodies with 415 (`AAuthApplicationBuilderExtensions.cs:163-166`) instead of the endpoint error table's `400 invalid_request`, requires `scope` unconditionally (`AAuthApplicationBuilderExtensions.cs:180-182`), and constructs `AAuthAuthorizationRequest` from only `scope`, generic verification, and `account` (`AAuthApplicationBuilderExtensions.cs:190-196`). The public request type still describes "agent identity" and makes `Scope` non-null (`AAuthAuthorizationRequest.cs:4-16`).

The spec requires a resource authorization endpoint request to present and verify a person token (#authorization-endpoint-request L667-L669); a request without one is answered with `401` and `AAuth-Requirement: requirement=person-token` (#requirement-person-token L615-L627). Its endpoint error table gives `invalid_request` status 400 (#authorization-endpoint-error-responses L714-L723), and errors use `application/problem+json` with an `error` member (#error-response-format L2571-L2578). R3 then extends the same endpoint with optional `r3_operations` and says the resource maps those operations to a resource token carrying `r3_uri`/`r3_s256` (R3 #authorization-endpoint-extensions L385-L417). The SDK's own `R3Request.CreateBody` emits only `r3_operations` plus optional `account` (`R3Request.cs:20-29`, `:37-50`), so a conforming SDK R3 client is currently rejected for missing `scope`, and a body that also adds `scope` loses typed operations before the handler.

The access-mode and helper defects are also verified. `AgentTokenRequired` passes any AAuth token type (`AAuthChallengeMiddleware.cs:97-100`), contradicting `requirement=agent-token`, which asks for `typ: aa-agent+jwt` specifically and no parameters (#requirement-agent-token L560-L572). `BuildResourceTokenAsync` accepts any `AAuthVerifiedAssertion`, calls `PersonServerOf`, and treats every non-auth token issuer as the PS (`AAuthChallengeMiddleware.cs:150-190`), while resource-token issuance may happen only after verifying a person or auth token and copies `ps`, `sub`, and `presented_jti` from that token (#resource-token L729-L745). `R3Challenge.BuildCoreAsync` already enforces that same person/auth-token precondition (`R3Challenge.cs:49-59`), so the core helper is the outlier.

Trust-policy denial is verified as a signature error. `AAuthVerificationMiddleware` throws `TokenVerificationException("... not trusted by policy")` for untrusted agent, auth, or person issuers (`AAuthVerificationMiddleware.cs:231-246`), catches it immediately, and writes `Signature-Error: error=invalid_jwt` with 401 (`AAuthVerificationMiddleware.cs:254-256`, `:400-403`). That is wrong after the JWT and HTTP signature verified: AAuth verification failures are 401 with `Signature-Error` (#verification L2240-L2255), but policy denial after successful signature and identity verification is 403 and MUST NOT include `Signature-Error` or `Accept-Signature-*` (Signature-Key #access-denied L1936-L1945).

The sample/doc findings reproduce the same unsafe public pattern. Inbox publishes `/authorize` and maps it with `.RequireAAuthSignature()` (`Inbox/Program.cs:56`, `:129-138`), and the resource-managed workflow copies the same snippet (`docs/workflows/resource-managed-access.md:132-139`). The current conformance fixture intentionally authorizes on agent identity (`ResourceManagedFlowTests.cs:55-68`) and asserts the non-JSON 415 result (`ResourceManagedFlowTests.cs:235-245`), so tests codify the non-conformance.

## Recommendation

Implement candidate 2, plus the tightly coupled helper/status fixes.

Add `AAuthAccessMode.PersonTokenRequired` and make `MapAAuthAuthorizationEndpoint` attach a non-overridable authorization-endpoint metadata marker as well as the person-token requirement. This avoids a copied `.RequireAAuthSignature()` call downgrading the route back to `IdentityOnly`. `UseAAuth` should recognize either the marker or the explicit mode, run normal verification for present signatures, but answer the "no `Signature-Key`/no verified AAuth assertion" case with `401` and `AAuth-Requirement: requirement=person-token` instead of `Signature-Error`. After verification, the authorization endpoint must check the verified assertion's *validated token type* (not the untrusted `typ` header alone); anything other than `aa-person+jwt` returns the same person-token requirement and never calls the handler. Invalid/malformed person tokens still fail in verification with 401 `Signature-Error`, matching #authorization-endpoint-error-responses L723.

Change `AAuthAuthorizationRequest` into a person-token request object: nullable `Scope`, `Account`, `AAuthVerificationResult Verification`, `AAuthVerifiedAssertion PersonToken`, and an extension/feature bag. The handler receives the verified person identity through `PersonToken.Token`/`Verification.PersonServer`/`Verification.Subject`, not a generic "agent identity". Core should parse the body as a `JsonObject`, validate `account`, validate `scope` when present, and require either a non-empty `scope` or a registered authorization-extension that marks a valid replacement authorization claim. Unknown fields do not satisfy this requirement.

Add a small R0-style extension seam, for example `IAAuthAuthorizationRequestExtension` with a context carrying `HttpContext`, the request body, `IServiceProvider`, cancellation, and the request feature bag. Extensions may validate fields, store typed values, and set `SatisfiesAuthorizationRequest = true` only for a complete, valid authorization claim. AAuth.R3 should register an extension (for example via `AddAAuthR3AuthorizationEndpoint`) that reads `r3_operations` with the existing `R3Request.ReadOperations`/schema validation and exposes `request.GetR3Operations()` from the companion package. Core must not reference `R3Operations`.

Add response helpers so samples do not improvise divergent wire formats: `AAuthAuthorizationResults.Authorized(scope, account)` for `200` plus `{ "status": "authorized", ... }`, and `AAuthAuthorizationResults.ResourceToken(resourceToken)` for `200` plus `{ "resource_token": "..." }`. The authorization endpoint resource-token response should be a JSON body, not a `401` challenge and not an `AAuth-Requirement` header.

Fix the coupled gates in the same implementation slice: `AgentTokenRequired` passes only `AAuthTokenType.AgentToken`; `AAuthChallengeMiddleware.BuildResourceTokenAsync` throws before signing unless the presented verified token is person or auth; authorization endpoint non-JSON/missing JSON content types return `400 invalid_request`; and trust-policy denial writes a 403 problem response such as `access_denied`/`untrusted_issuer` with no `Signature-Error`, `Accept-Signature-Scheme`, or `Accept-Signature-Alg`.

Adversarial closure: do not let "valid extension registered" become "empty body accepted"; each extension must validate the whole replacing claim and explicitly opt in. Do not trust `AAuthVerificationResult.TokenType` if no `AAuthVerifiedAssertion` exists; resource-token minting needs the signed, verified token object so it can copy `ps`, `sub`, `presented_jti`, mission, tenant, and the signing key thumbprint. Do not classify trust denial as JWT verification failure, or conforming peers will retry/rotate keys instead of treating the issuer as unauthorized.

## Public API delta

Yes.

- Add `AAuthAccessMode.PersonTokenRequired` and make `MapAAuthAuthorizationEndpoint` set it; update XML docs for `IdentityOnly`, `RequireAAuthSignature`, and authorization endpoint mapping.
- Change `AAuthAuthorizationRequest`: `Scope` becomes `string?`; add `PersonToken` and an extension/feature bag; update constructor shape and docs. This is a deliberate C1 cutover.
- Add authorization-extension abstractions in core (`IAAuthAuthorizationRequestExtension` plus context/result types, names final during implementation) and R3 companion registration/accessor methods.
- Add authorization response helpers (`AAuthAuthorizationResults` or `HttpContext` extension methods) for `authorized`, `resource_token`, and person-token requirement responses.
- No compat overloads or obsolete shims.

## Wire effect

- `POST authorization_endpoint` with no person token (unsigned, agent-token-signed, auth-token-signed, or other successfully verified non-person credential) returns `401` with `AAuth-Requirement: requirement=person-token` and no `Signature-Error`.
- A malformed, expired, untrusted-key, or invalid-signature person token still returns `401 Signature-Error` under #verification.
- Non-JSON or missing JSON content type at the authorization endpoint returns `400 application/problem+json` with `error=invalid_request`, not 415.
- A scope-less R3 body is accepted only when the R3 extension is registered and `r3_operations` is valid; otherwise `scope` remains required and the endpoint returns `400 invalid_request`.
- Authorization endpoint resource-token success is `200` JSON `{ "resource_token": "..." }`; reactive/per-call challenges continue to use `401 AAuth-Requirement: requirement=auth-token; resource-token="..."`.
- `AgentTokenRequired` with a person/auth token now returns `401 AAuth-Requirement: requirement=agent-token`.
- Trust-policy denial changes from `401 Signature-Error: error=invalid_jwt` to `403` problem details with no signature error/accept headers.

## Implementation sketch

1. Extend access-mode metadata: add `PersonTokenRequired` to `AAuthAccessMode`, `AAuthEndpointRequirement`, endpoint docs, and `UseAAuth` handling in `AAuthEndpointExtensions.cs`; add a dedicated authorization-endpoint marker that `RequireAAuthSignature()` cannot replace. The route middleware should pre-answer the truly missing-token case for this mode/marker, then run `AAuthVerificationMiddleware`, then let the endpoint/helper enforce verified person token before invoking the handler.
2. Update `MapAAuthAuthorizationEndpoint` in `AAuthApplicationBuilderExtensions.cs`: parse JSON into `JsonObject`; return 400 for content-type/JSON/account/scope-extension validation errors; read `GetAAuthVerifiedAssertion()` and require `PersonTokenBuilder.TokenType`; build the new `AAuthAuthorizationRequest`; invoke registered authorization request extensions from DI; require `scope` or a satisfying extension; call the handler.
3. Add core extension abstractions and feature storage. Keep protocol strings in `AAuthConstants`/existing constants; avoid stringly typed extension lookups in app code.
4. In `src/AAuth.R3`, add DI registration and request accessor for `r3_operations`. Reuse `R3Request.ReadOperations` so SDK client and server agree. Migrate Bookings' manual `/authorize` parser to the shared endpoint if practical; otherwise keep the sample's policy mapping but use the shared parser/person-token requirement.
5. Add authorization response helpers and update Inbox/Bookings/docs/tests to use them. Remove `AAuth-Requirement` from successful authorization-endpoint resource-token responses.
6. Fix `AAuthChallengeMiddleware`: `AgentTokenRequired` accepts only `AAuthTokenType.AgentToken`; `BuildResourceTokenAsync` validates `presented.Token.TokenType` is person/auth before calling `PersonServerOf`.
7. Fix trust denial in `AAuthVerificationMiddleware`: replace "not trusted by policy" `TokenVerificationException` throws with a distinct branch/result that writes 403 problem details and clears/avoids all `Signature-Error`/`Accept-Signature-*` headers.
8. Update XML comments, snippets, generated API surface, and docs inventory after the code shape is frozen.

- Depends on R01's resource audience binding for person/auth-token verification to be meaningful on the authorization endpoint.
- Overlaps R04 for R3 resource-token contents, operation validation, and entitlement; R03 owns parsing and gating of `r3_operations`, while R04 owns whether the resulting document/token is valid and single-use.
- Overlaps R14 for signature/JWT hygiene; R03 should make only the narrow trust-policy denial mapping change needed by A03-HIGH-002.
- Feeds R18/R19 sample/docs sweeps because Inbox and workflow snippets must stop demonstrating authorization on agent signatures.

## Open questions (with proposed default)

1. **Should low-level `UseAAuthVerification()` gain a public "missing token requirement" option?** Default: no. Implement the spec-correct missing-person-token response in `UseAAuth`/`PersonTokenRequired` route handling and steer authorization endpoints to route metadata. Add a public option only if implementation cannot preserve malformed-token `Signature-Error` behavior without it.
2. **Should Inbox keep `/authorize` with a person token?** Default: no. Remove it from the two-party resource-managed sample; keep proactive authorization examples in person-token/R3-focused samples.
3. **What exact 403 problem `error` should trust denial use?** Default: `access_denied` with optional `detail`, because the Signature-Key draft names the condition "Access Denied" and forbids signature-error headers, while AAuth does not define a narrower endpoint code for verifier trust policy.
