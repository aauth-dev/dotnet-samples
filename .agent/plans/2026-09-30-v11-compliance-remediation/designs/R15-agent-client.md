## Problem restated (verified)

SDK-15/A06-01 is verified, with one partial guard. The protocol binds agent identity to the signing key (#agent-provider L469), two-key refresh returns an agent token bound to a fresh ephemeral key (bootstrap L294-L310), and key rotation requires fresh authorization (#re-authorization L1293). `AgentProviderTokenRefresher.RefreshAsync` still supports `RefreshMode.TwoKey`, calls `AgentProviderClient.RefreshTwoKeyAsync`, stores `LatestEphemeralKey`, and returns only the new token (`AgentProviderTokenRefresher.cs:53`, `:84-88`). `AAuthClientBuilder` signs resource and exchange requests with its readonly durable `_key` (`AAuthClientBuilder.cs:31`, `:723`, `:726`, `:776-777`, `:857`, `:865`), so a TwoKey refresh through `WithTokenRefresh` installs the JWT but not the ephemeral signer. `EnrolledBuilder` rejects TwoKey in its convenience path (`EnrolledBuilder.cs:165-167`), but the primitive `WithTokenRefresh(new AgentProviderTokenRefresher(..., RefreshMode.TwoKey))` path remains broken.

A08-02/A13-01 is verified. Resource tokens may carry `login_hint`, and the agent MUST pass it unchanged as the PS token-request `login_hint` (#resource-token L754; #ps-token-endpoint L945). `TokenExchangeRequest` has `LoginHint` (`TokenExchangeRequest.cs:82`) and `TokenExchangeClient` serializes it (`TokenExchangeClient.cs:263`), but `ChallengeHandler.ExchangeOptions` copies account, mission, callbacks, upstream, capabilities, and prompt without copying `verified.Payload["login_hint"]` (`ChallengeHandler.cs:319-333`). A conforming PS that reads only the request parameter loses the resource hint.

A10-01 is verified. The agent SHOULD verify returned auth-token signatures and then verify issuer, audience, key and subject context (#auth-token-response-verification L1818-L1825). `TokenExchangeClient.ExchangeAsync` reads `auth_token` and calls `AgentAuthTokenValidator.Validate` (`TokenExchangeClient.cs:150-153`). That validator decodes only payload segments (`AgentAuthTokenValidator.cs:14-51`), never verifies the JWT signature, never checks the header `typ`, and never checks auth-token `dwk`. A hostile or buggy PS can return a compact JWT whose payload matches but whose header is `aa-person+jwt`, or whose signature is invalid; the SDK accepts it locally and fails later at the resource.

A06-02 is verified. The five-minute margin applies to agent, person, and auth tokens (#refresh-margin L1301-L1306). `TokenRefreshHandler` implements a default five-minute refresh threshold for the agent token (`TokenRefreshHandler.cs:56-70`), but cached carriers are considered fresh until `ExpiresAt > now` (`AAuthTokenCache.cs:111-112`), and a mission person token is reused until only one minute remains (`ChallengeHandler.cs:338-358`). This permits presenting a person/auth token with seconds left, which can expire while being named in a resource token and redeemed downstream.

A05-02/A06-03 is verified. Agent tokens SHOULD NOT exceed 24 hours (#agent-provider L479; #agent-tokens L517). `AgentTokenBuilder.Lifetime` is public and unbounded (`AgentTokenBuilder.cs:66-67`) and `BuildAsync` calculates `exp = iat + Lifetime` directly (`AgentTokenBuilder.cs:160-179`). `SelfIssuedTokenRefresher.RefresherBuilder.WithLifetime` stores any lifetime (`SelfIssuedTokenRefresher.cs:60-69`, `:117-118`). A self-hosted caller can emit a week/year token, and a refresher can install one.

A13-04/A07-004 is verified. When an agent has a PS, it SHOULD relay resource interactions to the PS `interaction_endpoint` first and fall back to direct user handling only on `interaction_unavailable` (#interaction-relay L2404-L2412). `InteractionHandler` admits the resource URL and calls the local callback directly (`InteractionHandler.cs:133-135`). `DeferredExchange` does the same for interaction requirements encountered during token exchange (`DeferredExchange.cs:203-209`). `Governance.InteractionClient.RelayInteractionAsync` already knows the wire body and 424 fallback shape (`InteractionClient.cs:56-63`, `:108-129`) but is not wired into these automatic paths. This finding depends on R12 for final governance endpoint/error semantics.

A07-003 is verified. `AAuth-Access` response recipients MUST reject empty/whitespace/control-character values and responses carrying more than one credential (#aauth-access L613-L614). `AAuthAccessHandler` sees response headers, but only stores when there is exactly one valid value (`AAuthAccessHandler.cs:83`) and always returns the response (`AAuthAccessHandler.cs:89`). Existing tests assert invalid/multiple values are merely not stored (`AAuthAccessHandlerTests.cs:161`, `:180`), so the caller can process a 200 body that a conforming recipient would reject.

A07-005 is partially fixed but still functionally verified. Mission approval may return `capabilities`, and the agent unions those with its own for `AAuth-Capabilities` (#mission-approval L1399-L1404; #aauth-capabilities L2472-L2473). The model stores `Mission.Capabilities` (`Mission.cs:55-58`, `:183`) and `AAuthCapabilitiesHeader.Union` exists (`AAuthCapabilitiesHeader.cs:55-77`), but `MissionContextHandler` forwards only `MissionS256` and `MissionPersonTokens` (`MissionContextHandler.cs:26-30`). The signer only unions configured capabilities with one request-local option (`AAuthSigningHandler.cs:296-304`), so mission approval capabilities never reach the wire.

A07-007 is verified, and A07-006 is a coupled cleanup. `AAuth-Capabilities` is an RFC 9651 Structured Field List of Tokens; current values have no parameters, and recipients ignore unknown parameters (#aauth-capabilities L2458-L2477). `AAuthCapabilitiesHeader.Format` blindly joins strings and `Parse` splits on commas (`AAuthCapabilitiesHeader.cs:31-45`); `WithCapabilities` accepts arbitrary strings (`AAuthClientBuilder.cs:253`); the signer emits with `TryAddWithoutValidation` (`AAuthSigningHandler.cs:301-304`). The challenge builder also injects `auth-token` as a capability (`AAuthClientBuilder.cs:729`, `:948-960`), which is a requirement value rather than one of the registered capabilities. A strict SF serializer would reject the SDK's own default unless that auto-capability is removed.

## Recommendation

Use approaches 1, 3, 4, 5, 6, 7, 8 and 9.

For SDK-15, deliberately remove automatic TwoKey from `AgentProviderTokenRefresher` rather than retrofitting signer swapping in R15. Log the decision in the API-surface implementation log as a re-ruling: two-key automatic refresh needs a future atomic credential-pair signer/provider, not an `ITokenRefresher` that returns only a string. Keep `AgentProviderClient.RefreshTwoKeyAsync` and docs showing manual rebuild with `result.EphemeralKey` and `result.AgentToken` for the informational bootstrap ceremony.

For token exchange, preserve the current flow but make the data exact and verified: copy `login_hint`, verify returned auth-token signatures by default, and retain the existing payload-context validator after signature verification. A malicious PS can still return a signed auth token for the wrong resource or subject; the context checks close that. A malicious resource can put a non-string `login_hint`; treat that as a malformed verified resource token and fail locally rather than converting it.

For token freshness, make the five-minute margin part of “usable carrier” semantics, not just agent-token refresh. A custom cache that returns a stale carrier should still be blocked by `AAuthTokenHolder` before presentation. After agent-token refresh, the existing cache key includes the agent token string (`AAuthTokenCacheKey.AgentToken`), so person/auth carriers obtained under the old token are naturally not reused.

For interactions, relay only when a PS is known and the interaction has not already been relayed for that request. Any PS response other than structured 424 `interaction_unavailable` is terminal; falling back on arbitrary PS failure would let an attacker suppress the PS channel.

For capabilities, validate outbound capability values as SF tokens and remove the `auth-token` default before turning validation on. Keep registered constants for `interaction`, `clarification`, and `payment`, while allowing syntactically valid extension tokens because the registry is open and recipients MUST ignore unknown values.

## Public API delta

- **Removed:** `RefreshMode`, `AgentProviderTokenRefresher.LatestEphemeralKey`, the `AgentProviderTokenRefresher(..., RefreshMode mode = ...)` constructor parameter, `AgentProviderTokenRefresher.RefresherBuilder.WithRefreshMode`, and `EnrolledBuilder.WithRefreshMode`. `AgentProviderTokenRefresher` becomes single-key only. `AgentProviderClient.RefreshTwoKeyAsync` and `TwoKeyRefreshResult` remain.
- **Added:** `AgentTokenBuilder.MaximumLifetime` (public `TimeSpan` constant/static readonly) and validation that `Lifetime` is `> 0` and `<= MaximumLifetime`. `SelfIssuedTokenRefresher.RefresherBuilder.WithLifetime` follows the same validation.
- **Added:** `TokenExchangeClientOptions` with `bool VerifyAuthTokenSignature { get; init; } = true` and optional `JwksClient? JwksClient { get; init; }` (or equivalent data-only option). `TokenExchangeClient` takes the options in its single constructor shape; direct callers opt out explicitly with `VerifyAuthTokenSignature = false`. `ChallengeHandlingOptions` mirrors the bool so automatic challenge handling can opt out without hand-building a client.
- **Changed:** `IAAuthTokenCache` XML contract: `Get`/`AcquireAsync` must not return tokens inside the configured refresh margin. The in-memory implementation enforces it; `AAuthTokenHolder` re-checks before presentation.
- **Changed:** `AAuthCapabilitiesHeader.Format` throws `FormatException` for non-SF-token values or values with parameters; `Parse` becomes a strict SF List parser that returns bare tokens and ignores item parameters. `WithCapabilities`/DI options validate at composition.
- **Changed behavior:** `AAuthAccessHandler` throws `HttpRequestException` (or a dedicated protocol exception if one already exists in R11/R14) for malformed/multiple `AAuth-Access` response credentials.
- ApiSurface impact: intentional breaking removals for TwoKey automatic refresh; additive options for token exchange; stricter exceptions for invalid capabilities/access headers.

## Wire effect

- Automatic AP refresh sends only single-key `Signature-Key: sig=hwk` refresh requests. Two-key `sig=jkt-jwt` refresh remains only via explicit `AgentProviderClient.RefreshTwoKeyAsync` followed by rebuilding the client with the returned ephemeral key/token.
- PS token requests now include `"login_hint": "<exact resource-token value>"` whenever the verified resource token carried a string `login_hint`.
- Auth-token exchange may perform additional metadata/JWKS GETs before returning. Bad returned `auth_token` values fail locally instead of being presented to resources.
- Carrier tokens inside the five-minute refresh margin are not presented; agents obtain fresh person/auth tokens earlier. Mission-provided person tokens inside the margin are ignored.
- Agent-token builders/refresh install paths reject tokens whose `exp - iat` exceeds 24 hours.
- Resource interaction flow with a PS adds a signed POST to the PS `interaction_endpoint` with `{ "type": "interaction", "url": "...", "code": "..." }`. Direct browser/display fallback happens only after structured 424 `interaction_unavailable`; no-PS agents behave as before.
- Responses with malformed or multiple `AAuth-Access` headers are rejected client-side instead of returned to application code.
- `AAuth-Capabilities` is emitted as a strict SF token list. Mission approval capabilities are unioned into resource requests. The spurious `auth-token` capability disappears from challenge-handling requests.

## Implementation sketch

1. **Remove automatic TwoKey.**
   - In `AgentProviderTokenRefresher.cs`, delete `RefreshMode`, `_mode`, `LatestEphemeralKey`, the mode constructor parameter, and `RefresherBuilder.WithRefreshMode`; `RefreshAsync` always calls `_client.RefreshAsync`.
   - In `EnrolledBuilder.cs`, delete `_refreshMode`, `WithRefreshMode`, and the build-time TwoKey rejection. The builder remains a single-key convenience path.
   - Keep `AgentProviderClient.RefreshTwoKeyAsync` and `TwoKeyRefreshResult`; update XML docs to say this is manual and requires rebuilding with the ephemeral signer.
   - Add an implementation-log entry documenting why `AAuthSigningKeySet` was not used here: it rotates issuer keys but does not provide an atomic agent credential-pair for `ITokenRefresher`.

2. **Pass `login_hint`.**
   - In `ChallengeHandler`, after `VerifyResourceTokenAsync`, read `verified.Payload["login_hint"]`.
   - If absent, leave `LoginHint` null. If present and not a JSON string, throw `TokenVerificationException`.
   - Add the string to `ExchangeOptions(...)` (extend helper signature with `loginHint`) so `TokenExchangeClient` serializes it unchanged.

3. **Verify returned auth tokens.**
   - Add `TokenExchangeClientOptions`; store options and either use an injected `JwksClient` or create one from `metadata.Policy` with correct disposal semantics.
   - In `ExchangeAsync`, after reading `auth_token` and capturing `signingKey`, decode the header and require `typ == AuthTokenBuilder.TokenType` and `dwk` in the allowed auth-token DWKs even when signature verification is disabled.
   - When `VerifyAuthTokenSignature` is true, call `TokenVerifier.VerifyAuthTokenWithJwksAsync(authToken, _metadata, _jwks, expectedAudience: resourcePayload["iss"], httpSignatureKey: signingKey, ...)`. Then call `AgentAuthTokenValidator.Validate` for resource-token/presented-token/upstream lifetime and subject context.
   - Thread `ChallengeHandlingOptions.VerifyAuthTokenSignature` through `AAuthClientBuilder` and DI `AAuthAgentOptions.Challenge`.

4. **Apply carrier refresh margin.**
   - Define one internal/default margin constant shared by `TokenRefreshHandler`, `InMemoryAAuthTokenCache`, and `ChallengeHandler.ReusableMissionPersonToken` (default five minutes, still allowing `_refreshThreshold` override where builder already exposes it).
   - Change `InMemoryAAuthTokenCache.Fresh` from `ExpiresAt > now` to `ExpiresAt > now + margin`; prune entries at or inside the margin.
   - In `AAuthTokenHolder.SelectForRequest` and after `IAAuthTokenCache.AcquireAsync`, parse `exp` and refuse to return/publish carriers inside the margin even if a custom cache returned them.
   - Change mission person-token reuse from one minute to the same five-minute margin.

5. **Cap agent-token lifetime.**
   - Add `AgentTokenBuilder.MaximumLifetime = TimeSpan.FromHours(24)` and validate `Lifetime` before computing `exp`; reject non-positive values too.
   - Validate `WithLifetime` in `SelfIssuedTokenRefresher.RefresherBuilder`.
   - In `TokenRefreshHandler`, before `_holder.Update(newToken)`, parse `iat`/`exp` for agent tokens and reject `exp - iat > MaximumLifetime` so AP refresh cannot install an oversized token.

6. **Relay interactions PS-first.**
   - Add an internal `IInteractionRelay`/delegate that returns `Relayed`, `Unavailable`, or throws. The default adapter wraps `InteractionClient.RelayInteractionAsync`.
   - In challenge-handling build, construct the relay from the already-created agent-signed PS channel (`exchangeHttpClient`, `metadata`, resolved `personServer`). In interaction-only/resource-managed build, construct it only when `_personServer` is configured or resolvable from the current agent token; otherwise leave null.
   - In `InteractionHandler`, before local callback, call relay with the parsed interaction and current mission if present. If relayed, continue polling the resource `Location`; if unavailable, call local callback; if other error, throw.
   - In `DeferredExchange`, add relay to `DeferredExchangeOptions` and use it before `OnInteractionRequired`. Guard against relaying the same interaction twice by tracking URL+code per exchange.

7. **Reject malformed `AAuth-Access`.**
   - In `AAuthAccessHandler`, if the response contains `AAuth-Access`, enumerate all values. If count is not exactly one or `TryParseAccess` fails, dispose the response and throw. Store only after successful parse.
   - Preserve replay-time validation before setting `Authorization`.

8. **Strict capabilities and mission union.**
   - Implement an SF token-list parser/formatter in `AAuthCapabilitiesHeader`: token starts with ALPHA or `*`, then RFC tchar plus `:`/`/`; list items may have parameters on parse, but `Format` emits bare tokens only and rejects parameters/control/whitespace.
   - Validate `AAuthClientBuilder.WithCapabilities`, `ChallengeHandlingOptions.Capabilities`, `AAuthAgentOptions.Capabilities`, and token-exchange `capabilities` request parameters using the same token validator.
   - Remove `MergeCapabilities("auth-token")`; infer only registered capabilities from callbacks (`interaction`, `clarification`, `payment` when a payment handler exists).
   - Add `AAuthRequestOptions.MissionCapabilities` or an internal request option. `MissionContextHandler` sets it from `_mission.Capabilities`; `InteractionHandler` appends request-local `interaction`; `AAuthSigningHandler` computes `AAuthCapabilitiesHeader.Union(mission, configured + request-local)` and emits the strict formatted list.

## Dependencies and conflicts with other Rnn

- **R12 Governance endpoints:** interaction relay depends on final `interaction_endpoint`, 424 `interaction_unavailable`, and deferred polling semantics. If R12 changes `InteractionClient`, R15 should consume that result rather than invent another client.
- **R14 JWT and verification hygiene:** default-on auth-token signature verification should reuse any R14 changes to `TokenVerifier`, `JwksClient`, TLS/egress policy, and header `typ`/`dwk` checks.
- **R13 HTTP-signature producer:** if R13 changes signing handler construction or key context, re-check the TwoKey-removal decision and the carrier cache thumbprint key. Do not implement automatic TwoKey until there is an atomic credential-pair signer/provider.
