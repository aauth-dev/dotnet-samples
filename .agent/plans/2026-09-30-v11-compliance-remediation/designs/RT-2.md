## Details

**R04 SDK-03 / DOC-06.** The design correctly rejects the current plain `Granted` replay path (`R3Enforcement.cs:95-141`) and moves mechanics into an execute-once handle (`R04-r3.md:29`, `R04-r3.md:40`, `R04-r3.md:60-62`), satisfying R3 single-use (`draft-hardt-aauth-r3.md:675-678`). The gap is key identity: both the recommended text and the current helper talk about `jti` alone (`HeldInvocations.cs:70`), while a JWT `jti` is only safe with issuer context. The existing `202` held path keys retained results as `id + ":" + jti` (`HeldInvocations.cs:325`), so R04 must either move held R3 completion onto the same `(auth_iss, auth_jti)` retained result or prove that the R3 `SingleUse` handle always wraps held-operation execution; otherwise the 202 path can still execute once per pending id rather than once per per-call auth token.

**R05 SDK-04 / A18-001.** The recommendation is directionally sound: step 4 requires the PS to identify the original caller from its own records and fail closed when it cannot (`draft-hardt-oauth-aauth-protocol.md:1826-1837`), while today's validator only performs steps 1-3 and static AS trust (`UpstreamTokenValidator.cs:70-132`) and today's inventory can register unseen tokens without provenance (`IJtiStore.cs:22`, `InMemoryJtiStore.cs:46`). R05 does say missing provenance fails closed (`R05-upstream-chaining.md:40`, `R05-upstream-chaining.md:92`) and that `RegisterAsync` must not create the needed record (`R05-upstream-chaining.md:49`), but the new record is much larger (`R05-upstream-chaining.md:22`) than the spec's minimal Records paragraph (`draft-hardt-oauth-aauth-protocol.md:2756-2758`). Add mandatory TTL pruning, maximum records per agent/resource, and backpressure/rate-limit behavior consistent with the person-token retention warning (`draft-hardt-oauth-aauth-protocol.md:844-847`).

**R06 SDK-05 / A20-001.** R06 finds the right invariant, "check recorded source dependencies, then act" (`R06-revocation.md:22`), and current code demonstrably violates it by calling `FederateAsync` before the tracked mint catches a revoked source (`AAuthPersonServerEndpoints.cs:1447-1456`). The design admits a residual race where revocation can arrive after the last preflight but while the HTTP request is in flight (`R06-revocation.md:31`). That is too loose for "PS MUST NOT present a revoked person token to an AS" (`draft-hardt-oauth-aauth-protocol.md:2752`) unless the implementation couples the guard to the outbound send: recheck after request shaping, use a revocation-linked cancellation token in `AccessServerClient.FederateAsync`, and atomically flip the pending entry to terminal `revoked` before any later callback can continue.

**R07 A17-001 / D06-02.** Explicit collapse declaration is the right answer because current routing treats `aud == issuer` as three-party (`AAuthPersonServerEndpoints.cs:588-604`) even though PS-AS collapse must be AS-shaped (`dwk: aauth-access.json`) and apply both PS consent and AS policy (`draft-hardt-oauth-aauth-protocol.md:1757-1765`). However, the declaration seam must be exact: resource issuer plus linked AS role plus expected AS issuer. R07 says undeclared `aud == PS` remains three-party (`R07-federation.md:46`) and linked local AS is required (`R07-federation.md:26`), but it should also forbid silent downgrade when a declaration exists and the linked AS is misconfigured; otherwise a configuration loss becomes an AS-policy bypass.

**R07 A17-003 / A19-HIGH-005.** The payment loop is spec-required: the AS response section says the PS handles `202` and `402` until `200` or terminal error, and `402 Location` is the polling URL after settlement (`draft-hardt-oauth-aauth-protocol.md:1610-1643`). R07 fixes today's terminal throw (`AccessServerClient.cs:141-153`) and wrong `PaymentUrl` shape (`IAccessPolicy.cs:139-172`), but the proposed `IAAuthPaymentSettler` should be scoped narrowly. Because the spec says the PS caches the billing relationship per AS (`draft-hardt-oauth-aauth-protocol.md:1640-1642`), add a cache/idempotency seam; because payment is out of scope, pass only payment challenge data, AS origin, and pending URL to the settler, not resource/person/agent tokens.

**R10 SDK-07 / A11-01.** The `PersonKey` and binding-store model directly fixes the current missing stable person identifier (`IdentityAssertion.Subject` is only directed `sub`, `IIdentityClaimsAsserter.cs:164-191`; current binding key omits person identity, `AgentPersonBinding.cs:21`) and matches the one-person invariant (`draft-hardt-oauth-aauth-protocol.md:2912-2920`). The remaining attack is partial persistence: R10 allows `NeedsConsent` without a person key until approval (`R10-person-binding.md:157`) and adds separate binding/enrollment stores (`R10-person-binding.md:30-40`). The plan must require atomic bind-or-verify, enrollment record, and token/provenance write before any person/auth token or claims response is observable; store write failure must be a denial, not a best-effort warning.

**R10 A11-03.** HMAC pairwise derivation with a non-signing secret is sound (`R10-person-binding.md:37-40`) and fixes the current fixed default subject (`IIdentityClaimsAsserter.cs:214-222`) against the directed-identifier requirement (`draft-hardt-oauth-aauth-protocol.md:2953-2962`). It is incomplete on secret lifecycle. R10 says signing-key rotation must not rotate person identifiers (`R10-person-binding.md:39`) and subjects remain stable while the secret/store persist (`R10-person-binding.md:75`), but production will need HMAC-secret rotation. Require a key ring with key ids, persisted derived subjects (or per-enrollment key version), old-key retention for resolution, and a minimum collision-safe output length.

**R10 A15-002.** Rejecting absent/foreign `ps` on governance endpoints is defensible: governance says an agent with a PS MUST carry `ps` (`draft-hardt-oauth-aauth-protocol.md:457-462`), and current governance accepts missionless agent tokens with no PS check (`GovernanceEndpoints.cs:31-38`). The spec also warns the agent-token `ps` is informational for resource authorization and the authorization's PS is learned from the person token (`draft-hardt-oauth-aauth-protocol.md:519-526`). R10 already narrows the rationale to governance endpoints (`R10-person-binding.md:44-53`); make that limitation explicit in API docs and tests so implementers do not start using agent-token `ps` as the authority for ordinary token issuance or resource trust.

## Cross-design conflicts and ordering

1. **Inventory/provenance/source dependencies must be one coordinated cutover.** R05 extends `IJtiStore` for provenance, R06 changes pending `SourceTokens` to typed dependencies, and R10 adds binding/enrollment records. Implement R06's `AAuthSourceDependency` shape and R05's provenance record together, then have R10 reference them rather than creating a parallel revocation/provenance path.
2. **R06 must wrap R07's final federation send.** R07 rewrites `AccessServerClient.FederateAsync` for 402 loops; R06's revocation guard must sit around the final outbound send and every composed 202/402 callback after R07 request shaping, not around the old client call that R07 removes.
3. **R04/R11 held-invocation semantics need a single key rule.** R04 per-call replay is globally single-use per auth token; current held invocations are per pending id. Decide the canonical retained-result key before changing R04 so deferred R3 and non-R3 held calls do not diverge.
4. **R05 and R10 both resolve upstream identity.** R05 wants upstream provenance to identify the original caller; R10 wants `(resource, directedSubject) -> PersonKey` enrollment. The upstream-token validator should consume the enrollment record/provenance atomically instead of doing two independent lookups with different failure codes.
5. **R07 collapse and R10 governance both touch role identity.** Use C5/C12 named role identity once; do not let collapse declarations or governance expected-PS parameters introduce a second source of issuer truth.

## Open questions the orchestrator must rule on (with proposed default)

1. **Single-use retained-result key:** default to `r3:{auth_iss}:{auth_jti}` (or token hash if issuer is unavailable) and require held R3 completion to use the same key.
2. **Provenance storage limits:** default to token `exp + skew` pruning, per-agent distinct-resource quotas, and fail-closed `429`/`invalid_request` when quotas are exceeded before minting.
3. **Revocation/FederateAsync race:** default to a source-guarded federation primitive, not ad hoc preflight calls.
4. **Payment state:** default to a PS-owned billing cache keyed by AS issuer and payment scheme/account; the settler gets no JWTs.
5. **Pairwise subject rotation:** default to a configured HMAC key ring with one active key, old keys retained until all enrollment records using them expire or are migrated.
