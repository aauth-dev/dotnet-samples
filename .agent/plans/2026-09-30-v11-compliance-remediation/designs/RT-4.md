## Details

**R13 SDK-16 / A02-HIGH-001 — SOUND-WITH-CHANGES.** The design correctly stops future-dating: AAuth requires `created` be the current time (#signature-parameters, spec L2234) and verifiers reject timestamps beyond the window as `clock_skew` (#verification, spec L2246). But the proposed replacement intentionally waits until the last issued second is current (`R13-signing-producer.md:60`, `:114`), serializing concurrent identical targets at 1/s. That is driven by an optional verifier replay cache: the spec says a verifier MAY reject duplicate `(thumbprint, created, @method, @authority, @path)` tuples and defines no nonce (#freshness-and-replay, spec L2270-L2272). The current SDK replay identity is actually a SHA-256 of the whole signature base (`src/AAuth/HttpSig/AAuthVerifier.cs:112`) recorded by middleware (`src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:204-L207`), not exactly the profile tuple, while current producer future-dates in `NextCreated` (`src/AAuth/HttpSig/AAuthSigningHandler.cs:67-L81`). Because ASL Phase 9/10 explicitly introduced unique `created` for cached-token concurrency, the orchestrator must rule whether SDK verifier relaxation is preferable to making the producer an availability bottleneck for every SDK client.

**R13 A04-04 — SOUND-WITH-CHANGES.** Adding typed `AdditionalSignatureComponents` is the right fix for first-request signing (`R13-signing-producer.md:33-L37`, `:65-L69`) and matches the resource metadata requirement (spec L2133) plus the agent-learning rule (#covered-components, spec L2216). The weakness is cross-design: R16 is simultaneously introducing a reserved-field validation table and forbidding `AdditionalMetadata` bypasses (`R16-metadata-identifiers.md:43-L46`, `:75-L76`). If R13 lands its field independently, resource metadata producers can disagree over whether typed fields or extension metadata win; make R13's typed field the only core-field path and have R16 validate that exact member.

**R15 SDK-15 / A06-01 — SOUND-WITH-CHANGES.** Removing automatic TwoKey closes the verified broken path where `AgentProviderTokenRefresher` returns a token but the builder continues signing with the durable `_key` (`R15-agent-client.md:29`, `src/AAuth/HttpSig/EnrolledBuilder.cs:165`, `src/AAuth/Crypto/AAuthSigningKeySet.cs:18-L63`). That is safer than installing only an `AAuthSigningKeySet`, because bootstrap two-key refresh binds the returned token to the fresh ephemeral HTTP-signing key (bootstrap spec L294-L310). The required change is documentation/API-surface clarity: callers must not infer that `AgentProviderTokenRefresher` still supports automatic two-key; examples must use `RefreshTwoKeyAsync` followed by rebuilding with both returned `AgentToken` and `EphemeralKey` (`R15-agent-client.md:41-L43`, `:63-L65`).

**R15 A10-01 — SOUND-WITH-CHANGES.** Default-on auth-token signature verification implements the SHOULD and then keeps the mandatory issuer/audience/key/subject context checks (#auth-token-response-verification, spec L1818-L1825; `R15-agent-client.md:32`, `:86-L91`). The attack surface is operational: every exchange can now fail early on PS/AS metadata/JWKS discovery, TLS/egress policy, cache misses, or unavailable dev fixtures, before the resource would have rejected the token. The design mentions injected/created `JwksClient` but not fetch caching or failure taxonomy (`R15-agent-client.md:84-L91`), while current code only payload-decodes (`src/AAuth/Agent/TokenExchangeClient.cs:153`, `src/AAuth/Agent/AgentAuthTokenValidator.cs:14-L51`). Reuse the shared cached JWKS client and document the opt-out as policy, not a hidden compatibility mode.

**R15 A05-02 / A06-03 — SOUND-WITH-CHANGES.** Capping SDK-produced agent tokens is sound: agent tokens SHOULD NOT exceed 24 hours (#agent-provider, spec L479; #agent-tokens, spec L517), and current `AgentTokenBuilder.Lifetime` is unbounded. The design also rejects refreshed/installed AP tokens over the cap (`R15-agent-client.md:34`, `:100-L102`). Because the normative word is SHOULD NOT rather than MUST NOT, rejecting a third-party AP's longer token is a deliberate alpha strictness choice that should be logged; otherwise this remediation can create an interop failure not required by the cited finding.

**R15 A13-04 / A07-004 — SOUND-WITH-CHANGES.** PS-first relay follows the spec: an agent with a PS SHOULD POST interaction details to the PS first and fall back only on `interaction_unavailable` (#interaction-relay, spec L2404-L2412). The design correctly treats arbitrary PS failure as terminal (`R15-agent-client.md:49-L50`) but depends on R12 for exact `interaction_endpoint`, 424 body, and deferred polling semantics (`R15-agent-client.md:35`, `:143-L145`). It also proposes relaying `DeferredExchange` interactions (`R15-agent-client.md:106-L111`, `:156-L158`); if those interactions were already produced by the same PS during token exchange, relaying them back can loop or double-notify. Default to resource-response relay only until R12 rules the loop case.

**R16 A04-02 — SOUND-WITH-CHANGES.** The central URL helper is the right defense against producer/consumer drift (`R16-metadata-identifiers.md:25-L47`) and matches the endpoint/common-URI rules (#endpoint-and-other-urls, spec L1971-L1976; metadata common fields, spec L1994-L1998). The missing piece is not validation logic but rollout mechanics: high-level samples currently use `http://localhost` issuers throughout (`samples/MockPersonServer/Program.cs:65`, `samples/MockAccessServers/Federated/Program.cs:41`, `samples/MockResourceServers/Calendar/Program.cs:34`), and e2e waits on loopback well-known URLs (`tests/e2e/playwright.config.ts:82-L123`). Strict validation will fail at host start unless a concrete local TLS/alias plan lands in the same cut.

**R16 A04-05 — UNSOUND.** Strict production server identifiers are required: issuer values MUST be `https`, host-only, lowercase, no port/path/query/fragment/trailing slash, and exact compared (spec L1948-L1970); loopback is only called out for callback parameters when `localhost_callback_allowed` is true (spec L1971-L1976). However, the design's "no localhost" ruling (`R16-metadata-identifiers.md:65`, `:121`) breaks this repo's dev topology without an alternative: `MetadataClient` derives `expectedIssuer` from the fetch URL and requires the JSON `issuer` to byte-match it before calling `ValidateIdentifier` (`src/AAuth/Discovery/MetadataClient.cs:81-L87`, `:131-L146`). If the servers keep listening at `http://localhost:port`, strict sample issuers such as `https://agent.example` cannot pass issuer-match; if issuers remain localhost, strict validation rejects them. The design's sample list omits `tests/e2e/playwright.config.ts` despite many loopback issuer/well-known dependencies, so the fix is incomplete and will strand e2e.

**R16 A04-06 — SOUND-WITH-CHANGES.** Typed AP `event_endpoint` and `localhost_callback_allowed` fields fix the discovery gap (`R16-metadata-identifiers.md:48-L51`, `:79-L80`) and align with AP metadata/Event discovery (protocol spec L2025-L2029; Events spec L196-L209). The conflict is with R17's Events endpoint implementation: R16 wants `MapAAuthEventEndpoint` to attach route metadata and AP metadata to derive exactly one endpoint (`R16-metadata-identifiers.md:120-L125`), while R17 is changing Events endpoint behavior and store outcomes (`R17-events.md:43-L50`). Land the route-metadata bridge in one place and add a multiple-endpoint failure test.

## Cross-design conflicts and ordering

- **R16 before or with R13 metadata:** R13 adds `additional_signature_components`; R16's reserved-field map must know it so `AdditionalMetadata` cannot shadow typed core fields.
- **R12 before R15 relay:** R15's PS-first relay should not ship until R12 fixes the 424 `interaction_unavailable` shape and deferred interaction endpoint semantics.
- **R16 before e2e gate:** strict identifiers require either local TLS/host aliases or a Development-only transport alias; otherwise current loopback samples/e2e cannot start.
- **R16/R17 AP Events bridge:** only one design should own `MapAAuthEventEndpoint` route metadata used to derive AP `event_endpoint`.
- **R13/R14 verifier cleanup:** deciding whether to relax SDK replay rejection versus producer waiting affects R14 verifier hygiene and Phase 9 token-cache behavior.

## Open questions the orchestrator must rule on (with proposed default)

1. **R13 same-tuple concurrency:** Is 1/s per tuple acceptable? Proposed default: relax the SDK verifier's optional duplicate-tuple rejection for SDK-to-SDK traffic and keep producer `created=current`; offer/document strict-interoperability waiting only after an explicit ruling.
2. **R16 local development:** Is a Development-only identifier exception allowed? Proposed default: no production `ServerId` exception; add a Development-only authority-to-loopback transport alias or local TLS/host setup, and keep conformance tests strict.
3. **R15 auth-token verification:** How should JWKS failures surface? Proposed default: default-on in builders/DI, cached through shared `JwksClient`, with explicit primitive opt-out and fail-closed structural checks always on.
4. **R15 token-exchange interactions:** Should `DeferredExchange` relay interactions back to the PS? Proposed default: no until R12 proves no loop; relay only resource-response interactions.
5. **R17 empty bodies:** What is body-bearing with `Content-Length: 0`? Proposed default: accept R17's default—no body unless `Content-Type` or transfer coding indicates one; `Array.Empty<byte>()` means intentionally signed empty JSON.
