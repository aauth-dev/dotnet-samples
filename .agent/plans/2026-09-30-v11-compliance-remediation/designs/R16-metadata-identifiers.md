## Problem restated (verified)

- **A04-01: agent identifiers do not enforce the reserved `+` structure everywhere.** Verified `AgentId.TryParse` accepts any `+` in the local part because it only checks local length and character class (`AgentId.cs:98-L105`), `IsSubAgent` is just `Local.Contains('+')` (`AgentId.cs:31`), and `ParentAgent` truncates at the first plus (`AgentId.cs:43-L45`). `AgentTokenBuilder` now partially guards top-level emission by rejecting a `Subject` with `+` when `ParentAgent` is absent (`AgentTokenBuilder.cs:120-L134`), but it still accepts `aauth:parent+@ap.example` as a sub-agent because `IsSubAgent` is true and `ParentAgent` derives to `aauth:parent@ap.example` (`AgentTokenBuilder.cs:140-L153`). `TokenVerifier` validates only that `sub` and `parent_agent` are individually parseable agent identifiers (`TokenVerifier.cs:653-L668`, `:719`); it does not require a non-empty discriminator or parent-derived subject. This conflicts with #agent-identifiers L490-L492 and #sub-agents L1897-L1901.
- **A04-02: producer metadata validation is mostly non-empty checks.** Verified direct metadata options validate issuer with `AAuthUrl.IsHttpsOrLoopback` and required key presence, but PS/AS required endpoints are only checked for non-empty (`AAuthPersonServerMetadataOptions.cs:73-L81`; `AAuthAccessServerMetadataOptions.cs:51-L59`), AP validates no URL fields beyond issuer (`AAuthAgentMetadataOptions.cs:48-L55`), and resource metadata validates only issuer and access mode (`WellKnownEndpoints.cs:395-L418`). The JSON builders then emit common URI and endpoint fields verbatim (`WellKnownEndpoints.cs:157-L158`, `:226-L227`, `:235-L250`, `:267-L275`). High-level PS/AS options derive endpoints from paths, but their validators only reject query/fragment on interaction paths, not token/person/revocation/governance paths (`AAuthPersonServerServiceCollectionExtensions.cs:213-L223`; `AAuthAccessServerServiceCollectionExtensions.cs:159-L170`). `AddAAuthResource` currently checks only that `Issuer` is non-empty before registering options (`AAuthResourceServiceCollectionExtensions.cs:45-L48`). This can publish `http://...`, `?...`, or `#...` values despite #endpoint-and-other-urls L1971-L1974 and common metadata URI requirements at #metadata-documents L1994-L1998.
- **A04-03: consumer metadata validation omits accepted fields.** Verified `MetadataClient.FetchDocumentAsync` validates a hard-coded list containing `jwks_uri`, selected endpoints, and `event_endpoint` (`MetadataClient.cs:104-L112`), but omits `permission_endpoint`, `audit_endpoint`, `mission_control_endpoint`, and common URI fields. `ServerMetadata.FromJson` then exposes those strings (`ServerMetadata.cs:78-L92`), and `ResourceMetadata.FromJson` exposes common URI, `authorization_endpoint`, and `revocation_endpoint` strings (`ServerMetadata.cs:165-L174`). A malicious document fetched from the right issuer can therefore surface `permission_endpoint="http://attacker/perm?x=1"` or `documentation_uri="http://phish/docs"`.
- **A04-05: the development egress policy is being used as a server-identifier exception.** Verified `AAuthEgressPolicy.IsValidIdentifier` returns true for exact configured loopback origins before applying server-identifier rules (`AAuthEgressPolicy.cs:73-L80`), and all identifier wrappers/options call that helper (`ServerId.cs:27-L35`; `AAuthUrl.cs:18-L19`; option validators cited above). The conformance tests explicitly pin `http://localhost:5100` and `http://127.0.0.1:8080` as accepted when `TestEgress.Policy` is supplied (`ServerIdTests.cs:56-L72`). The spec's only loopback exception in this slice is for interaction callback parameters when AP metadata says `localhost_callback_allowed` (#endpoint-and-other-urls L1975-L1976), not for `issuer`.
- **A04-06: AP metadata cannot publish Events or loopback-callback capability through the typed helper.** Verified `AAuthAgentMetadataOptions` has `CallbackEndpoint` but no `EventEndpoint` or `LocalhostCallbackAllowed` (`AAuthAgentMetadataOptions.cs:44-L46`), and `BuildAgentMetadata` emits only `callback_endpoint` beyond common fields (`WellKnownEndpoints.cs:216-L227`). Events provides `MapAAuthEventEndpoint("/events")` (`EventsEndpoints.cs:37`), and resource-side Events discovery requires AP metadata `event_endpoint` (`EventsProtocol.cs:88`), but there is no typed connection between them. This conflicts with #agent-provider-metadata L2025-L2029 and Events #ap-metadata L196-L209.
- **A07-002: endpoint validation rejects query but not fragment.** Verified interaction producer and consumer call `AAuthEgressPolicy.ValidateUrl(url, endpoint: true)` (`Interaction.cs:82`, `:104`), while `ValidateUrl` checks `endpoint && value.Contains('?')` only (`AAuthEgressPolicy.cs:95-L104`). A `requirement=interaction` URL with `#attacker` is accepted even though #interaction-required L2374 says the URL MUST NOT contain query or fragment components; `BuildUserUrl` would append `?code=` after the fragment (`Interaction.cs:51-L57`).

## Recommendation

Adopt **2** as one cutover, with a narrow manual fallback for AP Events metadata.

Create an internal URL validation helper, for example `AAuthMetadataUrl.Validate(AAuthEgressPolicy policy, string field, string value, UrlKind kind, string? metadataIssuer = null, bool localhostCallbackAllowed = false)`. The helper should parse the original string once and enforce:

- `Endpoint`: absolute `https`, no query, no fragment; then destination admission via the egress policy. Applies to `auth_token_endpoint`, `person_token_endpoint`, `authorization_endpoint`, `mission_endpoint`, `permission_endpoint`, `audit_endpoint`, `interaction_endpoint`, `mission_control_endpoint`, `revocation_endpoint`, `callback_endpoint`, and `event_endpoint`.
- `Jwks`: absolute `https`; same-origin with metadata issuer unless the egress policy has explicit cross-origin JWKS admission, preserving `ValidateJwksUrl` semantics.
- `Informational`: absolute `https`; query and fragment are allowed because #endpoint-and-other-urls only bans them for endpoints. Applies to `documentation_uri`, `tos_uri`, `policy_uri`, `logo_uri`, and `logo_dark_uri`.
- `Callback`: absolute `https`, no fragment, and no query unless the specific callback protocol allows it; `http://localhost`, `http://127.0.0.1`, or `http://[::1]` with any port is accepted only when the AP metadata/consumer context has `localhost_callback_allowed=true`. This kind is for callback parameters, not for metadata `callback_endpoint`.

Use that helper from `AAuthEgressPolicy.ValidateUrl(endpoint: true)` so A07-002 is fixed for all existing callers, but stop using the `endpoint` boolean in new code. `endpoint: true` should reject both `?` and `#`; public signature can remain for source compatibility, while the implementation delegates to the typed helper.

For identifiers, change `AAuthEgressPolicy.IsValidIdentifier` and `ServerId.TryParse` to implement #server-identifiers strictly regardless of `ForDevelopmentLoopback`: `https`, lowercase host only, no port/path/query/fragment/trailing slash, no IP literal, no `localhost`. Keep `ForDevelopmentLoopback` for outbound egress destinations and callback exceptions only. Do **not** keep loopback issuers as an INFO-level deviation; this is a wire interop bug because conforming peers compare `issuer` and `iss` by exact bytes.

For agent identifiers, keep `AgentId.Parse/TryParse` as the generic parser for either top-level or sub-agent identifiers, but make the `+` structure valid only when there is exactly one delimiter, it is not first or last, and both parent local and discriminator are non-empty. Then centralize token subject checks in `AgentTokenBuilder` and `TokenVerifier`: no `parent_agent` means `sub` MUST be top-level; with `parent_agent`, the parent MUST be top-level, the subject MUST be a sub-agent, and `subject.ParentAgent == parent.Value`. This still follows #sub-agents L1897-L1901: protocol decisions use `parent_agent`, but the readability naming MUST is enforced.

For metadata producers, call the helper in every `Validate()` or `IValidateOptions` path before metadata can be served:

- direct metadata options in `AAuthAgentMetadataOptions`, `AAuthPersonServerMetadataOptions`, `AAuthAccessServerMetadataOptions`, and `AAuthResourceMetadataOptions`;
- high-level DI options in `PersonServerOptionsValidator`, `AccessServerOptionsValidator`, and eager `AddAAuthResource` validation;
- path-to-URL derivation for PS/AS paths (`TokenPath`, `PersonTokenPath`, `RevocationPath`, `MissionPath`, `PermissionPath`, `AuditPath`, `InteractionEndpointPath`, `InteractionPath`, `InteractionLoginPath`) by first rejecting query/fragment/control characters and requiring an app-rooted path, then deriving `issuer + path`;
- `AdditionalMetadata` for resource metadata: forbid or validate any core-defined AAuth metadata field even when the typed property is unset, so callers cannot bypass checks by injecting `logo_uri`, `authorization_endpoint`, or future R13 fields through the extension dictionary.

For consumers, replace `MetadataClient`'s array literal with a per-field rule table shared with producer validation. Validate all defined URL fields, including `permission_endpoint`, `audit_endpoint`, `mission_control_endpoint`, common URI fields, `callback_endpoint`, and `event_endpoint`; validate `localhost_callback_allowed` is a JSON boolean if present. The raw `FetchAsync` result must not enter the cache until the document has passed issuer and field validation. Typed `ServerMetadata.FromJson` and `ResourceMetadata.FromJson` may keep their public signatures, but their XML docs should say they expect a `MetadataClient`-validated document; if practical, they should also reuse the helper for URL shape as defense in depth.

For AP metadata, add public `AAuthAgentMetadataOptions.EventEndpoint` and `LocalhostCallbackAllowed`. `BuildAgentMetadata` emits `localhost_callback_allowed` only when true (the spec default is false) and emits `event_endpoint` from, in order: a single mapped `MapAAuthEventEndpoint` path derived as `options.Issuer + path`; otherwise explicit `options.EventEndpoint`; otherwise omitted. `MapAAuthEventEndpoint` should attach endpoint metadata such as `AAuthEventEndpointMetadata(Path)` so `MapAAuthAgentWellKnown` can discover it. If both mapped and explicit values exist and differ, fail at map/start; if more than one event endpoint is mapped, fail and require explicit `EventEndpoint`. This preserves C5 identity-once for the common Events registration and still supports a manually hosted inbox.

Adversarial closure: a malicious metadata issuer can no longer hide non-conformant URLs in fields the client previously skipped; a resource cannot use `AdditionalMetadata` to smuggle a reserved URL field around typed validation; a buggy AP cannot mint `aauth:parent+@ap.example` or a top-level token with `+` that an SDK verifier accepts; and local dev no longer emits `http://localhost:port` identifiers that pass only inside this SDK but fail at every conforming peer. The remaining deliberate relaxation is only the spec's callback-parameter exception, gated by AP metadata.

## Public API delta

- **Added:** `AAuth.Server.Metadata.AAuthAgentMetadataOptions.EventEndpoint : string?`.
- **Added:** `AAuth.Server.Metadata.AAuthAgentMetadataOptions.LocalhostCallbackAllowed : bool`.
- **Internal:** add `UrlKind` / metadata URL rule helper. No public protocol-string constants are needed; this is a closed enum-like implementation detail (C7).
- **Behavioral changes, no signature change:** `AAuthEgressPolicy.IsValidIdentifier`, `ServerId.TryParse`, and `AAuthUrl.IsHttpsOrLoopback` no longer treat `ForDevelopmentLoopback` origins as valid server identifiers; `AAuthEgressPolicy.ValidateUrl(endpoint: true)` rejects URI fragments as well as queries; `AgentId.TryParse` rejects empty/malformed sub-agent delimiters.
- **ApiSurface impact:** two public properties are added to `AAuthAgentMetadataOptions`; tests expecting development loopback server identifiers must be updated or removed.

## Wire effect

- Misconfigured producers fail at startup/map time instead of serving invalid `/.well-known/aauth-*.json` documents.
- `/.well-known/aauth-agent.json` can now include `event_endpoint` and `localhost_callback_allowed:true`.
- `issuer` and token `iss` values emitted by SDK producers must be strict HTTPS server identifiers; `http://localhost:port` issuers stop being emitted/accepted.
- Consumers reject metadata documents with invalid endpoint/common URI fields before caching or exposing typed models.
- `AAuth-Requirement: requirement=interaction` with a `url` containing `?` or `#` is rejected by both formatter and parser.

## Implementation sketch

1. **Central URL rules.** Add an internal helper near `AAuthEgressPolicy` (or replace `AAuthUrl` with an internal richer helper) with `UrlKind.Endpoint`, `Jwks`, `Informational`, and `Callback`. Update `AAuthEgressPolicy.ValidateUrl(string, bool endpoint = false)` to delegate to `Endpoint` when `endpoint` is true, including fragment rejection (`AAuthEgressPolicy.cs:95-L104`), and keep `ValidateJwksUrl` delegating to the `Jwks` rule.
2. **Strict server identifiers.** Remove `_loopbackOrigins.Contains(identifier)` from `IsValidIdentifier` (`AAuthEgressPolicy.cs:73-L80`). Leave `_loopbackOrigins` for `ValidateUrl` destination admission and `Callback` rules. Update error text in `ServerId.TryParse` (`ServerId.cs:27-L35`) and `AAuthUrl.IsHttpsOrLoopback` naming/comments, because it will no longer mean "or loopback" for identifiers.
3. **AgentId structure.** In `AgentId.TryParse`, after character validation, count `+`. If none, mark as top-level. If one, reject first/last delimiter and ensure parent local is itself top-level-shaped. Reject multiple delimiters. Keep `IsSubAgent`/`ParentAgent` semantics but they now operate only on structurally valid values. Update XML comments at `AgentId.cs:26-L39` so they mention a single delimiter and non-empty discriminator.
4. **Agent token producer/verifier.** Factor a shared internal routine such as `AgentIdRules.ValidateTokenSubject(subject, parentAgent, policy)` and use it in `AgentTokenBuilder` (`AgentTokenBuilder.cs:120-L153`) and `TokenVerifier` (`TokenVerifier.cs:653-L668`). Error when `parent_agent` is absent and subject is sub-agent; error when present but parent is sub-agent, subject is top-level, discriminator is empty, or derived parent differs.
5. **Producer metadata options.** Update `AAuthAgentMetadataOptions.Validate`, `AAuthPersonServerMetadataOptions.Validate`, `AAuthAccessServerMetadataOptions.Validate`, and `AAuthResourceMetadataOptions.Validate` to validate every typed URL field using the rule table. Required endpoints remain required; optional fields, when non-empty, must pass their kind. Validate resource `AdditionalMetadata` keys against a reserved-field map before merge (`WellKnownEndpoints.cs:180-L190`).
6. **DI/high-level validation.** Extend `PersonServerOptionsValidator` and `AccessServerOptionsValidator` to validate strict `Issuer`, all advertised paths, trusted server identifiers, and derived endpoint URLs (`AAuthPersonServerServiceCollectionExtensions.cs:209-L223`; `AAuthAccessServerServiceCollectionExtensions.cs:159-L177`). Add eager resource validation in `AddAAuthResource` before registering `IOptions<AAuthResourceOptions>` (`AAuthResourceServiceCollectionExtensions.cs:45-L48`). Keep the C3 pattern: sync shape validation at host start/composition; async key/HTTP failures remain first-use.
7. **Metadata consumer.** Replace `MetadataClient`'s string array (`MetadataClient.cs:104-L112`) with a static field-to-kind table and role-aware checks based on the well-known suffix. Validate `localhost_callback_allowed` type for AP metadata. Validate all URL fields before `_cache.Response(doc, response)`.
8. **AP Events metadata.** Add `EventEndpoint` and `LocalhostCallbackAllowed` to `AAuthAgentMetadataOptions`. Have `EventsEndpoints.MapAAuthEventEndpoint` attach route metadata. Have `BuildAgentMetadata` derive `event_endpoint` from exactly one mapped event endpoint plus `options.Issuer`, falling back to explicit `EventEndpoint`, and fail on conflicts. Emit `localhost_callback_allowed` only when true.
9. **Docs/samples/tests.** Update local-dev issuers to strict HTTPS/example identifiers where they are protocol identifiers; keep loopback origins only in egress policies and callback examples.

## Dependencies and conflicts with other Rnn

- **R13** owns A04-04 (`additional_signature_components`) and will likely add a typed resource metadata field. The R16 reserved-field/URL helper must include R13's new resource field if it is URL-like or prevent `AdditionalMetadata` from shadowing it; do not duplicate R13's signing behavior.
- **R17** owns Events protocol behavior. R16 should only expose/discover AP `event_endpoint` and validate its URL; do not change subscription/event delivery statuses or body semantics here.
- **R18/R19** own broad samples/docs rewrites. R16 should list required files and update directly related text only if implementing this area in isolation; larger narrative changes can be coordinated there.
- **R14** may tighten TLS transport policy. R16's URL helper should check URI scheme and metadata shape, leaving protocol-version pinning to R14.
- **C12 named role instances**: PS/AS validators are named `IOptions` with `ValidateOnStart`; resource remains eager `IOptions<AAuthResourceOptions>`. Keep those conventions rather than introducing a new role options model.

## Open questions (with proposed default)

1. **Should strict server identifiers still allow `https://localhost` with no port?** Proposed default: no. The spec examples mark loopback only for callback parameters, and `AAuthEgressPolicy.IsValidIdentifier` already rejects `localhost`; keep that.
2. **Should `Informational` URLs use egress private-address admission?** Proposed default: yes for consumers (they may fetch/render those links) and shape-only for producers unless a policy is supplied; all cases require `https`.
3. **Should AP `localhost_callback_allowed=false` be emitted explicitly?** Proposed default: omit false because the spec default is false; emit only true.
4. **What if multiple `MapAAuthEventEndpoint` routes exist?** Proposed default: fail metadata mapping unless `AAuthAgentMetadataOptions.EventEndpoint` is set explicitly and validates, because AP metadata has one `event_endpoint`.
5. **Should `ServerMetadata.FromJson` reject invalid URLs even without `MetadataClient`?** Proposed default: add defense-in-depth validation for URL shape with Production policy, but keep issuer-match and JWKS same-origin checks in `MetadataClient` where expected issuer is known.
