# R05 — Upstream provenance and interaction chaining

Findings: SDK-04/A18-001, A18-003, SMP-03/S05-001, DOC-05/D07-01, D07-02. Spec: #upstream-token-verification L1826-L1837, #call-chaining L1846-L1881, #interaction-chaining L1882-L1887, #interaction-code-format L2382-L2401, #revocation-cascade L2747-L2758, #flow-call-chaining L3304-L3346, #flow-interaction-chaining L3347-L3417. Files read: `src/AAuth/Tokens/UpstreamTokenValidator.cs`, `src/AAuth/Tokens/AgentIssuanceContext.cs`, `src/AAuth/Person/AAuthPersonServerEndpoints.cs`, `src/AAuth/Server/IJtiStore.cs`, `src/AAuth/Server/InMemoryJtiStore.cs`, `src/AAuth/Server/TokenRegistration.cs`, `src/AAuth/Server/AuthTokenResponse.cs`, `src/AAuth/Person/AgentPersonBinding.cs`, `src/AAuth/Agent/AAuthInteractionExceptions.cs`, `src/AAuth/Server/CallChaining/CallChainingHandler.cs`, `src/AAuth/Server/ResourceManaged/*`, `samples/Concierge/Program.cs`, `samples/Concierge/PendingStore.cs`, `samples/SampleApp/Components/Pages/CallChain.razor`, `docs/workflows/call-chaining.md`, `docs/advanced/interaction-chaining.md`, related tests under `tests/AAuth.Conformance` and `tests/AAuth.Tests`.

## Problem restated (verified)

- SDK-04/A18-001 is still present. `UpstreamTokenValidator` documents and implements only §Upstream Token Verification steps 1-3 (`UpstreamTokenValidator.cs:70-132`): it verifies `typ`, `aud`, `ps`/`iss`, and then accepts any AS issuer approved by the `isTrustedAuthTokenIssuer` predicate (`:128-133`). `AgentIssuanceContext.VerifyAsync` calls that validator and adds the upstream token as a source (`AgentIssuanceContext.cs:75-86`), but it never asks the PS inventory whether this PS presented a person token to that AS for the upstream auth token's `aud`/`sub`, nor whether the original calling agent can be identified (`#upstream-token-verification`, L1833-L1835). The PS predicate is static trust only (`AAuthPersonServerEndpoints.cs:243-247`). `RegisterSourcesAsync` records the current intermediary agent subject (`:394-405`), not the original caller for the upstream token. If the store has no prior record, `InMemoryJtiStore.RegisterAsync` creates a new entry for a live token (`InMemoryJtiStore.cs:43-55`), so store loss or an unrelated trusted-AS token fails open.
- The existing inventory has useful pieces but not the required record. `IJtiStore` can register/revoke token keys, attach grants to sources, and record a subject for a registered token (`IJtiStore.cs:20-52`; `InMemoryJtiStore.cs:106-185`). `AuthTokenResponse.MintTrackedAsync` records each PS-issued or federated response as a `TokenGrant` with `(iss,jti)`, resource/audience and expiry (`AuthTokenResponse.cs:56-72`). However `TokenGrant` has no `sub`, presented-person-token key, AS-presentation tuple, original-caller agent key, or reverse source lookup (`TokenRegistration.cs:10-32`; `TokenGrant.cs:5`). That is insufficient for the Records paragraph of #revocation-cascade L2756-L2758 and for step 4 of #upstream-token-verification L1835.
- A18-003, SMP-03 and DOC-05 are still present. The chaining exception explicitly says the downstream PS `url`/`code` are “passed through” (`AAuthInteractionExceptions.cs:64-72`), and `CallChainingHandler` forwards only a callback with the downstream `Interaction` (`CallChainingHandler.cs:51-80`). The Concierge sample stores `ex.Interaction.Url` and `ex.Interaction.Code` and re-emits them in its own 202 (`samples/Concierge/Program.cs:217-239`, `:255-259`, `:279-284`; `PendingStore.cs:29-30`); the SampleApp page mirrors this (`CallChain.razor:89-112`). The docs teach the same pass-through (`docs/advanced/interaction-chaining.md:18-19`, `:107-119`, `:232-235`). This violates #interaction-chaining L1884-L1886: the intermediary must return its own interaction code and own `Location`.
- D07-02 is still present. `docs/workflows/call-chaining.md` tells PS authors to use `UpstreamTokenValidator` as the upstream-token check (`:324`, `:340-345`) and then notes only steps 1-3 (`:371-381`), so a copied manual endpoint omits step 4 and the PS-issued/federated provenance check.
- The SDK already has part of an interaction primitive, but for a different flow. `RequireAAuthInteraction` parks a resource-managed interaction and emits a spec-shaped 202 with a generated code and poll `Location` (`AAuthResourceManagedHttpContextExtensions.cs:23-47`), backed by `IInteractionPendingStore` single-use code semantics (`IInteractionPendingStore.cs:38-64`). Its poll endpoint issues `AAuth-Access` and is tied to two-party resource-managed access (`AAuthInteractionEndpointExtensions.cs:17-24`, `:77-90`), so intermediaries should not reuse it as-is for completing an arbitrary original call-chain request.

## Recommendation

Adopt candidate 2. Treat upstream provenance as part of the same token inventory used for revocation cascade, not as host policy and not as a separate optional store. Add a serializable `AAuthTokenProvenance` (name bikesheddable) and extend `IJtiStore`/`InMemoryJtiStore` with atomic provenance-aware grant registration and lookup. The record should include: token key, token type (`aa-person+jwt`/`aa-auth+jwt` via constants), `aud`, `sub`, `ps`, expiry, source keys, original caller agent issuer/sub and agent-token key, agent-person-binding key, and for federated AS auth tokens the AS issuer plus the presented person-token key. For AS-issued auth tokens, validation must compare the stored AS, `aud` and `sub` to the token being verified.

The PS full upstream check should be an SDK primitive used by `AgentIssuanceContext.VerifyAsync`, not a doc-only recipe. It should perform steps 1-3 with the current cryptographic validator, then at PS role perform provenance step 4: lookup the upstream token key; reject missing records as `invalid_upstream_token`; reject revoked upstream token, recorded caller agent token, or recorded agent-person binding as `revoked_upstream_token`; and surface the recorded caller on `UpstreamTokenValidationResult` for mission/supervision policy. Static `Trust.AccessServers` may still further restrict AS issuers, but it is never sufficient by itself.

For interaction chaining, add a call-chaining interaction module rather than reusing resource-managed `AAuth-Access`. The module parks a serializable `ChainedInteractionEntry` with an SDK-generated intermediary code, downstream `Interaction`, original-agent poll owner, operation name and JSON state; emits `202` with the intermediary's own `AAuth-Requirement` `url`/`code` and own `Location`; maps the intermediary interaction URL to validate/consume the own code and redirect the user to the downstream PS/AS interaction; and maps the poll URL to resume the registered operation and retain/return the original response. `AAuthInteractionChainedException` should no longer describe or encourage pass-through; it can carry the downstream requirement for the SDK primitive to wrap.

Adversarial closure: a compromised but statically trusted AS cannot mint an arbitrary upstream auth token unless the PS inventory has the exact federated-auth provenance for that `(iss,jti,aud,sub)`; a restarted/lost in-memory PS rejects because the record is absent; a revoked original caller or binding is caught through the recorded agent/binding keys even when the upstream token itself is not revoked. A malicious original agent only sees the intermediary's code and Location; it does not receive the downstream PS code until the user is redirected through the intermediary URL, so Resource 1 owns correlation, expiry and completion.

## Public API delta

- **Yes.** `IJtiStore` changes: add provenance-aware atomic grant registration/lookup, for example `RegisterGrantAsync(..., AAuthTokenProvenance provenance, ...)` and `GetProvenanceAsync(TokenKey, ...)`, or replace `TokenGrant` with a record that contains provenance and sources. `InMemoryJtiStore` implements it and continues warning as an in-memory default.
- **Yes.** Add public serializable records such as `AAuthTokenProvenance`, `UpstreamCallerRecord` and possibly `UpstreamTokenValidationRequest`/`Role` so `UpstreamTokenValidator` can distinguish PS full validation from AS steps 1-3. This is an ApiSurface diff and a single cutover per C1.
- **Yes.** `UpstreamTokenValidationResult` gains the identified caller (`CallingAgentIssuer`, `CallingAgentId`, `CallingAgentToken`, `AgentPersonBinding`) and an error classification for `invalid_upstream_token` versus `revoked_upstream_token`.
- **Yes.** Add call-chaining interaction APIs, e.g. `AddAAuthInteractionChaining`, `MapAAuthChainedInteractions`, `HttpContext.RequireAAuthChainedInteraction(...)`, `IChainedInteractionStore`, `ChainedInteractionEntry`, and endpoint metadata similar to `WithHeldInvocation`. `AAuthInteractionChainedException` documentation and possibly property names change from pass-through `Interaction` to `DownstreamInteraction`.

## Wire effect

- PS token endpoints that currently accept unknown AS-issued upstream auth tokens now fail closed with `400 {"error":"invalid_upstream_token"}` when no provenance record exists or the stored AS/audience/subject does not match (#upstream-token-verification L1833-L1835).
- If the upstream token, the recorded original caller agent token, or the recorded agent-person binding is revoked, PS token endpoints return `400 {"error":"revoked_upstream_token"}`. Pending chained requests whose source becomes revoked should terminate with polling `revoked` per #presenting-a-revoked-token L2766-L2767 (coordinate with R06).
- No new JWT claims are required. The new data is server-side inventory only, matching #revocation-cascade Records L2756-L2758.
- Intermediary 202 responses change: `AAuth-Requirement: requirement=interaction` carries the intermediary-owned URL/code, and `Location` is the intermediary poll URL. The downstream PS/AS URL/code is no longer emitted to the original agent. The intermediary interaction endpoint redirects the browser to the downstream URL with the downstream code.
- Unknown/expired/consumed chained interaction codes use registered polling errors (`invalid_code`/`expired`) instead of sample-only `unknown_pending`; waiting polls return `202` with `Retry-After` and `Cache-Control: no-store`.

## Implementation sketch

1. Add protocol constants for token `typ` values if they are not already centralized in `AAuthConstants`; use those in provenance validation (C7).
2. Extend the inventory model in `src/AAuth/Server`: add `AAuthTokenProvenance` and update `IJtiStore`, `InMemoryJtiStore`, `TokenGrant`/`AuthTokenResponse.MintTrackedAsync` so grant registration and provenance recording are atomic. Preserve source ancestry and subject lookup; do not allow `RegisterAsync` of an unseen upstream token to create the only record needed for step 4.
3. When minting any PS person/auth token in `AAuthPersonServerEndpoints`, build provenance from the current `AgentIssuanceContext`. For direct requests, caller is the current agent and binding key is `AgentPersonBinding.Key(...)`; for chained requests, caller is copied from the validated upstream provenance. Record issued person tokens with their upstream token key when applicable, as required by #revocation-cascade Records L2758.
4. In the four-party federation path, after `AccessServerClient.FederateAsync` returns and before returning the AS auth token to the agent, decode/verify the returned token and register provenance atomically: AS issuer, auth token key, `aud`, `sub`, `ps`, presented person-token key, and the caller from the presented person token's provenance. If the presented token lacks provenance, fail the request instead of federating/returning. Coordinate with R06 so source revocation is checked before the outbound `FederateAsync` call as well.
5. Replace `IsTrustedAuthTokenIssuer` as the deciding PS upstream-auth-token check. `UpstreamTokenValidator` may keep a steps-1-3 internal method, but `AgentIssuanceContext.VerifyAsync` at a PS must call the full provenance-aware validator with `IJtiStore`, the PS issuer, current trust policy and the intermediary agent token.
6. Update error rendering so provenance-missing maps to `invalid_upstream_token` and revoked caller/binding maps to `revoked_upstream_token`; do not leak whether a particular AS auth `jti` was once known beyond the spec error class.
7. Add `src/AAuth/Server/CallChaining` interaction-chaining module: options, store interface + in-memory implementation, helper to park a downstream `AAuthInteractionChainedException`, own-code generation via `AAuthInteractionCode`/`BrowserInteraction`, 202 result helper, user redirect endpoint, and owner-bound poll/resume endpoint. Reuse `HeldInvocationResult` for retained original responses where possible, but keep the store record serializable (operation name + JSON state, not delegates).
8. Update `AAuthInteractionChainedException` XML/docs and `CallChainingHandler` samples so callbacks throw/capture the downstream interaction but never write it directly to the caller; the new helper wraps it.
9. Update Concierge and SampleApp to use the SDK primitive. `PendingStore` should stop storing downstream `InteractionUrl`/`InteractionCode` as the emitted requirement; if it remains as sample state, store them only for the intermediary redirect/resume internals. Fix pending errors/statuses while touching the flow.
10. Rewrite docs: `docs/workflows/call-chaining.md` must state that PS upstream validation is full steps 1-5 only through the provenance-aware SDK path; `docs/advanced/interaction-chaining.md` must show own code + own Location and the intermediary redirect.

## Dependencies and conflicts with other Rnn

- R06 owns revocation ordering before federation and pending-source revocation. R05 needs its provenance records, but R06 should still perform the immediate preflight before outbound AS calls. Share the same `TokenRegistration`/source dependency model to avoid duplicate revocation checks.
- R02 owns four-party resource trust and AS-issued token acceptance at resources. R05 is PS-side upstream-token provenance only; do not make resources require PS inventory records for ordinary AS auth tokens.
- R11 owns deferred polling error-code cleanup. R05's chained poll endpoint should use the same polling error constants/status helpers to avoid another invented `unknown_pending`.
- R03/resource-managed access already has `IInteractionPendingStore`; R05 should reuse `AAuthInteractionCode` and result formatting, but not overload the `AAuth-Access` store/poll endpoint for call chaining.
- API-surface initiative C1 means no old pass-through helper overloads; samples/docs must cut over in the same implementation phase.

## Open questions (with proposed default)

1. **Should provenance be added to `IJtiStore` or a new store?** Default: extend `IJtiStore` with provenance-aware atomic grant registration and lookup. It is the existing token inventory named by #revocation-cascade Records, and one store is the only way to make revocation/provenance fail closed consistently.
2. **Must current `Trust.AccessServers` still pass for an AS-issued upstream auth token with matching provenance?** Default: yes when the trust policy is configured; when trust is intentionally open, provenance alone establishes that this PS actually federated to that AS for the token. Static trust never substitutes for provenance.
3. **How should PS-issued auth tokens be identified in step 4?** Default: record provenance for every PS-issued auth token at mint time, tied to the presented person token/caller just like federated AS auth tokens. Do not infer caller from `sub` or from the current intermediary.
4. **What happens after in-memory store loss?** Default: fail closed with `invalid_upstream_token` for upstream-token use. This is acceptable for the development default and should be called out in the in-memory warning/docs; production deployments need persistent/shared `IJtiStore`.
5. **Should the chained-interaction primitive store delegates?** Default: no. Store operation name + JSON state, and keep executable delegates in endpoint metadata like held invocations so custom stores remain serializable (C10).
