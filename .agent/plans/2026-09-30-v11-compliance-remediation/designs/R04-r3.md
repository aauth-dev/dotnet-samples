# R04 — R3 single use, audit and entitlement

Findings: SDK-03, SDK-19, A23-003, A23-004, A22-MED-001, DOC-06. Spec: R3 #operation-identifier-scope L150-L155, #operations-spanning-definitions L431-L443, #r3-processing L532-L559, #per-call-flow L671-L683, #r3-document-access-restriction L723-L733, #operation-validation L742-L745. Files read: `src/AAuth.R3/R3Enforcement.cs`, `R3ProposalStore.cs`, `R3Audit.cs`, `R3AccessTokenEndpoint.cs`, `R3DocumentEndpoint.cs`, `R3DocumentReaderPolicy.cs`, `R3DocumentEntitlements.cs`, `R3Challenge.cs`, `R3Metadata.cs`, `Model/R3VocabularySchemas.cs`, `src/AAuth/Server/HeldInvocations.cs`, `src/AAuth/Tokens/AgentIssuanceContext.cs`, `samples/MockResourceServers/Bookings/Program.cs`, `samples/MockResourceServers/Catalog/Program.cs`, `samples/MockAccessServers/R3/SqliteR3AuditSink.cs`, `docs/workflows/rich-resource-requests.md`, `src/AAuth.R3/README.md`, `tests/AAuth.R3.Tests/*`, `tests/AAuth.Conformance/ResourceTokens/HeldInvocationTests.cs`, audit and API-surface research/log extracts.

## Problem restated (verified)

- **SDK-03 / DOC-06: approved proposal replay executes repeatedly.** Verified current `R3Enforcement` still returns plain `Granted` for an approved proposal retry after hash, operation, account, and parameter checks (`R3Enforcement.cs:95-141`). The only SDK single-use mechanism is separate, `IAAuthSingleUseGate.ExecuteOnceAsync` keyed by auth-token `jti` (`HeldInvocations.cs:70`). Bookings composes it manually (`Bookings/Program.cs:276-278`), but the workflow doc's example calls `enforcement.Evaluate(... approvedProposalS256 ...)` directly (`docs/workflows/rich-resource-requests.md:157-158`). This contradicts #per-call-flow L676-L678: one per-call auth token must execute no more than one invocation and replay must return the retained result keyed by `jti`.
- **SDK-19: AS issuance audit omits required resource-token fields.** Verified `R3TokenIssuanceAuditRecord` includes R3 URI/hash, agent id, resource issuer, AS issuer, issued-at, token id/hash and account, but not `ps`, `sub`, or `agent_jkt` (`R3Audit.cs:11-23`). `MintAndAuditAsync` records only `parts.Uri`, `parts.S256`, `issuance.AgentId`, resource/AS issuers, timestamp, and kind (`R3AccessTokenEndpoint.cs:90-97`). #r3-processing L548 requires `r3_uri`, `r3_s256`, timestamp, `ps`, `sub`, `agent_jkt`, and agent identifier to be recorded with token issuance.
- **A23-003: designated AS can fetch any document.** Verified the DI `MapR3Document` path gates entitlements only for fetchers using the person-server DWK (`R3DocumentEndpoint.cs:43-53`). `R3DocumentReaderPolicy.Allows` admits the configured access server by identifier and `aauth-access.json` DWK (`R3DocumentReaderPolicy.cs:20-22`), so the AS bypasses `IR3DocumentEntitlements` even though `R3Challenge` entitles both `aud` and `ps` on mint (`R3Challenge.cs:116-117`). #r3-document-access-restriction L725-L730 requires both AS and PS fetchers to be parties named by a resource token carrying that `r3_uri`.
- **A23-004: resource-token minting does not require authoritative operation validation.** Verified `R3Challenge.BuildCoreAsync` validates only identifier shape and the R3 URI/hash pair (`R3Challenge.cs:55-60`) before minting a resource token. `R3AccessTokenEndpoint` can apply AS policy callbacks after fetching (`R3AccessTokenEndpoint.cs:695-696`), but that is not the resource-side MUST in #operation-validation L742-L745. Shape validation in `R3VocabularySchemas.Validate` (`Model/R3VocabularySchemas.cs:49-78`) does not prove membership in OpenAPI/MCP/etc.
- **A22-MED-001: ambiguous bare operation ids are accepted.** Verified `R3Metadata.ValidateOperations` flattens `authoritativeOperations` and succeeds if any identity matches (`R3Metadata.cs:34-44`); it never rejects duplicate authoritative identities for the advertised vocabulary. #operation-identifier-scope L150-L155 and #operations-spanning-definitions L431-L443 require the single advertised definition for a vocabulary to resolve bare identifiers unambiguously, or for the resource to rename/split services.

## Candidate fixes

| # | Approach | Pros | Cons | Spec fit | API-surface fit (C1–C13) |
|---|---|---|---|---|---|
| 1 | Document-only guidance: keep `R3Enforcement` returning `Granted`; tell consumers to wrap approved proposal routes in `IAAuthSingleUseGate`. | Tiny code churn; matches Bookings' current manual pattern. | Reproduces SDK-03 for any copied SDK primitive or doc snippet; not fail closed; SDK does not own mandated mechanics. | Poor: #per-call-flow L676 remains optional-by-composition. | Fails C6; also leaves DOC-06 fragile. |
| 2 | Make `R3Enforcement` claim the gate during evaluation and still return `Granted` when the claim succeeds. | SDK checks `jti`; old `Kind == Granted` route code still executes first call. | A claimed-but-never-executed decision can strand the grant until release; evaluation cannot retain the actual HTTP result; replay during/after execution still requires app-specific code. | Partial: prevents parallel claims but cannot satisfy retained-result replay by itself. | Partially uses C10, but mechanics are split and easy to misuse, so weak C6. |
| 3 | Add an SDK execute-once decision for approved proposals: evaluation validates the proposal and returns `R3EnforcementDecisionKind.SingleUse` carrying an execute-once handle keyed by auth-token `jti`/`exp` and an `IAAuthSingleUseGate`; `Granted` is reserved for class grants. The handle's `ExecuteOnceAsync` wraps the application callback and returns/retains `HeldInvocationResult`. Missing `jti`, `exp`, or gate rejects/fails before execution. | Fail closed for old `Kind == Granted` checks; SDK owns claim/complete/result; app only supplies operation callback; concurrent replay waits and receives retained result. | Public API cutover; samples/tests must update to call the handle for per-call approvals. | Strong: implements #per-call-flow L676-L678 and Deferred Delivery retained-result semantics. | Strong: C1 cutover, C6 mechanics in SDK, C10 gate shape reused. |
| 4 | Keep `IR3DocumentEntitlements` keyed only by `(s256, reader)` and apply it to AS as well as PS. | Fixes the direct AS bypass with minimal API change. | Entitlement is not tied to the `r3_uri` or resource-token lifetime; an old token can permanently authorize the same hash at a different URI. | Better but not exact: #r3-document-access-restriction names a token carrying that URI. | Partial C6; not adversarial enough for A23-003. |
| 5 | Replace entitlement checks with a typed entitlement record `(r3_uri, r3_s256, reader, resource_token_jti, expires_at)` and typed access check. `R3Challenge` writes AS and PS entitlements atomically with resource-token minting; `MapR3Document` requires a matching, unexpired entitlement for every AS/PS fetcher. | Closes AS bypass, URI aliasing, stale grant, and scale-out semantics; keeps `EntitleAsync` public for host-minted tokens. | Public API and store migration; token must be signed before entitlement so failures must suppress returning the header. | Strong: exactly models the parties named by a resource token carrying `r3_uri` (#r3-document-access-restriction L725-L730). | Strong: C1, C6, C10-style serializable store; respects ASL Q12. |
| 6 | Let every sample call `R3Metadata.ValidateOperations` before `R3Challenge`, and improve duplicate detection there. | Low churn; helps Bookings/Catalog. | SDK still allows minting without validation; other hosts miss the MUST. | Partial for samples only. | Fails C6 and R0 default enforcement. |

Update `R3Metadata.ValidateOperations` to reject duplicate authoritative matches. | Fail-closed SDK default; supports OpenAPI/MCP/proto/etc. through R0 provider; fixes both A23-004 and A22-MED-001. | Requires hosts to register or pass an authoritative provider/resolver; public API cutover. | Strong: #operation-validation L742-L745 and #operation-identifier-scope L150-L155. | Strong: C2/C4 R0 ladder, C6 SDK mechanics, C7 typed vocabulary constants. |

## Recommendation

Adopt candidate **3 + 5 + 7**, plus the SDK-19 audit shape change.

Single-use should **not** be a bare `Granted` decision after a successful gate claim. It should be an execute-once handle because the SDK must retain the actual resource response, not merely authorize execution. `R3Enforcement` should require an auth-token envelope with `jti` and `exp` for approved proposal retries and resolve an `IAAuthSingleUseGate` from the request/constructor/DI; after proposal verification it returns `SingleUse`, whose only success path is `ExecuteOnceAsync(Func<CancellationToken, Task<HeldInvocationResult>>)` over the existing gate. A replay receives the retained `HeldInvocationResult`; a missing gate, `jti`, or `exp` yields `single_use_required` rather than `Granted`.

For R3 document fetches, replace hash-only entitlement with typed, expiring, URI-bound entitlement and apply it to **both** AS and PS readers. Keep coarse `R3DocumentReaderPolicy` only as "could this identity ever be a reader for this resource?"; the per-document answer must come from `IR3DocumentEntitlements`.

For operation validation, make SDK resource-token minting fail closed unless the referenced R3 document/proposal has been validated against an authoritative definition provider. Update `R3Metadata.ValidateOperations` to reject duplicate bare ids before membership checks, so merged definitions with colliding `operationId`/tool names fail unless renamed or split.

Adversarial closure: an attacker who guesses an R3 URI but lacks a token-specific entitlement gets 404 even if they are the designated AS; an attacker replaying a copied per-call auth token gets the retained response, not a second side effect; a resource aggregating two `list` operations cannot mint a token until it publishes a single unambiguous definition; an AS audit sink cannot record a successful issuance without the required `ps`/`sub`/`agent_jkt` fields.

## Public API delta

- **Changed:** `R3ClaimReader.AuthTokenClaims` / new `R3VerifiedAuthToken` envelope includes `TokenId` (`jti`) and `ExpiresAt` (`exp`). `R3ClaimReader.ReadAuthToken(JsonObject)` must read them from verified JWT payloads; test-only/manual constructors must supply them when evaluating approved proposals.
- **Changed:** `R3Enforcement` approved-proposal evaluation returns `R3EnforcementDecisionKind.SingleUse` instead of `Granted`. Add `R3EnforcementDecision.SingleUseExecution` (or equivalent) with `ExecuteOnceAsync`; `ToResult()` must throw for `SingleUse` just as it throws for `PerCall`, because a route callback is required. Remove or cut over overloads that can approve a proposal without `jti`/`exp`/gate.
- **Added/changed:** `IR3DocumentEntitlements.EntitleAsync(R3DocumentEntitlement entitlement, ...)` and `IsEntitledAsync(R3DocumentAccessCheck check, ...)`, where entitlement/check include `Uri`, `S256`, `Reader`, `ExpiresAt`, and optionally `ResourceTokenId`. `EntitleAsync` remains public for host-minted tokens per ASL Q12.
- **Changed:** `R3DocumentReaderPolicy` no longer has a PS-only `IsEntitledPersonServer` bypass. If a deployment needs custom policy, expose it as an entitlement provider/delegate through the R0 ladder, not as a path around the entitlement store.
- **Added:** `IR3AuthoritativeDefinitionProvider`, `IR3OperationValidator`, `R3OperationValidationContext`, `R3AuthoritativeDefinition`, and a default validator used by `R3Challenge` and by public helpers. `R3Metadata.ValidateOperations` uses the same duplicate-detection logic.
- **Changed:** `R3TokenIssuanceAuditRecord` constructor/required properties add `PersonServer`, `Subject`, `AgentJkt`, `BoundAgentId`, and optional `ParentAgentId`/`ResourceTokenId`. The `AgentId` recorded for issuance should be the bound agent (`subagent_token.sub` when present); `ParentAgentId` records the parent agent-token `sub` when applicable, matching #r3-processing L550-L555.
- **ApiSurface impact:** yes. Expect snapshots to change for `AAuth.R3` enforcement decisions, entitlement records, audit record constructor, and operation-validation seams.

## Wire effect

- Per-call approved retries: first presentation executes the route callback and returns its normal response; repeated presentation of the same auth token `jti` returns the retained status/content/body. It no longer re-enters application side-effect code.
- If an approved proposal retry lacks a verified auth-token `jti`/`exp` or no `IAAuthSingleUseGate` is configured, the SDK returns/throws a fail-closed R3 denial such as `single_use_required` (403 for route evaluation; implementation can use `InvalidOperationException` for primitive misuse before an HTTP response starts).
- R3 document/proposal fetch: validly signed but unentitled AS/PS readers receive `404` (same indistinguishable behavior currently documented for unentitled PS readers); malformed/unsigned signatures remain `401`, and identities not trusted by the coarse reader policy remain `403`.
- Resource-token minting through `R3Challenge`: invalid, nonexistent, or ambiguous operations prevent the `AAuth-Requirement` challenge from being emitted. In middleware/high-level helpers this should become `r3_operation_validation_failed` / `r3_configuration_error`; primitive `BuildResourceTokenAsync` may throw.
- AS token endpoint response bodies and auth-token claims do not need new wire claims for SDK-19; the change is durable audit content. SQLite audit schema changes are local persistence wire, not protocol wire.

## Implementation sketch

1. **Single-use enforcement.**
   - Extend the R3 auth-token read path to carry `jti` and `exp` from the verified JWT payload. Prefer a new `R3VerifiedAuthToken.FromVerified(TokenVerifier.VerifiedToken, R3VocabularySchemas?)` wrapper so evaluation cannot accidentally use unverified payloads.
   - Add `SingleUse` to `R3EnforcementDecisionKind` and an execution object containing `Jti`, `ExpiresAt`, and `IAAuthSingleUseGate`.
   - In `R3Enforcement.EvaluateApprovedProposalRetry` (`R3Enforcement.cs:95-141`), after all existing proposal and parameter checks pass, return `SingleUse` instead of `Granted`. If `jti`/`exp`/gate are absent, return `Rejected("single_use_required")` or throw before any app callback can run.
   - Implement `R3EnforcementDecision.ExecuteOnceAsync` by delegating to `IAAuthSingleUseGate.ExecuteOnceAsync` (`HeldInvocations.cs:70-98`). On callback exception, the existing extension releases the claim; on success, it retains the result until token expiry.
   - Update `R3EnforcementDecision.ToResult()` (`R3Enforcement.cs:183-193`) to throw for `SingleUse`; add a route-friendly `ToResultAsync(Func<CancellationToken, Task<HeldInvocationResult>> execute, ...)` overload.

2. **Audit record.**
   - Add required audit fields to `R3TokenIssuanceAuditRecord` (`R3Audit.cs:11-23`). Keep `TokenId`/`TokenS256` required.
   - Extend `AgentIssuanceContext` (`AgentIssuanceContext.cs:18-126`) with `BoundAgentId` and optional `ParentAgentId`; set `BoundAgentId` from the bound token's `sub` after optional sub-agent verification.
   - In `/token`, copy `ps`, `sub`, `agent_jkt`, and `jti` from `verifiedResource.Payload` into `AuthMintParts` after `VerifyResourceTokenAsync` (`R3AccessTokenEndpoint.cs:163-178`). Record those fields in `MintAndAuditAsync` (`R3AccessTokenEndpoint.cs:63-99`) rather than inferring them from request parameters.
   - Update `SqliteR3AuditSink` (`samples/MockAccessServers/R3/SqliteR3AuditSink.cs:7-63`) to persist explicit columns for the required audit fields plus the JSON record. Use `PRAGMA user_version` and a transaction to migrate old sample databases: create a v2 table, copy records that deserialize with required fields, preserve nonconforming legacy rows in a `r3_audit_legacy` table or document that sample DBs must be recreated.

3. **Per-token R3 document entitlement.**
   - Replace `(s256, reader)` storage in `InMemoryR3DocumentEntitlements` (`R3DocumentEntitlements.cs:11-35`) with a serializable key including normalized absolute `Uri`, `S256`, and `Reader`, plus `ExpiresAt`; sweep expired records. Validate URI and reader identifiers with the egress policy where available.
   - In `R3Challenge.BuildCoreAsync`, sign the resource token, read its `jti` and `exp`, then call `EntitleAsync` for `Audience` and `personServer` with the exact `r3Uri`, `r3S256`, token id and expiry before returning the token (`R3Challenge.cs:84-118`). If either entitlement write fails, do not return the token/header.
   - In `R3DocumentEndpoint.MapR3Document` (`R3DocumentEndpoint.cs:38-54`), after signature verification and coarse `readerPolicy.Allows`, compute the absolute request URI and bytes hash, then require `entitlements.IsEntitledAsync` for both access-server and person-server DWKs. Remove the PS-only entitlement branch and `IsEntitledPersonServer` bypass.
   - Keep the explicit old `MapR3Document(..., isTrustedFetcher)` overload only if it is cut over to an entitlement-aware overload; otherwise remove it under C1 so samples cannot bypass A23-003 accidentally.

4. **Authoritative operation validation.**
   - Add a validator seam in `src/AAuth.R3`: `IR3AuthoritativeDefinitionProvider` returns the advertised vocabulary endpoint(s) and authoritative `R3OperationIdentity` set for the resource; `IR3OperationValidator` validates a parsed `R3Document` or `R3ProposalDocument` against it.
   - The default validator first validates vocabulary shape, then groups authoritative identities by the exact token-visible identifier for the advertised vocabulary. Any group with count > 1 throws an ambiguity error before checking requested/document operations. Each document/proposal operation must match exactly one authoritative identity.
   - Update `R3Metadata.ValidateOperations` (`R3Metadata.cs:34-44`) to call the same uniqueness helper. This fixes agent `r3_operations` requests as well as R3 documents.
   - Add an R0 ladder on `R3Challenge`: per-call argument/validated reference, explicit `OperationValidator`/provider property, DI provider, then no default provider => fail closed. `ChallengeAsync` can resolve DI via `HttpContext`; primitive `BuildResourceTokenAsync` must either receive a validated reference or an explicit validator/provider.
   - Register providers in Bookings and Catalog from their published OpenAPI metadata and supported operation arrays instead of passing ad-hoc `IEnumerable<R3OperationIdentity>` only at route sites.

## Dependencies and conflicts with other Rnn

- **R11 deferred delivery:** reuse `HeldInvocationResult` and `IAAuthSingleUseGate` semantics; do not fork a second retained-result store.
- **R14 JWT hygiene:** depends on verified auth tokens having trustworthy `jti` and `exp`; if R14 tightens JWT validation, R04 should consume that envelope rather than parse raw JSON independently.
- **R16 metadata and identifier validation:** operation-provider discovery endpoint validation overlaps resource metadata validation; share vocabulary constants and URI validation.
- **R18/R19 samples/docs:** Bookings, Catalog, GuidedTour, R3 README, and workflow docs all need coordinated rewrites.
- **R05/R10 agent identity:** audit `BoundAgentId`/`ParentAgentId` should align with any upstream/sub-agent identity changes; R04 should not invent a conflicting agent-binding model.

## Open questions (with proposed default)

None. Proposed defaults are part of the recommendation: execute-once handle instead of plain `Granted`; URI/hash/reader/expiry entitlements for both AS and PS; operation validation fail-closed via R0 provider; audit records use the bound agent id and optionally retain parent id.
