## Problem restated (verified)

- SDK-17 is verified. The compact-JWS path decodes header/payload and then calls `ValidateStructure` (`TokenVerifier.cs:734-742`), but `ValidateStructure` only requires `alg`, `typ`, `kid`, required claims and claim shapes (`TokenVerifier.cs:629-645`) and never reads `crit`. `NamingTokenVerifier.Verify` separately parses `jkt-jwt` and also never checks `crit` (`NamingTokenVerifier.cs:11-29`). A JWT with protected header `crit:["unknown"], unknown:true` can therefore pass normal signature verification if the signature is valid. #common-verification says verify per RFC 7515/#RFC7519 (L2311-L2313); RFC 7515 §4.1.11 makes a JWS invalid when any critical extension header is not understood/supported, and also constrains `crit` shape, duplicates, empty lists and listed names.
- A01-H01 is verified. For `jwt` and `self-jwt`, `DefaultSignatureKeyResolver.ResolveAssertionAsync` calls `TokenVerifier.ValidateStructure` and then unconditionally requires `iss`, `dwk` and `kid` before invoking a registered `ISignatureTokenVerifier` (`DefaultSignatureKeyResolver.cs:72-83`). `ISignatureTokenVerifier` can only verify with a key supplied by the resolver (`ISignatureTokenVerifier.cs:6-12`), so an application-specific verifier cannot supply the issuer key for a conforming `jwt` assertion where `iss` or `dwk` is absent. Signature-Key §3.8 says `jwt` assertions SHOULD contain `iss`/`dwk`, and if either is absent the verifier MUST obtain the issuer key through an application-specific mechanism (L1172-L1191). `self-jwt` is different: §3.9 requires `iss`, `dwk` and `kid` (L1251-L1311), so its current metadata-key requirement is correct.
- A01-M02 is verified. Built-in AAuth tokens use `TokenVerifier.Verify`, whose `exp` check has no tolerance (`TokenVerifier.cs:140-151`), but generic/companion `jwt` and `self-jwt` assertions use `NamingTokenVerifier.ValidateTime` with the configured clock skew (`DefaultSignatureKeyResolver.cs:72-73`). `ValidateTime` accepts until `expiresAt <= now - skew` (`NamingTokenVerifier.cs:35-42`), and the default verification skew is 30 seconds (`AAuthVerificationOptions.cs:56-60`). `jkt-jwt` also passes `_tokenVerifier.ClockSkew` into `NamingTokenVerifier.Verify` (`DefaultSignatureKeyResolver.cs:46-49`). This contradicts #common-verification L2315-L2318 and Signature-Key §3.8/§3.9 L1172/L1309: `exp` must be in the future / expired assertions are rejected, with no exp tolerance.
- A03-HIGH-001 is verified. `ChallengeOptions.AllowedSignatureKeySchemes` is a second, post-verification scheme policy (`ChallengeOptions.cs:46-51`). When it rejects, `AAuthChallengeMiddleware` returns `401` with only `AAuth-Error` (`AAuthChallengeMiddleware.cs:85-90`), not `Signature-Error: error=unsupported_scheme` and not `Accept-Signature-Scheme`. #verification step 4 and #scheme-rejection require the unsupported-scheme 401 shape and accepted-scheme header (L2247, L2256-L2267). The duplication also conflicts with the existing single verification policy, `AAuthVerificationOptions.AcceptedSchemes` (`AAuthVerificationOptions.cs:14`, `:49-54`).
- A19-HIGH-001 is verified. The main verification writer is correct (`AAuthVerificationMiddleware.cs:400-408`), and `AAuthProblemDetails` has a private bodyless `SignatureErrorResult` (`AAuthProblemDetails.cs:72-79`), but several AAuth paths still return 401 problem bodies through `AAuthProblemDetails.Create` with no `Signature-Error`: mapped authorization endpoint without verification (`AAuthApplicationBuilderExtensions.cs:157`), AS `invalid_carrier` / wrong `jwks_uri` carrier (`AAuthAccessServerEndpoints.cs:186`, `:256`), revocation endpoint without verification (`RevocationEndpoint.cs:141`), and resource-managed poll without verification (`AAuthInteractionEndpointExtensions.cs:53`). #error-responses L2565-L2570 says the `Signature-Error` header, not the body, is the machine-readable carrier for 401 authentication errors from AAuth endpoints. Requirement challenges that intentionally use `AAuth-Requirement` are not this finding.
- A21-TLS-01 is verified. `AAuthHttpTransport.CreateHandler` creates the SDK-owned `SocketsHttpHandler` and configures redirects, proxies, header size, timeouts, pooled lifetime and DNS pinning, but never sets `SslOptions.EnabledSslProtocols` (`AAuthHttpTransport.cs:63-80`). It admits HTTPS URLs via egress policy, but on a platform that still permits TLS 1.0/1.1 the handler can negotiate below the #tls-requirements floor (L2933-L2936). Injected handlers already require a declared `AAuthTransportContract`, whose docs currently mention egress/pinning/proxy obligations but not TLS version (`AAuthHttpTransport.cs:10-16`; `samples/README.md:71-74`).

## Recommendation

Implement candidate 2.

The SDK should understand no critical JOSE extensions today. Therefore any non-empty, well-formed `crit` list is rejected as `invalid_jwt`; malformed `crit` values, empty lists, duplicate names, names absent from the protected header, and registered JWS/JWA names in `crit` are also rejected. That is fail-closed for attackers who mark semantics critical to bypass validation, and honest peers using a real extension receive a deterministic `invalid_jwt` until the SDK explicitly adds that extension to an internal allow-list and actually processes it.

Replace `ISignatureTokenVerifier` with a context-based companion seam. The resolver still performs spec mechanics (parse, `typ`, JOSE `crit`, `exp`, metadata discovery when `iss` and `dwk` are both present), but for `jwt` with either claim absent it calls the registered companion to obtain the issuer key through an application-specific mechanism before signature verification. The companion must return the issuer `IAAuthKey` and then validate application claims using a verification context; the SDK still checks the returned key's algorithm against the JOSE `alg` before accepting. This closes the conforming `jwt`/no-metadata path without letting arbitrary companions bypass HTTP-signature key extraction. `self-jwt` continues to require `iss`, `dwk` and `kid` because §3.9 makes those mandatory.

Split time validation so `exp` always uses zero skew, while the existing `ClockSkew` remains only the optional future-`iat` window. This preserves built-in behavior and removes the 30-second replay grace from generic/companion assertions and `jkt-jwt`.

Remove `ChallengeOptions.AllowedSignatureKeySchemes`. The verification middleware is the single step-4 scheme gate; AAuth auth-token resources should keep `AAuthVerificationOptions.AcceptedSchemes = [AAuthConstants.Schemes.Jwt]`, while generic Signature Keys endpoints opt into `AAuthVerificationOptions.Generic()` only where they genuinely accept those schemes. If a request's scheme is not accepted, `AAuthVerificationMiddleware.WriteFailure` already emits `Signature-Error` plus `Accept-Signature-Scheme`; move that writing code into the shared helper described below so the behavior stays uniform.

Add a single internal signature-failure result/writer in `AAuthProblemDetails`, e.g. `SignatureFailure(SignatureErrorCode code, acceptedSchemes: ..., acceptedAlgorithms: ..., requiredInput: ...)`, and make `AAuthVerificationMiddleware.WriteFailure`, challenge scheme failures that remain after refactoring, AS carrier checks, revocation misconfiguration checks, and resource-managed poll verification checks use it. Requirement challenges keep `AAuth-Requirement`; 403 policy denials keep problem bodies and MUST NOT add signature headers per Signature-Key §5.3 L1938-L1944.

Pin the SDK-owned transport with `SocketsHttpHandler.SslOptions.EnabledSslProtocols = SslProtocols.Tls12 | SslProtocols.Tls13`. Extend `AAuthTransportContract.EnforcesEgressPolicy` documentation to include TLS 1.2-or-later, because the SDK cannot inspect opaque injected handlers; tests and samples using `AttachPolicy(..., EnforcesEgressPolicy)` must state that caller obligation.

## Public API delta

- **Changed:** `ISignatureTokenVerifier` becomes a breaking, context-based seam. Proposed shape: `ValueTask<IAAuthKey> ResolveIssuerKeyAsync(SignatureTokenIssuerKeyContext context, CancellationToken)` for `jwt` app-specific issuer keys, and `ValueTask<TokenVerifier.VerifiedToken> VerifyAsync(SignatureTokenVerificationContext context, CancellationToken)` for application claim validation after the SDK has an issuer key. Contexts carry `Jwt`, `Header`, `Payload`, `Scheme`, `TokenType`, optional `Issuer`/`Dwk`/`Kid`, `TokenVerifier`, `IServiceProvider?`, and any discovered `IssuerKey`. Events' subscribe/event verifiers update to the new methods.
- **Added:** public support records/classes needed by that interface: `SignatureTokenIssuerKeyContext` and `SignatureTokenVerificationContext` (or one context plus a result) in `AAuth.HttpSig`. Use `AAuthConstants.Schemes` / `AAuthConstants.TokenTypes` in examples rather than string literals.
- **Removed:** `ChallengeOptions.AllowedSignatureKeySchemes`; callers configure `AAuthVerificationOptions.AcceptedSchemes` only. This intentionally breaks divergent post-verification filtering per C1.
- **Internal/no ApiSurface:** `AAuthProblemDetails` signature-failure helper can be `internal` unless a public reuse case is desired; TLS pinning and JOSE `crit` validation do not require new public members. `AAuthTransportContract.EnforcesEgressPolicy` XML/doc text changes but not its value.

## Wire effect

- JWTs in `Signature-Key` or parameter-token verification with any unsupported/malformed `crit` protected header now fail as `401 Signature-Error: error=invalid_jwt` when carried in `Signature-Key`, or the corresponding token-parameter error when verified as a body parameter. Previously they could succeed.
- Companion `jwt` assertions with valid app-specific issuer keys and no `iss`/`dwk` can now succeed; without a registered/resolving companion they fail closed. `self-jwt` missing `iss`/`dwk`/`kid` continues to fail.
- Generic/companion `jwt`, `self-jwt`, and `jkt-jwt` assertions with `exp <= now` now fail immediately as `expired_jwt`; the 30-second `ClockSkew` no longer extends expiration. Future `iat` still uses the configured window and can return `clock_skew`.
- Scheme rejection happens at verification: `401 Signature-Error: error=unsupported_scheme` plus `Accept-Signature-Scheme: <accepted>` instead of the challenge-layer `401` + `AAuth-Error` body/header.
- AS token endpoints that receive the wrong `Signature-Key` carrier change from `401 application/problem+json {"error":"invalid_carrier"|"invalid_request"}` to `401 Signature-Error: error=unsupported_scheme` with `Accept-Signature-Scheme: jwks_uri`. Other missing/invalid signature 401s likewise become bodyless `Signature-Error` responses. 403 problem bodies are unchanged and remain without `Signature-Error`.
- SDK-owned HTTPS clients no longer negotiate TLS 1.0/1.1. A peer that only supports legacy TLS now fails during connection/handshake before any AAuth metadata/JWKS/token request is processed.

## Implementation sketch

1. Add `internal static void ValidateJoseProtectedHeader(JsonObject header)` in `TokenVerifier` or a new `JoseHeaderValidator`. It validates `crit` per RFC 7515 §4.1.11 and rejects because the SDK's understood-critical set is empty. Call it from `TokenVerifier.ValidateStructure` before claim checks and from `NamingTokenVerifier.Verify` before checking `typ`/`jwk`.
2. Split assertion-structure validation so `jwt` companions do not require `iss`/`dwk`/`kid` when metadata discovery is not possible. Keep built-in AAuth tokens and `self-jwt` on the strict path. Ensure `jwt` still requires `exp`, `typ` policy, and `cnf.jwk`; require `kid` only for metadata/JWKS discovery.
3. Replace `ISignatureTokenVerifier` and update `DefaultSignatureKeyResolver` constructors created in `AAuthApplicationBuilderExtensions.cs:55-57`, `AAuthEndpointExtensions.cs:126-127`, `AAuthResourceServiceCollectionExtensions.cs:88-89`, `EventsProtocol.cs:29`, and tests. Pass `IServiceProvider?` to the resolver when constructed from DI so the context follows C4.
4. In `DefaultSignatureKeyResolver.ResolveAssertionAsync`: find the companion by `Scheme`/`TokenType`; for built-in `jwt`, require `iss`/`dwk`/`kid` and discover as today; for companion `jwt` with both `iss` and `dwk`, discover and then call companion verification; for companion `jwt` with either missing, call `ResolveIssuerKeyAsync`; for `self-jwt`, require metadata claims and `kid`. Map companion key failures to `AAuthVerificationException` with `unknown_key` or `invalid_jwt` as appropriate.
5. Change `NamingTokenVerifier.ValidateTime` to take separate `expirationSkew` and `issuedAtWindow`. Pass `expirationSkew: TimeSpan.Zero` from `DefaultSignatureKeyResolver` for all assertion schemes and from `NamingTokenVerifier.Verify` for `jkt-jwt`; pass `_tokenVerifier.ClockSkew` only as `issuedAtWindow`.
6. Delete `AllowedSignatureKeySchemes` from `ChallengeOptions` and remove `AAuthChallengeMiddleware` lines 85-90. Update resource builder/middleware setup and tests that copied this value into verification; the only configured scheme list is `AAuthVerificationOptions.AcceptedSchemes`.
7. Add `AAuthProblemDetails.SignatureFailure` / `WriteSignatureFailureAsync` internally and have `AAuthVerificationMiddleware.WriteFailure` delegate to it. Replace 401 `AAuthProblemDetails.Create` calls at `AAuthApplicationBuilderExtensions.cs:157`, `AAuthAccessServerEndpoints.cs:186`/`:256`, `RevocationEndpoint.cs:141`, and `AAuthInteractionEndpointExtensions.cs:53` when the cause is missing/wrong signature authentication. Do not change `ChallengeAAuth` / requirement challenges or 403 policy errors.
8. In `AAuthHttpTransport.CreateHandler`, add `using System.Security.Authentication;` and set `SslOptions = new() { EnabledSslProtocols = SslProtocols.Tls12 | SslProtocols.Tls13 }` on the owned `SocketsHttpHandler`. Update XML comments for `AAuthTransportContract.EnforcesEgressPolicy` and docs for injected transports.
9. Add constants usages in new code (`AAuthConstants.Schemes.Jwt`, `AAuthConstants.Schemes.SelfJwt`, `AAuthConstants.Headers.SignatureKey`) rather than new protocol string literals, per C7.

## Dependencies and conflicts with other Rnn

- R03 also touches `AAuthChallengeMiddleware`, authorization endpoint behavior, and requirement responses. Coordinate so R14's 401 signature-failure helper is used for authentication failures, while R03-owned person-token requirement challenges keep `AAuth-Requirement` and do not become signature errors.
- R11/R19 own broader token/polling error-code cleanup. R14 should only convert 401 authentication/signature failures to `Signature-Error`; it must not relabel 400/403/410 token or polling problem bodies.
- R17 (Events) must update its `ISignatureTokenVerifier` implementations and tests in the same cutover because the interface change is intentionally non-compatible.
- R13 (HTTP-signature producer) is adjacent but not blocking: scheme labels and covered components are unaffected by this design.
- R01 resource identity and R14 scheme policy both touch high-level verification setup. The invariant should be: resource identity comes from role options; accepted signature schemes come from `AAuthVerificationOptions` only.

## Open questions (with proposed default)

1. Should any JOSE critical headers be understood today? **Default:** none. Reject all `crit` until an implementation actually processes the named extension; do not silently ignore even registered-but-irrelevant values.
2. Should `ISignatureTokenVerifier.ResolveIssuerKeyAsync` be called when `iss` and `dwk` are present? **Default:** no; use standard metadata discovery first for interoperability and cache behavior, then let the companion validate claims. App-specific key resolution is only for `jwt` when either claim is absent.
3. What error should a companion use when its app-specific issuer key is absent? **Default:** throw `AAuthVerificationException(SignatureErrorCode.UnknownKey, ...)` if the issuer/key identity is known but not found; otherwise `InvalidJwt` for malformed/unusable assertions. Document this in the interface XML.
4. Should `AAuthProblemDetails.SignatureFailure` be public? **Default:** keep it internal for this cutover to minimize API surface; expose later only if host applications need to produce conforming Signature-Key failures outside SDK endpoints.
5. How can TLS pinning be tested portably? **Default:** prefer a real TLS 1.1 loopback handshake test when the platform supports configuring it; otherwise use a focused unit/reflection assertion on the SDK-owned handler plus contract documentation tests for injected handlers.
