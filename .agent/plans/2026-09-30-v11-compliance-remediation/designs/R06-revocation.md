# R06 — Revocation ordering, pending dependencies, and scope step-up

Findings: SDK-05/A20-001, A20-002, A20-003, ASL "[Phase 10a] Open: scope step-up answers 403". Spec: #requirement-auth-token L628-L642, #token-endpoint-error-codes L2580-L2616, #polling-error-codes L2617-L2640, #revocation-cascade L2747-L2758, #presenting-a-revoked-token L2760-L2768. Files read: `src/AAuth/Person/AAuthPersonServerEndpoints.cs`, `src/AAuth/Access/AAuthAccessServerEndpoints.cs`, `src/AAuth/Server/AuthTokenResponse.cs`, `src/AAuth/Server/AAuthProblemDetails.cs`, `src/AAuth/Server/AAuthRevocationService.cs`, `src/AAuth/Server/RevocationEndpoint.cs`, `src/AAuth/Server/IJtiStore.cs`, `src/AAuth/Server/InMemoryJtiStore.cs`, `src/AAuth/Server/DeferredState.cs`, `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs`, `src/AAuth/Server/Challenge/AAuthChallengeMiddleware.cs`, `src/AAuth/Server/Authorization/AAuthScopeHandler.cs`, `src/AAuth/Server/Endpoints/AAuthEndpointExtensions.cs`, `src/AAuth/DependencyInjection/AAuthResourceServiceCollectionExtensions.cs`, `src/AAuth/Headers/AAuthRequirementHeader.cs`, `src/AAuth/Person/IPersonPendingStore.cs`, `src/AAuth/Access/IAccessPendingStore.cs`, relevant tests/docs listed below.

## Problem restated (verified)

- SDK-05/A20-001 is still present. `VerifyPairAsync` rejects a locally revoked resource token before accepting the request (`Person/AAuthPersonServerEndpoints.cs:374-378`), and `RegisterSourcesAsync` registers the agent/presented source tokens (`:397-405`), but the four-party background task calls `federation.FederateAsync(...)` with `fedRequest.PresentedToken` before re-checking those sources (`:1447-1456`). `AuthTokenResponse.CreateTrackedAsync` detects a revoked source only after the AS has received the `presented_token`. This violates #revocation-cascade L2752 and #presenting-a-revoked-token L2764-L2767: the PS must not present a revoked person token to an AS and must reject a token request whose parameter token is revoked as the right revoked error.
- A20-002 is still present on pending polls. The PS pending GET checks mission termination and only withdrawn resource tokens (`Person/AAuthPersonServerEndpoints.cs:619-640`), then returns `202` for awaiting clarification/federation or pending consent (`:652-683`). The AS pending GET checks only withdrawn resource tokens before `AwaitingClarification`/`Pending` returns (`Access/AAuthAccessServerEndpoints.cs:453-490`). `AuthTokenResponse.MintTrackedAsync` checks all source keys (`AuthTokenResponse.cs:56-63`), but only when an approved entry mints/returns, so revoked upstream or agent-token dependencies can stay `202` while pending. This misses #polling-error-codes L2624 and #presenting-a-revoked-token L2766-L2767 (`revoked`, `detail` says which).
- A20-003 is still present. Resource verification returns `401 Signature-Error: error=revoked_jwt` when the inventory says the presented JWT's `(iss,jti)` is revoked (`AAuthVerificationMiddleware.cs:260-270`), but `WriteFailure` only writes `Signature-Error` and Accept-Signature hints (`:395-410`). For a revoked auth token it omits the recommended `AAuth-Requirement: requirement=person-token`, contrary to #presenting-a-revoked-token L2762-L2765.
- The scope step-up open item is real. `RequireAAuth(scope:)` attaches `AAuthScopeRequirement` (`AAuthEndpointExtensions.cs:34-56`); `AAuthScopeHandler` only calls `Succeed` when an authorized token contains the scope (`AAuthScopeHandler.cs:24-39`), so ASP.NET authorization emits `403`. Meanwhile `AAuthChallengeMiddleware` always passes any auth token through before examining endpoint scope (`AAuthChallengeMiddleware.cs:119-124`), even though #requirement-auth-token L640-L642 explicitly allows `requirement=auth-token` with a new resource token when the existing auth token lacks needed authorization. The ASL 10a ruling left this open, not final.

## Candidate fixes

| # | Approach | Pros | Cons | Spec fit | API-surface fit (C1–C13) |
|---|---|---|---|---|---|
| 1 | Add point fixes: check `entry.SourceTokens` before `FederateAsync`, add source checks at pending GET starts, add person-token header for revoked auth tokens, and keep scope 403. | Small patch; few public changes. | Duplicates source/revocation rules; still loses `detail` fidelity because pending entries store only `TokenKey`; does not close POST/clarification paths; keeps known step-up incompatibility. | Partial: fixes the observed SDK-05 path but not the general "before presentation" invariant or L640 step-up. | Weak C6/C11: mechanics remain scattered; no typed failure seam. |

| 3 | Add proactive cascade-to-pending indexing: `AAuthRevocationService.WalkAsync` also queries every PS/AS pending store and marks/cancels entries whose sources include the revoked token; keep lazy checks as backup. | Immediate pending termination; background federation cancellation is prompt. | Couples generic revocation service to role-specific stores or adds a new public persistence contract; default in-memory can comply, but custom stores become fail-open unless they implement the new index; larger blast radius. | Strong if combined with #2; alone still needs outbound preflight to avoid races. | Mixed: C11 likes one cascade engine, but C2/C4 require a clean DI seam; public API impact is larger. |

## Recommendation

Adopt candidate 2 now, with a narrow piece of candidate 3 only as an optional internal notification from role endpoints: pending handlers and every outbound action must be correct even if no proactive revocation callback fires. The invariant should be: **check recorded source dependencies, then act, for every operation that would present a token outbound or return a grant**.

Concretely add an internal `AAuthSourceAuthorization`/`AAuthSourceGuard` in `src/AAuth/Server` that accepts `IReadOnlyCollection<TokenRegistration>` (or a new `SourceDependency` record with `TokenRegistration` plus a display label) and returns a typed result: live; revoked with `TokenCredential?`/label; expired with label. It exposes:

- `CheckAsync(inventory, sources, ct)` for pending GET/POST before returning `202`, invoking policy, accepting clarification, or resuming;
- `CheckThenActAsync(inventory, sources, pendingEntry, action, ct)` for four-party `FederateAsync` and local `Mint` callbacks;
- helpers to render fresh token-endpoint failures (`revoked_presented_token`, `revoked_upstream_token`, etc.) and pending failures (`403 {"error":"revoked","detail":"The upstream token was revoked."}`).

For adversarial races: the guard must run immediately before `FederateAsync`, before each AS clarification/claims callback that sends the stored presented/upstream context, and inside `AuthTokenResponse.MintTrackedAsync` before the mint delegate. For local minting, keep `RegisterGrantAsync` after mint because `InMemoryJtiStore.RegisterGrantAsync` atomically rejects revoked/expired ancestors before the token is returned (`InMemoryJtiStore.cs:106-134`). For federation, also cancel the entry's `FederationCancellation` and mark its lifecycle delivered when a guard failure is observed; if a revocation arrives after the last preflight but while the HTTP request is in flight, the cancellation token passed to `FederateAsync` is the only enforceable local control. Document that distributed stores must make `IsRevokedAsync` strongly consistent for the issuer's own revocation endpoint; otherwise no SDK can satisfy immediate revocation.

Resolve the ASL step-up open item in favor of the spec: a valid auth token that lacks the endpoint's required **scope** should receive `401 AAuth-Requirement: requirement=auth-token; resource-token="..."` with a new resource token naming the existing auth token as `presented_token`. Keep `403` for a valid auth token that has the required scope but fails role/application policy, and for non-AAuth/hwk cases with no token upgrade path.

## Public API delta

- **Changed**: `PersonPendingEntry.SourceTokens` and `AccessPendingEntry.SourceTokens` should store typed source dependencies (`IReadOnlyList<TokenRegistration>` or `IReadOnlyList<AAuthSourceDependency>`) instead of bare `TokenKey`, so pending poll errors can name `resource`, `presented`, `upstream`, or `agent` and the same collection can feed `AuthTokenResponse.CreateTrackedAsync`. This is an ApiSurface break but allowed by C1; do not add compatibility aliases.
- **Added internal**: `AAuthSourceGuard`/`AAuthSourceAuthorization` and a small `PendingRevocationResult` renderer. Keep it internal unless tests or custom stores force exposure.
- **No new high-level app API** for step-up. Existing `.RequireAAuth(scope:)`, `AddAAuthScopePolicy`, `UseAAuth`, and `AAuthRequirementHeader.FormatAuthToken/FormatPersonToken` are sufficient.
- **Optional public surface if persistence requires it**: if the implementation cannot change pending entries without an external contract, add a single public `AAuthSourceDependency` record in `AAuth.Server` rather than strings/dictionaries, preserving C7 typed protocol values.

## Wire effect

- Four-party deferred approval after the stored `presented_token`, upstream token, resource token, or starting agent token is revoked returns terminal polling `403` with `application/problem+json`, `error="revoked"`, and a `detail` naming the dependency, instead of federating or continuing `202`.
- Fresh token endpoint requests still return token-parameter errors from #token-endpoint-error-codes: `revoked_resource_token`, `revoked_presented_token`, `revoked_upstream_token`, or `revoked_subagent_token` as applicable. Do not collapse those into polling `revoked` unless the request is already pending.
- Revoked auth token in `Signature-Key` remains `401 Signature-Error: error=revoked_jwt`; when the token type is `aa-auth+jwt`, add `AAuth-Requirement: requirement=person-token`. Do **not** include `resource-token` on this response.
- Scope step-up changes a valid narrower auth token on `.RequireAAuth(scope:)` from `403` to `401` with `AAuth-Requirement: requirement=auth-token; resource-token="..."`. The resource token should carry the endpoint scope and should bind to the existing auth token's `jti`, `ps`, `sub`, `mission_s256`, tenant/account, and agent confirmation key via existing `BuildResourceTokenAsync` auth-token support (`AAuthChallengeMiddleware.cs:141-188`).

## Implementation sketch

1. Add `AAuthSourceDependency` or change pending `SourceTokens` to `TokenRegistration` in `IPersonPendingStore.cs` and `IAccessPendingStore.cs`. Populate with credentials at source verification time: agent token (`TokenCredential.Agent`, already in `issuance.SourceTokens`), resource token, presented token, upstream token, subagent token. Stop calling `Keys(...)` when parking pending entries (`Person/AAuthPersonServerEndpoints.cs:1036-1042`, `:1234-1237`; `Access/AAuthAccessServerEndpoints.cs:341-380`).
2. Add `AAuthSourceGuard.CheckAsync` and renderers in `src/AAuth/Server`. Use `inventory.IsRevokedAsync(source.Token)` for revocation; use `ExpiresAt <= now` for expiration. Credential-to-detail mapping should be typed: resource/presented/upstream/subagent/agent. For fresh requests, reuse `AAuthProblemDetails.TokenFailure`/`SourceRevoked`; for pending, render only polling codes (`revoked`, `expired`) and `detail`.
3. Refactor `AuthTokenResponse.CreateTrackedAsync`/`MintTrackedAsync` to take `IReadOnlyCollection<TokenRegistration>` on the main path, call the guard immediately before `mint`, and keep `RegisterGrantAsync` after mint. Retain a small internal adapter only where a caller truly has no credential metadata; prefer eliminating `IReadOnlyCollection<TokenKey>` overloads if ApiSurface allows the single cutover.
4. In `HandleFederatedAsync` background `Task.Run` (`Person/AAuthPersonServerEndpoints.cs:1447-1456`), call the guard immediately after `RequireConsentAsync` and before `federation.FederateAsync`. On failure, set `entry.Error="revoked"` (or `expired`), `entry.ErrorStatus=403`/`408`, `entry.Status=Denied`, cancel `FederationCancellation`, and do not call the AS. Also call the guard in `OnClarificationRequired`, `OnClaimsRequired`, and `ApplyReplacementAsync` before presenting stored/replacement tokens to the AS.
5. At the start of PS pending GET and POST lifecycle bodies (`Person/AAuthPersonServerEndpoints.cs:619-700`) and AS pending GET/POST lifecycle bodies (`Access/AAuthAccessServerEndpoints.cs:453-522`), call the guard before mission/resource-only checks and before returning `202`. On failure, cancel `entry.FederationCancellation` for PS entries, call `entry.Lifecycle.Cancel()` only after the terminal result is selected or rely on `DeferredState.ExecuteAsync` to mark delivered for `403`/`408`, and return the polling error with detail.
6. Keep `WithdrawnResourceAsync` for the unseen-resource-token case where the entry may not have registered the resource token dependency yet, but make it delegate to the same guard/rendering when the resource token is in the dependency list. This avoids two divergent `revoked` details.
7. Teach `AAuthVerificationMiddleware.WriteFailure` enough context to know token type on revocation. The simplest internal change is to pass `parsedInfo`/`typ` (or a `bool revokedAuthToken`) into `WriteFailure` at `AAuthVerificationMiddleware.cs:268`; if `code == RevokedJwt` and `typ == AuthTokenBuilder.TokenType`, add `AAuthRequirementHeader.FormatPersonToken()`.
8. Move scope step-up before ASP.NET authorization denial: in `AAuthChallengeMiddleware`, for `tokenType == AuthToken` look at `context.GetEndpoint()?.Metadata.GetMetadata<AAuthEndpointRequirement>()?.Scope` (or `ChallengeOptions.DefaultScopes` as already set by `UseAAuth` at `AAuthEndpointExtensions.cs:196-205`). If the verified auth token's `AAuthVerificationResult.Scopes` lacks that scope, call `IssueChallenge(context, presented, parsedInfo)` instead of `_next`. If no scope is configured or the token already has it, pass through. Leave `AAuthScopeHandler` as the final authorization guard for named policies and non-`UseAAuth` pipelines.
9. Update logging/diagnostics tags only if existing tests assert the 403 path; otherwise no observability contract change.

## Dependencies and conflicts with other Rnn

- R05 (upstream provenance) should share the same `TokenRegistration` dependency model so upstream-token revocation/provenance failures are not implemented twice.
- R07 (federation collapse/402/dwk pinning) touches `AccessServerClient.FederateAsync` and four-party callbacks; coordinate the preflight guard so it wraps the final outbound call after any R07 request shaping.
- R11 (deferred polling and error codes) owns `DeferredState.Missing`/`invalid_code`/`Retry-After`; this design only adds `revoked`/`expired` source checks and should not rework the broader polling code catalogue.
- R03 (authorization endpoint/access-mode gating) may touch `AAuthChallengeMiddleware` and `RequireAAuth`; scope step-up should be implemented there, not in a separate ASP.NET result handler unless R03 centralizes all challenge responses.
- C11 is satisfied if revocation remains inventory-first and all pending/outbound paths consult the same inventory through the guard. A proactive pending index can be added later, but correctness must not depend on it.

## Open questions (with proposed default)

1. **Should pending stores receive proactive revocation callbacks?** Default: no public callback in this remediation; use lazy poll checks plus pre-outbound guards. Add an internal notification only for in-memory role stores if it falls out naturally, but do not make conformance depend on it.
2. **Should `AddAAuthScopePolicy` named policies step up too?** Default: only `.RequireAAuth(scope:)`/`UseAAuth` step up, because only endpoint metadata/challenge options know how to mint a resource token. Named policies without challenge middleware remain `403` and should be documented as lower-level authorization.
3. **Should missing roles step up?** Default: no. Step-up is scope-specific per #requirement-auth-token L640; roles/claims denied by ASP.NET or app policy remain `403` unless a later spec ruling maps them to claims/clarification flows.
4. **Is changing `SourceTokens` from keys to registrations too large an ApiSurface break?** Default: accept the break under C1; the alternative cannot reliably produce #polling-error-codes L2624 `detail`.
