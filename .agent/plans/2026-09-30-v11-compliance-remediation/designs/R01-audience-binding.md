## Problem restated (verified)

The finding is verified in current code. `UseAAuthVerification()` builds `AAuthVerificationOptions` from DI and the caller delegate but does not copy the DI-registered resource issuer into `ResourceIdentifier` (`AAuthApplicationBuilderExtensions.cs:39-48`). `AAuthVerificationMiddleware` then verifies auth and person JWT carriers by choosing `_options.ResourceIdentifier ?? token.payload["aud"]` (`AAuthVerificationMiddleware.cs:237-248`), so with the public low-level middleware's default `ResourceIdentifier = null` (`AAuthVerificationOptions.cs:36-41`) the expected audience is attacker-controlled and the `aud` check is a tautology. That reaches `AAuthAuthenticationHandler` and any `HttpContext.GetAAuthVerification()` consumer as an `Authorized`/person-identified result even when the token was minted for another resource (`AAuthVerificationMiddleware.cs:320-331`; `AAuthAuthenticationHandler.cs:76-125`; `AAuthHttpContextExtensions.cs:25-31`).

The spec requires the opposite: person-token verification must verify `aud` matches the resource's own identifier (#person-token-verification L913-L918); auth-token request-context binding must verify `aud` matches the resource's own identifier (#auth-token-verification L1802-L1815); common verification only establishes JWT trust and says token-specific checks are added by each token section (#common-verification L2311-L2326). The spec also warns that person and PS-issued auth tokens can share `iss`, `dwk`, `aud`, `sub`, and `cnf`, so implementations must check `typ` before acting (#person-token-not-authorization L2894-L2896); this finding is specifically the remaining audience-binding gap after `typ` is read.

Safe paths are partially present but incomplete. `MapAAuthResource()` sets `ResourceIdentifier = metadataOptions.Issuer` for verification and challenge (`AAuthApplicationBuilderExtensions.cs:215-245`). Endpoint-oriented `UseAAuth()` derives `resourceIdentifier = opts.ResourceIdentifier ?? resourceMetadata?.Issuer`, fails closed for `RequireAuthToken` endpoints without one, and passes it to middleware/challenge (`AAuthEndpointExtensions.cs:130-200`). `AddAAuthResource()` already requires `AAuthResourceOptions.Issuer` and publishes it as `AAuthResourceMetadataOptions.Issuer` (`AAuthResourceServiceCollectionExtensions.cs:38-53`, `:97-125`; `AAuthResourceOptions.cs:12-18`). However, the documented `docs/server/multi-scheme-verification.md:36-44` snippet uses `AddAAuthResource(...Issuer...)` followed by bare `app.UseAAuthVerification()`, which currently remains unsafe because no post-configure derives the verification audience.

PS/AS internal uses were checked. `MapAAuthPersonServer()` installs `UseAAuthVerificationCore(new AAuthVerificationOptions { AcceptedSchemes = ["jwt"], RequireBodyCoverage = true, ... })` (`AAuthPersonServerEndpoints.cs:207-216`), but its token endpoints require the `Signature-Key` carrier to be an agent token before processing (`AAuthPersonServerEndpoints.cs:323-355`). Presented/upstream person or auth tokens are body parameters verified separately with explicit expected audiences (`issuer` or the resource-token audience) via `VerifyPairAsync`/`VerifyPresentedTokenAsync` (`AAuthPersonServerEndpoints.cs:363-381`). `MapAAuthAccessServer()` uses `AcceptedSchemes = ["jwks_uri"]` for PS callers and verifies `parsed.Identifier == GetAAuthVerification()?.Issuer` (`AAuthAccessServerEndpoints.cs:153-176`); it does not use the middleware to accept person/auth JWT carriers. Therefore PS/AS middleware do not need a resource `aud` for normal operation, but if a person/auth JWT is mistakenly presented through the PS `jwt` carrier path it must now fail closed instead of self-audiencing.

## Candidate fixes

| # | Approach | Pros | Cons | Spec fit | API-surface fit (C1–C13) |
|---|---|---|---|---|---|
| 1 | Only remove the fallback: middleware rejects auth/person JWT carriers when `ResourceIdentifier` is null; callers must set it manually. | Smallest code change; impossible to accept a token against its own `aud`. | Leaves `AddAAuthResource(...Issuer...)` + bare `UseAAuthVerification()` failing; DOC-03 snippet must become more verbose; does not honor C5 identity-once. | Correct fail-closed behavior, but no automatic resource identity derivation. | C1 good; C5 weak; C2/C3 weaker because high-level DI identity is ignored by a low-level building block. |
| 2 | Derive `AAuthVerificationOptions.ResourceIdentifier` from `AddAAuthResource(options.Issuer)` with DI post-configuration, and also remove the middleware fallback. Explicit options can still override. | Fixes the unsafe documented pattern; keeps manual/custom pipelines possible; fail-closed if no resource identity exists; no public API churn. | Requires tests for DI post-configure ordering; a caller that explicitly sets `ResourceIdentifier = null` still gets request-time 401 for auth/person tokens, which is a behavior change. | Best: accepted auth/person tokens are always checked against a resource-owned identifier; no token-supplied expected audience. | Best: C1 no compat shim, C3 uses options/post-configure, C5 derives resource identifier once from issuer, C12 respects single resource instance. |
| 3 | Change public surface to require a resource identifier for `UseAAuthVerification` or split agent-only vs resource-token verification options. | Compile-time pressure for app authors; clearer low-level intent. | Public API break across docs/tests/samples; still needs a separate agent-only story; does not leverage existing `AddAAuthResource` identity. | Can be correct, but over-constrains generic and agent-token-only verification. | C1 allows cutover, but C2/C5 worse than deriving from the registered role; unnecessary API blast radius. |

## Recommendation

Implement candidate 2.

`AddAAuthResource` should register a default-name post-configure for `AAuthVerificationOptions` that sets `ResourceIdentifier` to the already-required `AAuthResourceOptions.Issuer` only when the verification options did not set one. `AAuthOptionsResolver.Create()` already applies `IConfigureOptions<T>` and `IPostConfigureOptions<T>` before the per-pipeline delegate (`AAuthOptionsResolver.cs:8-21`), matching the current middleware-options-from-DI convention in the API-surface log (ASL L458-L463). Because the resource role is intentionally single-instance and exposes `IOptions<AAuthResourceOptions>` (C12 / ASL L1057-L1063), this should be a single resource-role default, not named options.

Then change `AAuthVerificationMiddleware` so auth-token and person-token verification require an independently configured expected audience. Do not read `aud` from the token to choose the expected audience. If `_options.ResourceIdentifier` is null/empty when `typ` is `aa-auth+jwt` or `aa-person+jwt`, return a signature failure (recommended `401` with `Signature-Error: error=invalid_request` and `AAuth-Error` detail such as “AAuthVerificationOptions.ResourceIdentifier is required to verify aa-auth+jwt/aa-person+jwt; configure AddAAuthResource(options.Issuer) or set ResourceIdentifier.”). If it is set, pass exactly that value to `VerifyAuthToken`/`VerifyPersonToken`; wrong-audience tokens continue to fail as `invalid_jwt` through `TokenVerifier`.

This closes the adversarial case: a token minted for `https://resource-a.example` replayed to `https://resource-b.example` no longer supplies its own expected audience. With `AddAAuthResource(o => o.Issuer = "https://resource-b.example")` plus bare `UseAAuthVerification()`, post-configure supplies `https://resource-b.example`; without any resource identity, the auth/person JWT is rejected before a principal or `AAuthVerificationResult` is exposed. Agent-token and generic non-JWT schemes remain usable without `ResourceIdentifier` because they have no resource `aud` check in these spec sections.

## Public API delta

No public member additions, removals, or signature changes. `AAuthVerificationOptions.ResourceIdentifier` stays public for custom pipelines, intermediaries, tests, and apps that intentionally verify for an identifier other than the DI resource issuer. The public behavioral contract changes:

- old: `ResourceIdentifier = null` meant “auth/person audience validation is skipped by comparing against the token's own `aud`”; docs even said audience validation is skipped (`docs/reference/configuration.md:35-43`);
- new: `ResourceIdentifier = null` means “auth/person JWT carriers are not accepted by this middleware; agent tokens and generic signature schemes may still verify.”

ApiSurface impact should be no binary/source API diff except XML-doc text. If an internal post-configure helper class is added it is not public API.

## Wire effect

- Bare `AddAAuthResource(...Issuer...)` + `UseAAuthVerification()` changes from accepting cross-resource auth/person JWTs to `401 Unauthorized` with `Signature-Error: error=invalid_jwt` for wrong `aud` (the existing `TokenVerifier` wrong-audience path).
- `UseAAuthVerification()` with no `ResourceIdentifier` and no `AddAAuthResource` changes from accepting any auth/person JWT whose own `aud` is well-formed to `401 Unauthorized`, recommended `Signature-Error: error=invalid_request`, before `AAuthVerificationResult` or authentication claims are created.
- Agent-token requests, `hwk`/`jkt-jwt`/`jwks_uri` generic verification, endpoint `UseAAuth()` startup guard behavior, and `MapAAuthResource()` successful auth-token flows stay wire-compatible.
- Account binding becomes stricter by construction: any accepted auth token has an independent resource expectation, so `AccountVerified` can only be observed after audience binding (`AAuthVerificationMiddleware.cs:328`).

## Implementation sketch

1. In `src/AAuth/DependencyInjection/AAuthResourceServiceCollectionExtensions.cs`, after `AAuthResourceOptions.Issuer` validation and before returning, register a default-name `IPostConfigureOptions<AAuthVerificationOptions>` (or `services.PostConfigure<AAuthVerificationOptions>(...)`) that performs `verification.ResourceIdentifier ??= options.Issuer` when `options.Issuer` is non-empty. Use post-configure so ordinary `services.Configure<AAuthVerificationOptions>` and the seed defaults are normalized before the resource default, while the `UseAAuthVerification(o => ...)` delegate remains an explicit per-pipeline override because `AAuthOptionsResolver.Create()` invokes that delegate after DI post-configure.
2. In `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs`, add a private helper such as `RequireResourceIdentifier(string tokenType)` that returns `_options.ResourceIdentifier` when non-empty, otherwise throws `TokenVerificationException(SignatureErrorCode.InvalidRequest, ...)`. Use it for both `AuthTokenBuilder.TokenType` and `PersonTokenBuilder.TokenType` branches (`AAuthVerificationMiddleware.cs:225-260`). Delete the fallback to `SignatureKeyParser.Text(resolution.VerifiedToken.Payload, "aud")`.
3. Keep the existing `UseAAuth()` fail-fast check for `RequireAuthToken` endpoints (`AAuthEndpointExtensions.cs:157-168`) and `MapAAuthResource()` explicit `ResourceIdentifier = metadataOptions.Issuer` (`AAuthApplicationBuilderExtensions.cs:225-240`). They become redundant safety belts for their high-level paths, not replacements for the low-level fix.
4. Do not change `AAuthAuthenticationHandler`, `GetAAuthVerification()`, or `AAuthVerificationResult`; they should only observe fewer results because invalid/misconfigured auth/person JWT requests stop in middleware.
5. Do not set `ResourceIdentifier` on PS/AS internal `UseAAuthVerificationCore` just to appease the new check. Their valid carriers are agent JWTs (PS) or `jwks_uri` PS signatures (AS), and presented/upstream person/auth tokens are already verified in endpoint logic with explicit expected audiences. The new middleware helper will reject accidental person/auth JWT carriers in the PS pipeline fail-closed.
6. Update XML docs on `AAuthVerificationOptions.ResourceIdentifier` to state that it is required for auth/person JWT acceptance and is derived from `AddAAuthResource(options.Issuer)` for the low-level middleware.

## Dependencies and conflicts with other Rnn

- R02 (trust/four-party issuers) composes after this fix. R01 binds `aud` to the resource; R02 must still decide which auth-token issuers are trusted for three- vs four-party deployments. Do not treat derived audience as issuer trust.
- R03 (authorization endpoint) may change `MapAAuthAuthorizationEndpoint` to require person tokens. R01's middleware change helps by preventing self-audienced person/auth carriers, but R03 still owns endpoint-specific token-type requirements and error bodies.
- R06/R11 revocation and deferred flows rely on verified token `(iss, jti)` and `AAuthVerificationResult`; they will simply not see cross-resource or unconfigured auth/person tokens.
- PS/AS internals should not be “fixed” by giving them resource audiences for header person/auth JWTs; their endpoint logic already uses explicit expected audiences for body-carried resource/presented/upstream tokens. If another Rnn changes PS endpoints to accept person/auth JWT carriers, that design must supply the appropriate recipient identifier explicitly.
- No conflict with C8: this fix does not require consumers or samples to add HTTP plumbing.

## Open questions (with proposed default)

None. Proposed defaults are: derive resource audience from `AddAAuthResource(options.Issuer)` via post-configure, keep `AAuthVerificationOptions.ResourceIdentifier` public, return request-time `401 invalid_request` for auth/person JWT carriers when no audience is known, and never fall back to the token's own `aud`.
