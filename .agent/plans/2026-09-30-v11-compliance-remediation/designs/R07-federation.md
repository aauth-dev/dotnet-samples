## Problem restated (verified)

- **A17-001 / D06-02 verified.** The spec says roles are independent even when collocated (`#roles`, L434-L438), and PS-AS collapse is structurally four-party: the resource's chosen AS is also the PS, the auth token has `dwk: aauth-access.json`, and the server applies both PS consent and AS policy (`#ps-as-collapse`, L1759-L1764). Current PS routing peeks resource-token `aud` and sends every `aud == issuer` request to `HandleThreePartyAsync` (`AAuthPersonServerEndpoints.cs:588-604`). `MintAuth` never sets `Dwk`, so `AuthTokenBuilder` defaults to `aauth-person.json` (`AAuthPersonServerEndpoints.cs:292-319`; `AuthTokenBuilder.cs:66-70,163-170`). The docs still say collapse needs no code changes (`docs/workflows/federated-access.md:231-233`). A resource that intentionally chose a collocated AS is therefore downgraded to three-party identity assertion and bypasses `IAccessPolicy`.
- **A17-003 / A19-HIGH-005 verified, with one partial fix.** The spec requires the PS-to-AS client to handle `202` and `402` until `200` or terminal error (`#as-response`, L1612), requires `402` to include a polling `Location` (`#as-response`, L1631), and requires settlement then polling, composable with interaction and claims on the same URL (`#as-response`, L1640-L1642; `#ps-as-trust-establishment`, L1692-L1695; `#deferred-responses`, L2545-L2546). Current `AccessServerClient` throws `AAuthPaymentRequiredException` immediately on the first `402` (`AccessServerClient.cs:141-153`), and the PS records that as a terminal pending error (`AAuthPersonServerEndpoints.cs:1496-1501`, surfaced at `650-665` and `1548-1552`). The direct AS path now validates `NeedsPayment` has a `Location` (`AAuthAccessServerEndpoints.cs:394-403`), but the pending path still emits `402` with `ctx.Response.Headers.Location = decision.PaymentUrl` without validation or `Cache-Control` (`AAuthAccessServerEndpoints.cs:730-732`). The current `AccessDecision.NeedsPayment(string paymentUrl)` shape also names the `402 Location` as a payment URL (`IAccessPolicy.cs:137-172`; `AAuthPaymentRequiredException.cs:12-36`), while the spec's `Location` is the polling URL and payment details belong to the payment protocol headers/body (`#as-response`, L1631-L1638; `#requirement-responses`, L2326-L2328).
- **S04-01 verified, with SDK-side partial fixes and sample drift.** The spec says `sub` is already in the presented token; an AS MUST NOT request it and a PS MUST NOT include it in the claims response (`#requirement-claims`, L1680). The client rejects AS `required_claims` containing protocol-owned names before invoking the PS callback (`AccessServerClient.cs:205-207`), and the PS projection does not include reserved claims (`AAuthPersonServerEndpoints.cs:1437-1443,1691-1719`). The AS endpoint rejects invalid `AccessDecision` claim requests (`AAuthAccessServerEndpoints.cs:369-370,712`) but the helper currently uses `AuthTokenBuilder.IsIdentityClaimAllowed`, which also rejects useful identity claims such as `tenant`, `roles`, and `groups` because they are auth-token reserved claims (`AuthTokenBuilder.cs:26-36`) even though the AS projection code explicitly handles them (`AAuthAccessServerEndpoints.cs:745-780`). The sample Keycloak callback still copies Keycloak `required_claims[].name` directly into `entry.RequiredClaims` (`KeycloakAccessPolicy.cs:227-254`; `Program.cs:313-317`), and its README says the PS pushes a directed `sub` plus claims (`samples/MockAccessServers/Federated/README.md:38-43`).

## Candidate fixes

| # | Approach | Pros | Cons | Spec fit | API-surface fit (C1–C13) |
|---|---|---|---|---|---|
| 1 | Keep current routing and document collapse/payment as unsupported. | Lowest code churn. | Leaves HIGH findings open; docs remain false or must admit non-compliance; no interop with conforming AS 402. | Poor: contradicts `#ps-as-collapse` L1759-L1764 and `#as-response` L1612-L1640. | Poor: C1 permits breaking changes; C6 says SDK owns mechanics. |
| 2 | Treat every `aud == PS issuer` as collapsed whenever a local AS role is registered, and keep 402 terminal unless apps retry externally. | Simple local routing; no resource declaration seam. | Breaks existing three-party resources on cohosted deployments; AS policy can be bypassed or over-applied depending on registration; still non-compliant for 402. | Partial for collapse; poor for `#as-response` 402. | Poor: not fail-closed; violates C6 and C12 isolation. |
| 3 | Add explicit cohost/collapse binding plus a resource-declaration policy; extract a shared AS evaluation core for HTTP AS and internal collapse; add a PS payment-settlement seam and make `AccessServerClient` loop over 402; fix AS 402 and claims validation. | Spec-accurate, fail-closed, preserves three-party, reuses `IAccessPolicy`, supports tests with fake settlement, keeps consumers owning billing policy. | Breaking API for payment decision shape; more internal refactor. | Strong: implements `#ps-as-collapse`, `#as-response`, `#requirement-claims`, and deferred 402 state machine. | Strong: C1 cutover, C2/C4 seams, C5 identity, C6 mechanics vs policy, C7 constants, C12 named roles. |

## Recommendation

Choose **Approach 3**.

Add a deliberate collapse declaration rather than guessing from `aud == issuer`. A cohosted PS+AS is configured as linked named role instances with one shared role identity declaration for the same issuer, and the PS only takes the collapse path when all of these are true:

1. the verified resource token `aud` equals the linked AS role issuer (which equals this PS issuer);
2. a local AS role with that linked name is registered and has an `IAccessPolicy`;
3. a new collapse declaration seam says this resource issuer chose that local AS for this request.

The default collapse declaration is **deny** so existing `aud == PS` three-party resources remain three-party. The SDK resource helper that issues a resource token with `ChallengeOptions.AccessServer == linked AS issuer` should also expose data to configure the PS/AS cohost declaration in samples/docs, but no non-standard JWT claim should be added; if a deployment cannot prove the resource chose the AS, it must fail closed to three-party or return a clear configuration error, not silently collapse.

Payment settlement is protocol-policy, not AAuth mechanics. The SDK should own the 402 loop and same-origin polling mechanics, while the consumer supplies a settler through the R0 ladder. With no settler, the PS returns a clean terminal `payment_required` response and logs an explicit unsupported-payment warning; with a settler, the PS settles and continues polling the AS `Location` through any composed 202 steps.

## Public API delta

- **Add** `AAuthPersonAccessServerBuilder` (or equivalently named cohost builder) and `IServiceCollection.AddAAuthPersonAccessServer(name?, configureIdentity, configurePerson?, configureAccess?)`. The shared identity options set issuer, egress policy, match-host behavior, and signing material once, then register named `AAuthPersonServerOptions` and `AAuthAccessServerOptions` instances with the same issuer and role-specific DWKs. Existing separate `AddAAuthPersonServer` + `AddAAuthAccessServer` remains valid, but collapse requires an explicit link.
- **Add** `AAuthPersonServerBuilder.UseCollocatedAccessServer(string accessServerName = AAuthAccessServerBuilder.DefaultName, ...)` with R0 overloads for data / delegate / DI service, normalized to `IAAuthCollapsedFederationPolicy`. Context should include `IServiceProvider`, `HttpContext`, PS name/issuer, AS name/issuer, resource issuer, resource-token payload, scope, account, mission, and presented-token identity. Builder validation fails if the named AS is missing or its issuer differs from the PS issuer.
- **Add internal** `AAuthAccessTokenEvaluator` / `AccessTokenEvaluationContext` that factors the AS endpoint's verification-independent policy/decision handling so both `MapAAuthAccessServer` and PS collapse call the same `IAccessPolicy` seam. This can be internal to avoid exposing a second policy API.
- **Add** primitive payment types: `AAuthPaymentChallenge`, `AAuthPaymentSettlementContext`, `AAuthPaymentSettlementResult`, and `IAAuthPaymentSettler.SettleAsync(...)`. Add `AAuthPersonServerBuilder.UsePaymentSettler(...)` and `AAuthPersonServerOptions.PaymentSettler` delegate/data equivalents; defaults resolve keyed by PS name then unkeyed, then an unsupported settler.
- **Change** `AccessServerRequest` to add `OnPaymentRequired` for primitive clients (`Func<AAuthPaymentChallenge,CancellationToken,Task<AAuthPaymentSettlementResult>>?`). The Person Server wires this from the configured `IAAuthPaymentSettler`.
- **Change/remove** `AccessDecision.NeedsPayment(string paymentUrl)` and `AccessDecision.PaymentUrl`. Replace with a spec-shaped payment challenge API, e.g. `AccessDecision.NeedsPayment(AAuthPaymentChallenge challenge)` or `NeedsPayment(Action<AAuthPaymentChallengeBuilder>)`, where the AS endpoint always owns the pending `Location`; payment protocol details are `WWW-Authenticate` values and/or a response body. This is a breaking cutover (C1), not an obsolete shim.
- **Add** a claims helper such as `ClaimsRequirement.IsRequestableClaimName` / `AAuthConstants.Claims.Subject = "sub"` so AS request validation can forbid `sub` and structural JWT claims while allowing `tenant`, `roles`, `groups`, and custom identity claims. Keep `AuthTokenBuilder.IsReservedClaim` for auth-token payload projection only.
- ApiSurface impact: new public builder, options, policy/settler interfaces, context/result models, payment decision shape; removed/changed `AccessDecision.PaymentUrl` and `NeedsPayment(string)`.

## Wire effect

- Collapse requests that are explicitly declared use no PS→AS HTTP hop, but the returned auth token is AS-shaped: `iss` is the collocated AS/PS issuer, `ps` is the PS issuer, `aud` is the resource issuer, `sub` is copied from the resource token, and `dwk` is `aauth-access.json` (`#ps-as-collapse`, L1761-L1762). Undeclared `aud == PS` requests remain three-party and keep `dwk: aauth-person.json`.
- AS `402 Payment Required` responses always include `Location: {pending URL}` on the AS origin, `Cache-Control: no-store`, and payment details in `WWW-Authenticate` and/or the problem/body, not in the `Location` URL (`#as-response`, L1631-L1640; `#deferred-responses`, L2515-L2519). Pending-path `402` uses the same pending URL as earlier composed steps (`#ps-as-trust-establishment`, L1695).
- PS federation no longer treats a conforming AS `402` as terminal when a settler is configured. It calls the settler, polls the `Location`, and then handles `200`, `202 requirement=claims`, `202 requirement=interaction`, `202 requirement=clarification`, further `402`, or terminal AS errors in one bounded loop.
- If no settler is configured or settlement declines, the PS pending response is a clean terminal `402` `payment_required` problem with the AS payment details relayed where safe. This is a deliberate unsupported-payment default, not a malformed `as_unreachable`.
- AS policies that request `sub` via `NeedsClaims` fail closed before any `202 requirement=claims` is emitted. PS claims pushes never include `sub`; pushed `tenant`, `roles`, `groups`, and custom claims remain possible.

## Implementation sketch

1. **Shared cohost registration.** In `AAuthPersonServerServiceCollectionExtensions.cs` and `AAuthAccessServerServiceCollectionExtensions.cs`, add the cohost builder and validators. Register both named role options from one shared identity block, then role-specific options. Validate linked issuers at startup and keep named role isolation (C12). Extend `ServerRoleRegistrationTests.CoHostedRoles_AreIsolated` (`ServerRoleRegistrationTests.cs:398-432`) instead of relying on duplicate issuer configuration.
2. **Collapse policy seam.** Add `IAAuthCollapsedFederationPolicy` and data/delegate defaults. The data default is a set of resource issuer URLs (or `AAuthTrustRule`-like rule) plus optional predicate. Resolve keyed by PS name then unkeyed using the same keyed-forwarding pattern from ASL L1050-L1055. Add builder helpers on `AAuthPersonServerBuilder`.
3. **Extract AS evaluator.** Move the duplicated decision handling from `AAuthAccessServerEndpoints.cs:349-433` and pending reevaluation from `698-738` into an internal evaluator that accepts already verified tokens/context and returns an `IResult`/token/pending action. Preserve existing HTTP AS verification (`AAuthAccessServerEndpoints.cs:250-335`) for network calls. Collapse calls the evaluator directly after PS-side `VerifyPairAsync` (`AAuthPersonServerEndpoints.cs:1199-1215`) and PS consent.
4. **Route collapse after verification, not from an untrusted peek.** Keep the current peek only to choose the initial branch for non-equal AS audiences (`AAuthPersonServerEndpoints.cs:588-604`). For `aud == issuer`, verify the resource/presented pair as today; then ask the collapse policy. If it returns true, call the internal AS evaluator with the linked AS options/policy and mint with AS signing key and `Dwk = AuthTokenBuilder.AccessDwk`. If false, continue `HandleThreePartyAsync` unchanged. If the policy says the resource declares the local AS but no linked AS is configured, return `server_error` / startup validation failure rather than downgrading.
5. **Collapse deferred composition.** Reuse the PS pending entry for user-visible consent/clarification/interaction. For `NeedsClaims`, call `RequireConsentAsync` and `ProjectClaims` internally, then reevaluate policy without adding `sub`. For `NeedsInteraction`, surface the AS interaction URL/code through the PS pending response as current federation does (`AAuthPersonServerEndpoints.cs:1430-1435,1532-1539`). Bound internal composition with the same max-step guard as the network client.
6. **Payment API and loop.** Update `AccessServerClient.FederateAsync` (`AccessServerClient.cs:141-267`) so the composition loop handles both `202` and `402`. On `402`, require and same-origin-validate `Location`, parse payment headers/body into `AAuthPaymentChallenge`, call `request.OnPaymentRequired`, and on `Settled` poll the pending URL. Handle `402` from the initial POST, from a GET after a 202, and from a claims push response. Preserve AS terminal error relay (`#auth-token-delivery`, L1658).
7. **AS 402 correctness.** In `AAuthAccessServerEndpoints.cs`, replace both direct and pending `NeedsPayment` handling. Direct path should `Park()` and return `402` with `Location = pending path`; pending path should keep `Location = same pending path`; both set `Cache-Control: no-store` and payment headers/body from the decision. Reject `NeedsPayment` without payment details as `policy_error` but never emit `402` without a polling `Location`.
8. **Claims rule.** Replace `InvalidClaimPolicy` and pushed-claims validation (`AAuthAccessServerEndpoints.cs:369-370,581-582,620-621,712`) with a purpose-built claims-required validator: `sub` is forbidden; JWT structural claims (`iss`, `aud`, `jti`, `exp`, `cnf`, `dwk`, `ps`, `scope`, `mission_s256`, `account`, `agent`, `act`, `mission`) are forbidden unless the spec later allows them; `tenant`, `roles`, `groups`, and custom names are allowed with their existing type checks. Add validation to `AccessDecision.NeedsClaims(...)` so sample policies fail early.
9. **Samples.** In `samples/MockAccessServers/Federated/Policy/KeycloakAccessPolicy.cs:227-254`, filter/deny Keycloak `required_claims` that include `sub` before returning `NeedsClaims`; if every requested claim is forbidden, return `Deny` or a policy error rather than parking an impossible request. In `samples/MockAccessServers/Federated/Program.cs:313-317`, revalidate before assigning `entry.RequiredClaims`.
10. **Docs.** Rewrite the collapse section and payment sections as listed below; remove all “directed sub + claims” wording.

## Dependencies and conflicts with other Rnn

- **R02 (dwk pinning) owns A17-002.** This design only ensures collapse-minted tokens set `dwk=aauth-access.json` and AS HTTP/collapse discovery uses the AS role. It does not define the resource-side pinning/trust rules for accepting that DWK.
- **R06 (revocation ordering and pending dependencies).** Collapse uses AS policy and AS-shaped auth tokens without a network AS hop; implementation must still register source tokens and pending dependencies consistently with R06's revocation cascade design. Do not duplicate revocation logic in the collapse evaluator.
- **R11 (deferred polling/error codes).** The 402 loop composes with the common deferred state machine. Align exact terminal error names (`payment_required`, `as_unreachable`, `denied`, `policy_error`) with R11 if it changes polling error taxonomy.
- **R18/R19 (samples/docs).** Sample/doc edits here overlap the broader sweeps; this design names the concrete files and lines so those areas can include them rather than rediscovering them.
- **API-surface constraints.** The payment API shape is a breaking cutover (C1). The new seams must use keyed DI fallback (C4/C12) and constants for any protocol strings (C7). Do not add compatibility overloads for `NeedsPayment(string)`.

## Open questions (with proposed default)

- **None blocking.** Proposed default for collapse ambiguity: fail closed to three-party unless an explicit collapse declaration policy says the verified resource issuer chose the linked local AS. Proposed default for unsupported payment protocols: terminal `402 payment_required` with a warning, while fake/real `IAAuthPaymentSettler` implementations can make the PS fully follow the spec loop.
