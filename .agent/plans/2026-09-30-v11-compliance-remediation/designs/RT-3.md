## Details

R08 SDK-06 is mostly sound, but the design leaves an ambiguity implementers could resolve incorrectly. The recommendation says `ApplyUpdatedRequestAsync` swaps `AuthorizationExpiresAt`/`SourceTokens` atomically (R08-clarification-inputs.md:27,33) and later says to “recompute ceiling/source dependencies from the replacement pair” (R08-clarification-inputs.md:79). Draft-11 requires the updated `presented_token` be verified before replacement (draft-hardt-oauth-aauth-protocol.md L1109-L1118) and requires issued auth tokens not outlive the active `presented_token` (L1775); it does not impose a shrink-only rule relative to the original pending pair. Current code proves the original bug by replacing tokens without changing `AuthorizationExpiresAt`/sources (`AAuthPersonServerEndpoints.cs:734-751`, `IPersonPendingStore.cs:154`). Required change: say “not min(original, replacement) unless local PS policy denies the update,” and test a longer-lived replacement plus the existing shorter/revoked cases.

R09 A16-004 is directionally sound but under-specifies the timing side-channel. The design correctly moves identity to `(PersonServer, s256)` and a single evaluator (R09-missions.md:27,54,66), fixing current direct pre-loads such as `missions.GetAsync(request.MissionS256)` before authorization (`AAuthGovernanceApplicationBuilderExtensions.cs:179-181`, `:252-253`, `:284-285`). However draft-11 requires the same status, body, header set, and observably equivalent timing for absent and foreign missions (draft-hardt-oauth-aauth-protocol.md L1539-L1547). The current design says custom stores should be equivalent (R09-missions.md:31) but the tests only assert bodies/headers (R09-missions.md:94). Add a contract/test harness with a spy/fake store proving all SDK call sites go through the evaluator and no path logs/details/headers differently before authorization.

R11 SDK-11 is unsound as written because it can regress the deferred-auth-token state machine. The design moves polling into `PollCoreAsync` and has `ChallengeHandler` call that core after the first auth-token exchange (R11-polling-errors.md:62-67), but draft-11 says a resource may include a fresh resource token in `AAuth-Requirement` on a later poll response when the original resource token expires (draft-hardt-oauth-aauth-protocol.md L660-L663). Current `ChallengeHandler` keeps a loop around the pending `Location`, re-checks requirements on each 202/401, obtains a new carrier, and then polls the same pending URL (`ChallengeHandler.cs:198-303`). A generic `DeferredPoller` loop that treats 202 as “sleep and GET again” or returns terminal non-202s will miss this re-exchange/step-up path. Required change: make the internal core expose requirement responses to `ChallengeHandler` or keep an outer challenge loop, and add a test where a pending GET returns a fresh `requirement=auth-token` before final success.

R11 A19-HIGH-003 needs a different Signature-Error default. The design is right that token endpoint JSON must not invent `untrusted_*` or `policy_error`: token codes are the registered table (draft-hardt-oauth-aauth-protocol.md L2580-L2616), Signature-Key failures are 401/header-carried (L2567-L2569, L2613-L2615), and error bodies must use a code defined for the endpoint returning it (L2574). But the proposed `issuer_mismatch` default (R11-polling-errors.md:33,118) is specifically for metadata issuer not matching discovery identity (draft-hardt-httpbis-signature-key-09.txt L2077-L2085). A verified key/issuer that is simply not trusted for this endpoint fits `invalid_key`: “does not meet the server's trust requirements” (L2044-L2052). Use that unless the metadata issuer check itself failed.

R11 polling-code cleanup is sound with documentation. The spec does not literally say “no extension polling codes,” but the polling table defines `invalid_code` as 410 for an unrecognized/already-consumed code (draft-hardt-oauth-aauth-protocol.md L2617-L2640), the deferred state machine makes 410 terminal/no retry (L2557), and the current SDK emits unregistered `unknown_pending`/`unknown_interaction`/`request_withdrawn` (`DeferredState.cs:10-13`, `AAuthPersonServerEndpoints.cs:616,699,705,791,871`). The design’s `410 invalid_code` default (R11-polling-errors.md:120) is the safest conforming cutover; just record the reasoning so implementers do not reintroduce 404 AAuth bodies.

R12 SDK-09 is sound for `interaction`/`payment` only if the relay result model is tightened. The design requires only `Pending=true` -> 202+`Location` or `Unavailable=true` -> 424 for those types (R12-governance.md:91-96), which matches the interaction endpoint’s deferred relay or `interaction_unavailable` behavior (draft-hardt-oauth-aauth-protocol.md L1154-L1168, L1183-L1190) and fixes current default `Pending=false` -> `200 {status:"ok"}` (`DefaultInteractionRelay.cs:21-25`, `AAuthGovernanceApplicationBuilderExtensions.cs:328-334`). But leaving mutable `InteractionRelayResult` states ambiguous lets a relay set both or neither. Also, the design keeps the default blank answer for `question` (R12-governance.md:99-101) even though the spec says the PS delivers the question and returns the user's answer (L1174-L1181); with no channel, a fabricated empty answer is not a relay. Fail closed or require an explicit question relay.

R12 SDK-10/DOC-07 is the right direction but needs a duplicate-route guard. The design makes `.WithGovernance()` declare governance paths and has `MapAAuthPersonServer()` map them (R12-governance.md:75-85,128-135), fixing today’s metadata fallback to browser `InteractionPath` (`AAuthPersonServerEndpoints.cs:108-111,195`) and route drift. Keeping `MapAAuthGovernance()` public as a primitive (R12-governance.md:293-296) is compatible with C2, but without an idempotency/conflict rule a host can again advertise one set of PS paths and manually map another, violating C5 identity-once. Required change: high-level auto-map is authoritative; primitive mapping must either derive from the same resolved PS declaration or fail fast on conflicts.

## Cross-design conflicts and ordering

1. **Top conflict:** R09 and R12 both rewrite `AAuthGovernanceApplicationBuilderExtensions` and `GovernanceEndpoints`. Land R09’s `(PersonServer, s256)` store/evaluator first or in the same patch, then make R12 auto-mapped permission/audit/interaction/mission routes call that evaluator instead of reviving direct `GetAsync(s256)` preloads.
2. R11’s `DeferredState`/polling-code changes and R09’s “mission termination beats generic deferred expiry” must share one pre-expiry hook; otherwise mission-governed pending entries can flip between `403 mission_terminated`, `408 expired`, and `410 invalid_code` depending on landing order.
3. R08’s pending replacement gate and R09/R11 pending lifecycle changes all touch `entry.Lifecycle.Gate`; apply them as one critical-section design so updates, mission expiry, and terminal polling markers cannot interleave.
4. R08, R11, and R12 all add constants/error helpers under `AAuthConstants`/problem helpers; coordinate namespaces to avoid duplicate open-set containers and stringly-typed fallback paths.

## Open questions the orchestrator must rule on (with proposed default)

1. **Can `updated_request` bounds grow?** Default: yes, recompute from the active replacement pair; draft-11 caps to the active `presented_token` and mission/upstream/agent bounds, not the original pending pair. A PS may deny an expansive update as policy, but the SDK should not impose shrink-only mechanics.
2. **Must unknown future `platform` values be accepted?** Default: no. The vendored draft-11 registry is strict; future values require a spec/registry update and new constants.
3. **Unknown pending ID wire shape?** Default: `410 invalid_code` with a polling problem body. A bare 404 is outside the polling table and forces special poller behavior; unregistered `unknown_pending` is worse.
4. **Untrusted Signature-Key issuer error?** Default: `401 Signature-Error: error=invalid_key` for trust/role rejection; reserve `issuer_mismatch` for metadata issuer mismatch only.
5. **Should `MapAAuthPersonServer()` auto-map governance?** Default: yes when `.WithGovernance()` is set, with idempotent/conflict-checked primitive `MapAAuthGovernance()` for advanced hosts.
