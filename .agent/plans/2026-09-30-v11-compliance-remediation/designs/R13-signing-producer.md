## Problem restated (verified)

SDK-16/A02-HIGH-001 is verified. `AAuthSigningHandler.NextCreated` records the last `created` per `(key, method, authority, path)` and, when another identical target is signed in the same second, returns `last + 1` instead of wall-clock time (`AAuthSigningHandler.cs:60-81`). `SignHeadersAsync` then places that synthetic value in `Signature-Input` (`AAuthSigningHandler.cs:242`, `:340`). This was deliberate: ASL Phase 10b says cached-token identical requests otherwise collide with the resource replay cache and that the profile has no nonce (ASL L708-L718 and L933-L939). The current design conflicts with the draft-11 profile: `created` is the signature creation timestamp and the agent MUST set it to the current time (#signature-parameters L2234); verifiers MUST reject values further ahead than the validity window as `clock_skew` (#verification L2246). The audit's >60 identical requests in one second reaches `now + 61`, which the default verifier rejects (`AAuthVerifier.cs:137-141`).

The replay rationale is still valid. The profile allows a verifier to reject a duplicate `(signing-key-thumbprint, created, @method, @authority, @path)` tuple inside the window and explicitly defines no nonce mechanism (#freshness-and-replay L2270-L2272). RFC 9421 defines optional `nonce` and `tag` parameters, and encourages applications to enforce nonce uniqueness if they define it, but AAuth does not define a nonce mechanism; adding one only to this SDK would not stop conforming third-party AAuth verifiers from using the profile tuple. `AAuthVerifier` currently type-checks `nonce`/`tag` if present but gives them no replay semantics (`AAuthVerifier.cs:145-147`). The ASL decision must therefore be superseded, not silently kept: signatures still need tuple uniqueness for interop, but uniqueness cannot be achieved by future-dating `created`.

A02-HIGH-002 is verified. `CoverBody` tries to cover body components for every `HttpContent`, but when the caller supplied a body without `Content-Type` it adds only `content-digest` (`AAuthSigningHandler.cs:154-167`). The spec requires a body-bearing request to a PS endpoint, AS endpoint, or revocation endpoint to cover both `content-digest` and `content-type` (#covered-components L2211-L2214). Because the signer cannot reliably classify all destinations, its existing fail-safe choice to cover body components on every signed request with a body should remain; the missing-header case must fail closed instead of emitting a non-compliant signature.

A01-M01 is verified. The handler obtains a complete `Signature-Key` header from the provider at `AAuthSigningHandler.cs:228-229`, but emits `Signature-Input` and `Signature` with its own `Label` at `:291-293`. `JwtSignatureKeyProvider` and `JktJwtSignatureKeyProvider` accept an independent label (`JwtSignatureKeyProvider.cs:15-20`, `:22-27`; `JktJwtSignatureKeyProvider.cs:20-25`). Constructing a provider with `label: "alt"` and leaving the handler at `sig` produces `Signature-Key: alt=...` but `Signature-Input: sig=...`. Signature-Key correlates labels by equality and a verifier using `Signature-Key` MUST find the same label member (#signature-key-http-request-header L403-L424; #label-consistency L436-L441).

A04-04 is verified. Resource metadata defines `additional_signature_components` as an array of RFC 9421 component identifiers that agents MUST include when signing requests to the resource (#resource-metadata L2133), and #covered-components says agents learn further requirements from metadata or from `invalid_input` `required_input` (#covered-components L2216). `ResourceMetadata` has no typed property for the field and `FromJson` drops it (`ServerMetadata.cs:147-179`). Resource metadata producers only have the untyped `AdditionalMetadata` escape hatch (`WellKnownEndpoints.cs:180-190`, `:379-389`). The signing path can already seed components per origin (`ChallengeHandler.AdditionalSignatureComponents`, `ChallengeHandler.cs:158-167`, `:480-538`) and falls back to learning from `invalid_input` (`ChallengeHandler.cs:419-465`), but an agent that fetched resource metadata cannot type-safely seed the first request.

## Recommendation

Adopt candidates 1, 4, 6, and 8.

Re-rule ASL Phase 10b explicitly: **supersede "Signatures take a unique created per target" as implemented.** The invariant remains "do not emit a duplicate replay tuple when using the same key for the same method/authority/path," but the mechanism changes from future-dating to waiting until the current Unix second is unused for that tuple. If the caller cancels while waiting, the request fails before any signature is emitted. Do not add `nonce`/`tag` to AAuth producer signatures: RFC 9421 permits them, but the AAuth profile does not define nonce semantics and third-party verifiers can still use the profile replay tuple.

For content bodies, keep the existing conservative rule that the SDK covers body components on every signed request with `HttpContent`, because the signer cannot distinguish all PS/AS/revocation endpoints from resource endpoints. Change the missing-`Content-Type` case to fail closed. For Signature-Key labels, add a producer-side consistency check instead of changing the provider API. For resource metadata, add typed `AdditionalSignatureComponents` fields and a first-class way to seed `ChallengeHandler` from parsed `ResourceMetadata`; keep `invalid_input` learning as a fallback for resources whose metadata is absent or stale.

## Public API delta

- Add `ResourceMetadata.AdditionalSignatureComponents : IReadOnlyList<string>?` in `src/AAuth/Discovery/ServerMetadata.cs`.
- Add `AAuthResourceMetadataOptions.AdditionalSignatureComponents : IReadOnlyList<string>?` and mirror it on `AAuthResourceOptions` so `MapAAuthResourceWellKnown`/`MapAAuthWellKnown` emit the typed field instead of requiring `AdditionalMetadata`.
- Add an agent-side data helper to avoid consumer string plumbing, preferably `ChallengeHandlingOptions.ResourceMetadata` or `ChallengeHandlingOptions.AddResourceMetadata(ResourceMetadata metadata)` normalized internally into the existing per-origin `AdditionalSignatureComponents` dictionary. If the implementation wants no new method, then `ResourceMetadata.ToAdditionalSignatureComponentsSeed()` is the minimum acceptable typed helper; the plan should prefer the options helper because it fits the existing `WithChallengeHandling(options => ...)` surface.
- No public API change for SDK-16, A02-HIGH-002, or A01-M01. `AAuthSigningHandler.SignHeadersAsync` is already async; provider constructors can remain, but inconsistent labels now throw instead of producing invalid wire output.

ApiSurface impact: additive members for resource metadata and challenge seeding only. No obsolete members, dual overload shims, or compatibility modes.

## Wire effect

- SDK-produced `Signature-Input` `created` values are never ahead of the signer's current Unix second. Under same-target bursts, requests wait/cancel before signing rather than sending `created=now+n`.
- SDK-produced body-bearing signatures either include both `content-type` and `content-digest`, or no request is sent because the caller omitted `Content-Type`.
- SDK producer no longer emits mismatched labels across `Signature-Key`, `Signature-Input`, and `Signature`; mismatches fail locally.
- Resource metadata may now include typed `"additional_signature_components": [...]`. Agents that receive parsed metadata can include those components on the first signed request instead of provoking a first `401 Signature-Error: error=invalid_input; required_input=...` retry.
- No new `nonce`, `tag`, `alg`, or `keyid` signature parameter is emitted by the AAuth producer. The verifier may continue to type-check `nonce`/`tag` for generic RFC 9421 tolerance, but the replay cache remains profile-based.

## Implementation sketch

1. Replace `AAuthSigningHandler.NextCreated` with an async helper such as `WaitForCurrentCreatedAsync(method, authority, path, cancellationToken)`.
   - Keep the `ConditionalWeakTable<IAAuthSigner, ...>` so the gate is shared across handlers using the same key.
   - For a target whose last issued second is greater than or equal to `now`, compute the delay until `last + 1` becomes the current Unix second, release the lock, and await using the configured `TimeProvider` and the request cancellation token. Re-check after waking; do not reserve a future second.
   - Prune stale entries after successful issuance. Never return a value greater than `_time.GetUtcNow().ToUnixTimeSeconds()` at the moment of return.
   - Update comments to cite #signature-parameters L2234 and #freshness-and-replay L2272 and record that ASL L933-L939 is superseded.
2. In `SignHeadersAsync`, call the new async created helper before `BuildSignatureParams`.
3. Change `CoverBody` so every non-null `request.Content` merges both `content-type` and `content-digest` into `AdditionalComponentsKey`. Leave `EnsureRequiredContentDigestAsync` to compute a missing digest. Let `ResolveAdditionalComponents` throw if `content-type` is unavailable; improve its message to say body-bearing AAuth requests must set `Content-Type`.
4. Extend `TryResolveFieldValue` for additional RFC 9421 derived components the verifier already understands (`@scheme`, `@query`, `@target-uri`, and `@request-target` from `RequestUri`) so metadata-required derived components are not rejected unnecessarily. Continue to fail closed for unsupported/unavailable components.
5. In `SignHeadersAsync`, validate the handler label once with `SignatureKeyHeader.Label(Label)` and parse the provider's header with that label immediately after obtaining it. Use the validated label for both `Signature-Input` and `Signature`. Throw an `InvalidOperationException` wrapping/clarifying provider-label mismatch.
6. Add `ResourceMetadata.AdditionalSignatureComponents` parsing from a JSON array of strings. Trim, lowercase, de-duplicate preserving order, and reject non-string/blank values as malformed metadata. Keep the set open (header fields and derived components), but expose known protocol strings via constants if the implementation adds new names (C7).
7. Add `AAuthResourceMetadataOptions.AdditionalSignatureComponents` and `AAuthResourceOptions.AdditionalSignatureComponents`; emit `additional_signature_components` as a `JsonArray` in `BuildResourceMetadata` before `AdditionalMetadata` so typed fields win on collision.
8. Add the agent-side typed seeding helper. The normalization key must match `ChallengeHandler.GetOrigin` (`scheme://host[:port]`). Merge parsed metadata components with any caller-provided `AdditionalSignatureComponents`, preserving metadata order and existing per-origin overrides per the R0 data/delegate/DI ladder.
9. Leave `AAuthVerificationMiddleware` replay storage on `IJtiStore.TryRecordRequestAsync` intact. Do not key replay on nonce. A later verifier-cleanup area can align the replay key exactly to the profile tuple if desired, but this producer fix must not weaken exact-signature replay detection.

## Dependencies and conflicts with other Rnn

- R16 owns broader metadata URL/identifier validation. This design should parse and expose `additional_signature_components`, but should not duplicate all URL-validation work.
- R14 may tighten verifier parameter handling and Signature-Key JWT validation. This design must not add producer `nonce`/`tag` semantics that R14 would need to support.
- R06/R11 may touch `IJtiStore` and `AAuthVerificationMiddleware`; this design leaves replay storage semantics intact except for tests proving the producer no longer needs future timestamps.
- A04 metadata producer changes overlap with R16's metadata options work; coordinate the typed `AAuthResourceMetadataOptions` additions so `AdditionalMetadata` collision precedence remains "typed field wins."

## Open questions (with proposed default)

- **Q1: Should the same-target wait have an SDK-specific timeout?** Proposed default: no new public timeout. Await the next current second using `TimeProvider` and honor the request cancellation token; document that same-key/same-target throughput is one signed request per second when interoperable replay-cache safety is required.
- **Q2: Should producer labels be hard-coded to `sig` and label constructor parameters removed?** Proposed default: no for this remediation. Validate consistency at runtime; consider removing custom labels only in a future API simplification if generic Signature-Key demos no longer need them.
- **Q3: Should resource metadata seed `signature_window` into signer behavior?** Proposed default: no. `signature_window` is verifier tolerance, not permission to future-date `created`; it may inform retry/backoff after `clock_skew`, outside this producer fix.
