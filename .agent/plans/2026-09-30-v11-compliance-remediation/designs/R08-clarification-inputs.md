## Problem restated (verified)

- SDK-06 is still present in both PS-owned and federated pending flows. On a clarification `updated_request`, the pending POST verifies the replacement pair and replaces `ResourceToken`, `PresentedToken`, `ResourceContext`, `Scope`, and `ResourceInteraction` (`Person/AAuthPersonServerEndpoints.cs:734-751`), but `MintEntry` still mints/tracks with the entry's original `AuthorizationExpiresAt`, `ExpiresAt`, and `SourceTokens` (`:253-265`; `IPersonPendingStore.cs:121`, `:154-160`). The federated replacement helper only updates `fedRequest.PresentedTokenExpiresAt` (`AAuthPersonServerEndpoints.cs:1356-1373`), while the background tracked AS token is still bounded/recorded by `entry.ExpiresAt` and `entry.SourceTokens` (`:1447-1456`). The replacement `presented_token` therefore does not bound the grant or its revocation dependencies, contrary to #ps-token-endpoint L941-L942, #agent-response-to-clarification L1109-L1118, #resource-token-verification L767-L770, and the records/revocation rules at L2758-L2767.
- A12-02 is verified. `TryReadAgentAsserted` only checks that `justification`, `platform`, and `device` are strings (`AAuthPersonServerEndpoints.cs:1610-1626`). It accepts `platform: "ios"`/`"evil-os"` even though the registry values are only `web`, `mobile`, `desktop`, `workload`, and `self-hosted` (#aauth-platform-value-registry L3139-L3145), and it accepts overlong/control-character `device` values despite #ps-token-endpoint L949-L950 and #untrusted-input L2842-L2845.
- A12-03 is verified. `ParseStringArray(body["capabilities"] as JsonArray)` treats a non-array as absent and skips non-string/empty entries (`AAuthPersonServerEndpoints.cs:582`, `:1725-1745`). This contradicts #ps-token-endpoint L951-L952 and #untrusted-input L2842-L2845: a present malformed parameter is protocol input to reject, not an omitted capabilities declaration.
- A12-04 is verified. Normal agent answers check `entry.ClarificationRounds >= ClarificationExchange.DefaultMaxRounds` and increment after a valid POST (`AAuthPersonServerEndpoints.cs:729-760`); mission-gate clarification also checks before emitting another question (`:912-924`). The federated `TriageClarificationAsync` branch can answer an AS clarification locally, including `updated_request`, without checking or incrementing the same counter (`:1395-1407`), bypassing #clarification-chat L1123-L1126.
- A13-02 is verified. `ClarificationRequirement.FromResponse` parses `timeout` into `TimeoutSeconds` (`Headers/ClarificationRequirement.cs:69-73`), but `DeferredExchange` invokes `OnClarificationRequired` and then posts the returned response with only the overall deferred/poll cancellation token (`Agent/DeferredExchange.cs:160-168`). A callback that returns after the timeout still sends `clarification_response`/`updated_request`, violating #clarification-chat L1067-L1072.
- A13-03 is verified as a LOW agent-side gap because the PS enforces it. `TokenExchangeClient` only checks replacement account context when a clarification callback returns `Update` (`Agent/TokenExchangeClient.cs:99-116`); `ClarificationResponse.Update`/`ClarificationExchange.UpdateRequestAsync` accept any non-empty JWT-looking strings (`Agent/ClarificationExchange.cs:61-70`, `:164-181`). The same-request helper exists on the server path (`TokenVerifier.RequireSameResourceRequest`, `TokenVerifier.cs:598-607`) but is not used before the agent signs/posts an invalid `updated_request`.
- A13-05 is verified. `TokenExchangeRequest.ValidateDevice` caps at 64 UTF-16 code units but rejects every non-ASCII printable character (`Agent/TokenExchangeRequest.cs:115-140`), so a conforming `Device = "Café laptop"` cannot be sent even though #ps-token-endpoint L950 allows printable UTF-8.

## Recommendation

Adopt candidate 2.

For SDK-06, make `PersonPendingEntry` carry enough internal state to distinguish immutable issuer-side sources from the active resource/presented pair. Keep the public `AuthorizationExpiresAt` initializer shape by backing it with a private field, then add an internal method such as `ReplaceActiveAuthorization(DateTimeOffset? authorizationExpiresAt, IReadOnlyList<TokenKey> sourceTokens, string resourceToken, string presentedToken, JsonObject resourceContext, PersonResourceInteraction? interaction)`. Both the normal pending POST and federated `ApplyReplacementAsync` call one helper, `ApplyUpdatedRequestAsync`, that:

1. verifies the replacement pair with `VerifyPairAsync`;
2. calls `RequireSameRequest` and account binding;
3. recomputes the authorization ceiling as `min(issuance.ExpiresAt, replacementPresented.ExpiresAt, mission.ExpiresAt when present)`;
4. registers source dependencies for the active presented token plus the original agent/subagent/upstream/binding/mission indexes;
5. swaps `ResourceToken`, `PresentedToken`, `ResourceContext`, `Scope`, `ResourceInteraction`, `AuthorizationExpiresAt`, and `SourceTokens` atomically while holding `entry.Lifecycle.Gate`.

An attacker can try to replace a request after approval but before mint, revoke the replacement presented token, or race old and new replacement pairs. The helper closes this by running under the entry lifecycle gate, by rechecking/registering source dependencies before accepting the replacement, and by relying on R06's source guard again immediately before mint/federation. Old registered dependencies may remain in the inventory, but the grant is tracked against the active source set only; stale dependencies must not over-revoke the new grant.

For A12-02/A12-03/A13-05, add a single internal validator (for example `AAuth.Protocol.AAuthProtocolInput`) used by both producer and consumer paths:

- `ValidatePlatform(string? value, string parameterName)` allows `null`, otherwise exact ordinal match with `AAuthConstants.Platforms.Web/Mobile/Desktop/Workload/SelfHosted`.
- `ValidateDevice(string? value, string parameterName)` allows `null`, requires a non-empty printable Unicode scalar sequence of at most 64 runes, rejects invalid surrogate pairs and Unicode categories `Control`, `Format`, `Surrogate`, `PrivateUse`, and `OtherNotAssigned`, and allows non-ASCII printable text such as `Café laptop`.
- `ReadCapabilities(JsonObject body, out bool present)` rejects a present non-array, non-string members, empty/whitespace strings, and invalid RFC token syntax with `400 invalid_request`; a present empty array returns `Array.Empty<string>()`, while absence returns `null`. Unknown valid capability tokens are preserved and later ignored by recipients, as required by #aauth-capabilities L2470-L2477.
- `ValidateCapabilities(IEnumerable<string>)` is called by `TokenExchangeClient.AddRequestParameters`, `AAuthClientBuilder.WithCapabilities`, `AAuthSigningHandler` before formatting `AAuth-Capabilities`, and PS body parsing.

Move known open-set values to `AAuthConstants.Platforms` and `AAuthConstants.Capabilities` per C7/ASL L131-L133. Replace string literals (`"interaction"`, `"clarification"`, `"payment"`) in inference, tests, samples, and docs. Because C1 forbids compatibility shims, remove `AAuthCapabilitiesHeader.Capabilities` rather than leaving duplicate constant homes.

For A12-04, add one `ConsumeClarificationRound(PersonPendingEntry entry)` helper near the pending handlers. It checks `entry.ClarificationRounds >= ClarificationExchange.DefaultMaxRounds`, marks the entry denied when appropriate, and increments exactly once for every accepted clarification answer/update. Use it in the normal pending POST after syntactic validation but before applying the answer/update, and in the `TriageClarificationAsync` branch before returning a local answer to the AS. Mission-gate question emission may keep checking the same limit before issuing another `202`; the consuming helper is still the only increment site.

For A13-02, enforce the deadline in `DeferredExchange` at the moment a `requirement=clarification` response is parsed. Create a linked per-round token whose deadline is `min(caller/poll cancellation, clarification.TimeoutSeconds)`. Pass that token to `OnClarificationRequired`; await with `WaitAsync(roundToken)`; if it cancels because the clarification timeout expired, throw `AAuthInteractionTimeoutException` (or a new clarification-specific subtype only if R11 creates one) and do not call `ClarificationExchange.ApplyAsync`. Check `roundToken.IsCancellationRequested` again immediately before `ApplyAsync` so a callback that wins a race by returning just after the deadline cannot sign/post a late response.

For A13-03, add agent-side structural pre-validation before `ClarificationExchange.ApplyAsync` posts an update: decode the original resource token, replacement resource token, original presented token, and replacement presented token; call `TokenVerifier.RequireSameResourceRequest(original, replacement)`; require replacement `presented_jti` equals replacement presented `jti`; require replacement presented `sub`, `mission_s256`, and `tenant` still match the replacement resource token; require `agent_jkt` matches the signing key captured from the signed request; and keep the existing account check. This is not a substitute for PS signature/revocation verification, but it suppresses locally non-conforming `updated_request` posts from buggy/malicious callbacks.

## Public API delta

- Add `AAuthConstants.Platforms` with `Web`, `Mobile`, `Desktop`, `Workload`, `SelfHosted`.
- Add `AAuthConstants.Capabilities` with `Interaction`, `Clarification`, `Payment`.
- Remove/move `AAuthCapabilitiesHeader.Capabilities` to the new constants home (breaking but single-cutover per C1).
- No new consumer policy seam. `TokenExchangeRequest.Platform` and `Device` remain string properties, but their setters/sending path now fail fast on invalid values; `Device` accepts printable Unicode instead of ASCII only.
- No intended public pending-store API change: keep `PersonPendingEntry.AuthorizationExpiresAt` publicly init-only via a private backing field, and add only internal replacement/source-state members. If implementation cannot avoid changing `AuthorizationExpiresAt` to `set`, record the ApiSurface diff as a public mutability change.

## Wire effect

- PS `/token` and `/person` now return `400 {"error":"invalid_request"}` before the asserter for invalid `platform`, invalid/overlong/control-character `device`, present non-array `capabilities`, non-string capability entries, empty/whitespace capability entries, or syntactically invalid capability tokens.
- Present `capabilities: []` now refreshes capabilities to an empty list instead of being treated as absent; omitted `capabilities` remains `null`/mission-captured behavior.
- A conforming non-ASCII printable `device` is now emitted by agents instead of throwing locally.
- Invalid agent-produced `updated_request` replacement pairs are not posted to the PS; callers see a local token/protocol exception.
- Clarification callbacks that miss `timeout` produce no POST/DELETE to the pending URL after the deadline; the exchange fails locally with a timeout exception.
- Grants minted or federated after `updated_request` are capped by the active replacement `presented_token` expiry and tracked against the active replacement source tokens, so revocation/expiry can now fail or shorten grants that previously succeeded.

## Dependencies and conflicts with other Rnn

- R06 should own the reusable source-revocation guard. R08 should store/recompute the active source set for replacements and call the R06 guard, not create a parallel revocation mechanism.
- R07 federation changes may touch the same `HandleFederatedAsync`/`AccessServerRequest` code; apply R08 replacement-ceiling/source updates after any federation collapse/refactor.
- R09 mission work touches mission gates and pending entries; share `ConsumeClarificationRound` so mission clarification and triage cannot diverge.
- R11 deferred error-code work may introduce a more specific timeout exception/status mapping. Until then, reuse `AAuthInteractionTimeoutException` for client-side clarification timeouts.
- R15 agent-client behavior may update challenge handling and capability inference; keep the constants/validation helper as the single source for body and header capabilities.

## Open questions (with proposed default)

1. **What exactly is "printable UTF-8" for `device`?** Proposed default: valid Unicode scalar values, reject control/format/surrogate/private-use/unassigned categories, count runes for the 64-character limit, allow spaces and non-ASCII letters/symbols.
2. **Should `capabilities: []` be distinguishable from omission?** Proposed default: yes. Present empty means "refresh to no capabilities"; omitted means "use captured mission capabilities" where the spec says so.
3. **Should non-positive clarification `timeout` be parsed or rejected?** Proposed default: reject a present `timeout <= 0` as malformed clarification input; if maintainers prefer lenience, treat it as an already-expired deadline and still suppress POST.
4. **Can `AAuthCapabilitiesHeader.Capabilities` remain as aliases?** Proposed default: no, because C1 forbids compatibility shims and C7 says open-set protocol values live in `AAuthConstants`.
