## Verified compliant

- Calendar and Trips use the high-level `UseAAuth` path with configured PS auth-token issuers and matching revocation issuer predicates — `Calendar/Program.cs:69-77`, `Trips/Program.cs:69-76`.
- Wallet mitigates SDK-02 for the four-party sample by setting the AS as the auth-token issuer, the PS allow-list for person tokens, and `AccessServer` for challenges; revocation accepts only the AS or trusted PSes — `Wallet/Program.cs:70-82`.
- Catalog and Documents avoid SDK-01 on their manual verification paths by setting `ResourceIdentifier` to the resource issuer and configuring accepted token issuers — `Catalog/Program.cs:56-63`, `Documents/Program.cs:32-39`.
- Bookings verifies auth-token audience via `resourceUrl`, then pins the auth-token issuer to the configured AS before accepting the token — `Bookings/Program.cs:400-415`.
- Bookings composes the SDK-03 single-use mitigation for per-call R3 tokens: per-call completions go through `IAAuthSingleUseGate` keyed by auth-token `jti`, retaining the result for replay — `Bookings/Program.cs:87-89`, `:276-279`.
- Bookings verifies per-call retry parameters against the stored proposal before execution and returns a fresh auth-token challenge for unapproved proposals — `Bookings/Program.cs:541-565`, matching R3 `#per-call-flow`, L673-L676.
