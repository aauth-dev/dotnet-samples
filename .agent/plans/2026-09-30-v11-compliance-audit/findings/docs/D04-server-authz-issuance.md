## Verified compliant

- Direct middleware guidance avoids SDK-01: the MVC example sets `options.ResourceIdentifier = resourceUrl` before `UseAAuthChallenge` (`docs/server/authn-authz.md:193-201`), matching auth-token audience verification requirements (`#auth-token-verification`, L1812).
- Person-token prose correctly says identity is not authorization and carries no `scope`/`account` (`docs/server/token-issuance.md:89-94`), matching `#person-token-not-authorization` L2894-L2896 and person-token structure L892-L923.
- Resource-token docs use draft-11 claim names (`ps`, `presented_jti`, `agent_jkt`, `mission_s256`, `tenant`) and `typ=aa-resource+jwt` (`docs/server/token-issuance.md:20-87`), matching `#resource-token` L725-L781.
- Auth-token docs use draft-11 `typ=aa-auth+jwt`, `dwk=aauth-person.json`/`aauth-access.json`, `cnf.jwk`, no agent identifier/delegation chain (`docs/server/token-issuance.md:111-158`), matching `#auth-tokens` L1766-L1783.
- Resource-token/presented-token verification docs require both `resource_token` and `presented_token`, `aud`, `agent_jkt`, `ps`, pair matching, and mission checks (`docs/server/token-issuance.md:242-303`), matching `#ps-token-endpoint` L924-L951 and `#resource-token` L761-L768.
- Person Server consent presentation guidance separates resource-asserted and agent-asserted content and requires sanitizing Markdown (`docs/server/token-issuance.md:492-503`), matching consent-presentation requirements L1035-L1039.
- Known unsupported features from `SPEC-VERSION.md` (Budgets, `accept_signature_algs`, X.509/cached carriers) are not advertised by these three docs.
