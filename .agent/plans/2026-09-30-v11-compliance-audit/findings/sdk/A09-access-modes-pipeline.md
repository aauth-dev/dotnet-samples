## Verified compliant

- Scope enforcement uses the verified token's scope and only succeeds for `Authorized` (auth-token) level — `src/AAuth/Server/Authorization/AAuthScopeHandler.cs:31`, `src/AAuth/Server/Authorization/AAuthScopeHandler.cs:35`; `RequireAAuth` also requires `AAuthLevel.Authorized` before adding scope/role requirements — `src/AAuth/Server/Endpoints/AAuthEndpointExtensions.cs:48`, `src/AAuth/Server/Endpoints/AAuthEndpointExtensions.cs:51`.
- Person tokens are rejected by the token verifier where an auth token is required: middleware dispatches `aa-auth+jwt` to `VerifyAuthToken` and `aa-person+jwt` to `VerifyPersonToken` — `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:233`, `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:243`; `TokenVerifier.Verify` checks exact `typ` — `src/AAuth/Tokens/TokenVerifier.cs:109`; covered by `tests/AAuth.Conformance/AuthTokens/AuthTokenVerificationTests.cs:157`.
- `RequireAuthToken` challenge flow does not let a bare agent token satisfy an auth-token endpoint: it returns `requirement=person-token` for agent tokens and issues a resource-token challenge only after a verified person token — `src/AAuth/Server/Challenge/AAuthChallengeMiddleware.cs:125`, `src/AAuth/Server/Challenge/AAuthChallengeMiddleware.cs:127`, `src/AAuth/Server/Challenge/AAuthChallengeMiddleware.cs:134`; covered by `tests/AAuth.Conformance/HttpSignatures/ChallengeMiddlewareTests.cs:328` and `:342`.
- Resource-token challenge construction sets `aud` to the configured AS for four-party mode or the verified person token's PS for three-party mode, and copies mission/person context from the presented token — `src/AAuth/Server/Challenge/AAuthChallengeMiddleware.cs:169`, `src/AAuth/Server/Challenge/AAuthChallengeMiddleware.cs:170`, `src/AAuth/Server/Challenge/AAuthChallengeMiddleware.cs:175`.
- Missing or malformed AAuth signature inputs fail closed before the handler runs — `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:93`, `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:97`, `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:168`, `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:182`.
- Trust allow-list semantics are fail-closed when a list is explicitly configured: an empty `Allowed` set denies all because evaluation rejects issuers not contained in the set — `src/AAuth/Server/AAuthTrustPolicy.cs:67`, `src/AAuth/Server/AAuthTrustPolicy.cs:73`, `src/AAuth/Server/AAuthTrustPolicy.cs:89`.

## Not assessed / out of slice

- Full token structure, resource-token verification, presented-token verification, revocation, and PS/AS token endpoints are owned by other audit slices; supporting files were read only to prove this slice's dispatch/trust behavior.
- Application-specific handlers supplied to `MapAAuthAuthorizationEndpoint` can return arbitrary success bodies; this audit assessed the SDK helper's preconditions and built-in error status, not every downstream resource handler's response shape.
- R3 `per-call` semantics and access annotations are outside this protocol slice; only the core metadata value was noted as the logged INFO extension above.
