## Verified compliant

- `upstream_token` `typ` is read from the JWT header and only person/auth token types are accepted — `src/AAuth/Tokens/UpstreamTokenValidator.cs:102`, `src/AAuth/Tokens/UpstreamTokenValidator.cs:107`.
- Upstream `aud` is verified against the intermediary agent-token `iss`, and upstream `cnf.jwk` is compared to the calling agent key rather than the intermediary signing key — `src/AAuth/Tokens/AgentIssuanceContext.cs:79`, `src/AAuth/Tokens/UpstreamTokenValidator.cs:106`, `src/AAuth/Tokens/UpstreamTokenValidator.cs:109`.
- Call-chain routing uses the upstream token's PS (`iss` for person token, `ps` for auth token), not the intermediary's own `ps` — `src/AAuth/Server/CallChaining/CallChainingRouter.cs:39`, `src/AAuth/Server/CallChaining/CallChainingRouter.cs:42`.
- Downstream exchanges carry `presented_token` and `upstream_token` as body parameters while the request is agent-signed by the intermediary channel — `src/AAuth/Server/CallChaining/CallChainingHandler.cs:75`, `src/AAuth/Server/CallChaining/CallChainingHandler.cs:82`, `src/AAuth/Agent/TokenExchangeClient.cs:104`, `src/AAuth/Agent/TokenExchangeClient.cs:250`.
- Downstream-issued auth tokens are bound to the resource token's directed `sub`, not copied from upstream; migration tests explicitly cover copied-`sub` rejection/avoidance — `src/AAuth/Person/AAuthPersonServerEndpoints.cs:1387`, `src/AAuth/Access/AccessServerRequest.cs:61`, migration log L377–L380 and L1171–L1179.
- Auth tokens do not carry an `act`/delegation-chain claim; reserved-claim checks block `act` injection — `src/AAuth/Tokens/AuthTokenBuilder.cs:26`, `src/AAuth/Tokens/AuthTokenBuilder.cs:31`.
- Direct PS token requests signed by a sub-agent token are rejected before body processing — `src/AAuth/Person/AAuthPersonServerEndpoints.cs:333`, `src/AAuth/Person/AAuthPersonServerEndpoints.cs:335`; the shared issuance verifier also rejects them — `src/AAuth/Tokens/AgentIssuanceContext.cs:65`.
- The agent-token builder enforces sub-agent local-part `parent+discriminator` and refuses sub-sub-agent parent identifiers when producing tokens — `src/AAuth/Tokens/AgentTokenBuilder.cs:115`, `src/AAuth/Tokens/AgentTokenBuilder.cs:143`, `src/AAuth/Tokens/AgentTokenBuilder.cs:148`, `src/AAuth/Tokens/AgentTokenBuilder.cs:153`.
- Parent-mediated sub-agent authorization checks that `subagent_token.parent_agent` names the signing parent and that the issuers match; issued-token key selection uses the sub-agent key — `src/AAuth/Tokens/AgentIssuanceContext.cs:90`, `src/AAuth/Tokens/AgentIssuanceContext.cs:91`, `src/AAuth/Tokens/AgentIssuanceContext.cs:105`.
- AS-side upstream verification uses the signing PS as expected person server and deliberately does not re-check AS-issued upstream auth-token `iss`, matching L1833 — `src/AAuth/Access/AAuthAccessServerEndpoints.cs:290`, `src/AAuth/Access/AAuthAccessServerEndpoints.cs:294`, `src/AAuth/Access/AAuthAccessServerEndpoints.cs:296`.
- Resource-token PoP for parent-mediated sub-agents is checked against the key that will receive the auth token (`issuance.ConfirmationKey`, the sub-agent key) at PS/AS — `src/AAuth/Access/AAuthAccessServerEndpoints.cs:309`, `src/AAuth/Tokens/TokenVerifier.cs:580`.
- PS-hosted resource interaction relay validates the resource interaction URL/code, uses a PS-hosted `/interaction/resource` entry point, stores state/cookie, and redirects back through the PS callback rather than asking the agent to handle the resource URL directly — `src/AAuth/Person/PersonResourceInteraction.cs:42`, `src/AAuth/Person/PersonResourceInteraction.cs:85`, `src/AAuth/Person/PersonResourceInteraction.cs:98`.
