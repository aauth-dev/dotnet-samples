## Verified compliant

- An agent can lazily obtain an agent token before its first signed request: `TokenRefreshHandler` acquires under a semaphore before calling the inner handler — `src/AAuth/Agent/TokenRefreshHandler.cs:41-53`, `87-105`.
- Default agent-token refresh margin is five minutes and concurrency is single-flight per handler — `src/AAuth/Agent/TokenRefreshHandler.cs:60-78`; covered by `tests/AAuth.Tests/Agent/TokenRefreshHandlerTests.cs:151-163`.
- In the challenge-handling pipeline, agent-token refresh wraps the challenge handler, so agent refresh happens before person/resource/auth exchanges on that request — `src/AAuth/AAuthClientBuilder.cs:771-783`.
- 401/202 `auth-token` challenges trigger fresh resource-token exchange and retry; refused presented tokens are not simply reused — `src/AAuth/Agent/ChallengeHandler.cs:202-219`, `287-294`.
- Cache keys include full agent token, upstream token, mission, audience, account, and signing-key thumbprint, preventing cross-resource/upstream/mission reuse and naturally avoiding old carriers after agent-token string rotation — `src/AAuth/Agent/AAuthTokenHolder.cs:81-88`; tests document/share concurrency behavior at `tests/AAuth.Conformance/Agents/TokenCacheSharingTests.cs:7-10`, `52-66`.
- The holder and cache are thread-safe for their intended state: volatile current-token slot, cache lock, per-key in-flight single-flight — `src/AAuth/Agent/AAuthTokenHolder.cs:13-17`; `src/AAuth/Agent/AAuthTokenCache.cs:51-53`, `86-92`.
- Single-key AP refresh signs an empty POST with the durable key under `hwk` and sends no resource/person-token activity data to the AP during refresh — `src/AAuth/Agent/AgentProviderClient.cs:150-164`.
- Two-key refresh request proof itself is correctly constructed: fresh ephemeral key, durable-key naming JWT with `jti`, `exp`, and `cnf.jwk`, and HTTP signature by the ephemeral key — `src/AAuth/Agent/AgentProviderClient.cs:197-215`; `src/AAuth/Agent/NamingJwtBuilder.cs:40-49`.
- `EnrolledBuilder` prevents accidental use of two-key refresh in its fixed-key convenience pipeline — `src/AAuth/EnrolledBuilder.cs:74-80`, `165-167`.
- Enrollment signs the public-key registration body with the enrolled key and optionally includes pluggable attestation; the bootstrap draft makes attestation optional — `src/AAuth/Agent/AgentProviderClient.cs:72-94`; `src/AAuth/Agent/IPlatformAttestor.cs:10-26`; spec `#optional-attestation`, L205-L247.

## Not assessed / out of slice

- AP server-side behavior for refusing refresh, enforcing attestation freshness, revoking at the PS, and capping AP-issued token lifetime was not assessed; this slice only had SDK client/self-issued producer code.
- The protocol rationale says every agent needs a distinct AP and not self-signed token (`#why-agents-are-under-an-agent-provider`, L3446), while the AP section allows a self-hosted agent to be its own AP (`#agent-provider`, L482) and the informational bootstrap draft says self-hosted agents self-issue (`#refresh-patterns`, L326). I treated SDK self-hosted support as spec ambiguity rather than a scored defect; A06-03 covers only the oversized lifetime it can emit.
- Person Server revocation reporting behavior to the AP is server-side. In the assigned agent/AP client code, refresh sends an empty body and I found no resource/person-token activity report to the AP; enrollment may send the configured `ps` because the AP-issued agent token carries that claim.
- Jitter is not present in the assigned code, but no jitter requirement appears in the assigned normative protocol lines.
