## Verified compliant

- Ed25519 is the default generated signing key and ES256 is implemented; both public JWK exporters include fully specified `alg` values — `src/AAuth/Crypto/AAuthKey.cs:101`, `src/AAuth/Crypto/EcdsaAAuthKey.cs:104`.
- Keys with absent/unsupported/polymorphic/symmetric `alg` values are rejected as `unsupported_algorithm`, and `kty`/`crv` mismatches are rejected as `invalid_key` in the default JWK path — `src/AAuth/Crypto/KeyFactory.cs:48`, `src/AAuth/Crypto/KeyFactory.cs:53`.
- The signer emits the three HTTP signature headers and its base component order is `@method`, `@authority`, `@path`, `signature-key` — `src/AAuth/HttpSig/AAuthSigningHandler.cs:35`, `src/AAuth/HttpSig/AAuthSigningHandler.cs:291`.
- For body requests with `Content-Type` present, `SignAsync` requests and computes `content-digest`, then covers `content-type` and `content-digest` — `src/AAuth/HttpSig/AAuthSigningHandler.cs:165`, `src/AAuth/HttpSig/AAuthSigningHandler.cs:207`.
- The signer does not emit `alg`, `keyid`, `tag`, or `nonce` signature parameters; it appends only `created` after the component list — `src/AAuth/HttpSig/AAuthSigningHandler.cs:340`.
- The verifier requires the base components, requires integer `created`, enforces the 60-second default window with `invalid_signature` for stale and `clock_skew` for too-far-future values, and honors `expires` when present — `src/AAuth/HttpSig/AAuthVerifier.cs:134`, `src/AAuth/HttpSig/AAuthVerifier.cs:135`, `src/AAuth/HttpSig/AAuthVerifier.cs:138`, `src/AAuth/HttpSig/AAuthVerifier.cs:140`, `src/AAuth/HttpSig/AAuthVerifier.cs:142`.
- `keyid` conflicts are rejected while the verification key still comes from `Signature-Key` resolution — `src/AAuth/HttpSig/AAuthVerifier.cs:70`, `src/AAuth/HttpSig/AAuthVerifier.cs:71`.
- Middleware maps missing signature headers to `401`/`invalid_signature` and maps `invalid_input` responses with `required_input`; unsupported algorithms get `Accept-Signature-Alg` — `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:93`, `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:402`, `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:405`.
- When `content-digest` is covered, the middleware recomputes and compares the body digest before calling the endpoint — `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:143`, `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:154`.
- Replay caching is optional in the profile; when configured, the SDK records verified requests through `IJtiStore.TryRecordRequestAsync` with an expiry derived from `created + MaxAge` — `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:205`, `src/AAuth/Server/Verification/AAuthVerificationMiddleware.cs:207`, `src/AAuth/Server/InMemoryJtiStore.cs:31`.

## Not assessed / out of slice

- `#scheme-rejection` L2256–L2267 was intentionally skipped; another agent owns it.
- JWT assertion claim validation (`typ`, `aud`, `iss`, `iat`, `exp`, revocation semantics beyond `Signature-Key` error mapping) belongs to token-verification slices.
- Reverse-proxy deployment requirements for preserving `Host`/scheme or applying ASP.NET Core forwarded-header middleware were not assessed beyond noting the verifier uses `HttpRequest.Host` and `HttpRequest.Scheme`.
- Resource-specific `additional_signature_components` publication and challenge learning outside the verifier’s `requiredComponents` parameter were not fully assessed in this slice.
